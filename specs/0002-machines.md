# Machines

## Selectors

A job asks for one label, its **selector**: a shape, and optionally Spot.

```
lanescape-<vCPUs>vcpu-linux-<amd64|arm64>[-spot]
```

```yaml
runs-on: lanescape-2vcpu-linux-amd64
runs-on: lanescape-80vcpu-linux-amd64-spot
```

A selector names a machine and nothing else: no image, disk, scope or run. Machines are general: every machine of a selector is the same, booted from the service's base image (specs/0003-disks.md), and holds nothing of any run's until the service admits a job on it. So GitHub may give a job any machine of its selector, made for whichever of its consumer's jobs, and what the job then installs and works on, it sees to in its own steps: it sets the machine up from its own commit (Setting up a machine, below), and asks for a work disk of a family, which the `disk` action attaches (The work disk, below). What a job doesn't say, the service works out for itself from GitHub's records of the run, never from anything the job says: the run's scope (below) and the key of the saved disk its commit asks for (specs/0003-disks.md).

**Shapes.** Each names the machine types that satisfy it, in order of preference, in `config/shapes.yaml`: at least that many vCPUs of that architecture, the memory the shape promises, and the size of its work disk. For example, `lanescape-80vcpu-linux-amd64` is `n4-highcpu-80`, then `c4-highcpu-96` when N4's quota or capacity is short; `lanescape-16vcpu-linux-arm64` is `c4a-highcpu-16`. The **smallest shape** is the first in `config/shapes.yaml`, `lanescape-2vcpu-linux-amd64`. Machines are made in zones `northamerica-northeast1-a`, then `-b`. Every machine boots the service's base image for its architecture (specs/0003-disks.md) on a boot disk of `boot_disk_gb`, 100 GB, which also holds the runner's working directory and whatever the job's setup installs, and gets a work disk only when its job asks for one (below), each with 3,000 IOPS and 400 MiB/s.

**Provisioning.** Machines are standard unless the selector says `-spot`. Spot is each job's own choice, made in its selector, never a class of job's. A Spot machine costs less and can be preempted at any time, so it suits a job that resumes from its work disk, picking up on a rerun where its preempted machine left off (below), or that is cheap to rerun. A long job that can't resume should be made resumable, rather than run on a standard machine because it can't. A standard machine is never preempted; Compute Engine migrates it live for host maintenance. A `-spot` selector's machine is standard only when no zone has Spot capacity or quota for any of its shape's machine types: it costs more, and the job runs as on any standard machine.

**Names.** A selector is in lowercase: labels compare without regard to case, as GitHub's do, so the service works with a selector in lowercase throughout. A label that starts with `lanescape-` but isn't a selector of a shape `config/shapes.yaml` offers gets no machine: the service cancels the run of a queued job that names one, and logs why.

**Scope** is where the run may read and save disks, and it's what keeps one run's disks from reaching another's jobs:

| Scope | The run | Reads | Saves |
|---|---|---|---|
| `main` | A push to the default branch | Main's | Main's |
| `branch-<name>` | A push to a long-lived branch the consumer lists | Its branch's, then main's | Its branch's |
| `pr<number>` | A pull request's run, the repository's own or an approved contribution | Its pull request's, then its base's: the listed branch's it targets, or else main's | Its pull request's |
| `read` | Anything else | Main's | Nothing |

What a scope reads and saves are its saved disks (specs/0003-disks.md). What it reads, in that order, is its **restore chain**: its own scope, if it saves, then its **base**, the scope it falls back to, if it has one. A pull request's base is the listed branch it targets, or else main's; a long-lived branch's push falls back to main's, so a new branch starts warm; `read` reads main's alone, as main does.

**Long-lived branches.** A consumer lists its long-lived branches, such as release branches, in its default branch's `.github/runners.json`, under `"branches"`, each with a name for its scope (specs/0005-interface.md): `{"support/v1": "v1"}` gives pushes to `support/v1` the scope `branch-v1`, which saves and reads as main's does for the default branch. A name is 1 to 16 lowercase letters and digits, starting with a letter. The service ignores an entry for the default branch, one whose name isn't valid, and every entry whose name another entry shares, and logs why. Listing a branch trusts everyone who can push to it, as main's scope trusts everyone who can push to the default branch, so a consumer lists only branches it protects as it does the default branch.

## Binding a run

The service never takes a run's scope from a job's steps or from a label. Each run is **bound** once, in the bucket, and every decision about the run's jobs that needs its scope uses that binding. The binding is created only if absent, so nothing later changes it.

**A run is bound by its first job's check.** Nothing in a workflow has to ask. Before a job's first step, its runner's job-started hook asks the service whether the job may run (A machine's life, below). Every machine boots the service's base image, and on a fresh one nothing but the service's own programs and GitHub's runner has run yet: the machine is new, it's for one job, and the job's steps haven't started. So what the hook sends along with its question is what GitHub told the runner about the job: its event's name, `GITHUB_REF`, `GITHUB_REF_TYPE` and `GITHUB_SHA`, and from the event's payload, `GITHUB_EVENT_PATH`, a pull request's number, head repository ID and head commit. If the job's run has no binding, the service binds it from those, after checking them against GitHub's own records of the run, which it reads with the App: the run is the one GitHub shows on that runner, its event and head commit are the run's, and each rule's conditions below hold. The service keeps the facts of a machine's first check, and a retried check from that machine, asking again after the service told it to wait, is decided from those kept facts, never new ones; once a machine's job is admitted, nothing from that machine binds anything again.

- **`main`** only for a `push` whose ref is `refs/heads/<default branch>`, with ref type `branch`, whose head commit is on the default branch, by GitHub's comparison of the two. A tag, or another branch named like the default branch, fails both.
- **`branch-<name>`** the same way, for a `push` whose ref is `refs/heads/<branch>`, for a branch listed with that name in the default branch's `.github/runners.json`, read with the App, and whose head commit is on that branch.
- **`pr<number>`** for a `pull_request` run, from its ref, `refs/pull/<number>/merge`, which names the pull request that triggered it; only if GitHub's record of the run lists that pull request among its own, when it lists any, and GitHub's pull request of that number targets this repository, has the run's head repository, which is this one, and has the run's head commit among its commits. So a run of one of two stacked pull requests can't claim the other, whose commits hold its head. A same-repository pull request's author controls its workflow, so nothing the workflow's steps say is used.
- **`pr<number>`** for an approved contribution's `pull_request_target` run, whose ref is the base branch's and names no pull request, from its event's pull request: only once GitHub records an approval of the `contribution` environment for the run, and only if the pull request of that number is open, targets this repository, and has the event's head repository, with the event's head commit among its commits. Until it's approved, the run is unbound (Unbound runs, below). An approved run whose pull request fails those conditions, such as one closed or force-pushed while its run waited for approval, is bound to `read`, and its jobs are failed, saying why (Failing a job, below), its contribution job included, so nothing waiting on that job runs.
- **`read`** for anything else, and for a pull request run whose head commit and repository are the head of more than one open pull request. That pull request run's jobs are failed, saying that each head commit must be the head of one open pull request (Failing a job, below), since nothing it built would persist.

A binding also records the run's **commit**, whose files decide its saved disks' keys: a push's head commit, a pull request run's head commit, the pull request's own, and a contribution's head commit, the event's. A binding of a pull request also records its base: the scope of the branch it targets, by GitHub's pull request when the run is bound, if that branch is listed, or else main's. A pull request retargeted later keeps its run's base; its next run binds afresh.

If GitHub can't be reached, or limits the service's requests, while a binding is being checked, no binding is made; the check answers the hook to wait and ask again, and only a confirmed answer binds a run.

**Unbound runs.** Until it's bound, a run's queued jobs get machines like any job's, and a job admitted on one gets nothing that needs a scope: neither the `disk` nor the `save-disk` action is answered for an unbound run (specs/0005-interface.md). A `pull_request_target` run is bound only once a maintainer has approved it, so a consumer that runs approved contributions gives such a run one **contribution job**, which names the environment `contribution`, so that GitHub holds it until a maintainer approves, which every other job of the run on the service's machines needs, and which runs only the default branch's code. Its check binds the run. Before that, a `pull_request_target` run's job is admitted only if its selector is the smallest shape, standard: a machine with nothing saved and no work disk. That's what its contribution job needs, and what a `pull_request_target` workflow that runs only the default branch's code needs, which GitHub runs for a contributor's pull request without anyone's approval. A job of an unbound `pull_request_target` run with any other selector is failed, saying why.

**Failing a job.** When the service knows a job can't run, it stops the job, saying why, rather than leave it queued or let any of its steps run. The reason is decided for the job, at its check, from GitHub's records and the job's run, never from the machine: whichever of its selector's machines the job lands on, the check answers the hook with the reason, which the hook prints in the job's log, and then the hook waits and never returns, while the service cancels the job's run and stops the machine. A hook that exited instead would fail the job but still let GitHub's runner run every step whose condition is `always()` or `failure()`; a hook that never returns, on a machine that stops, lets none of them run. So the job ends cancelled, with the reason in its log, and so does its run, which a workflow whose jobs the service can't serve couldn't finish anyway. A job the service will fail is given a machine as any queued job is, of its own selector, so that another run's job that takes that machine instead is answered for itself, and admitted if it may run. The reasons are those above. What a job's own steps ask for, a work disk or its save, fails in that step instead, with the service's reason, such as a family that `.github/runners.json` doesn't declare or a file it lists that doesn't exist (specs/0005-interface.md).

**A runner's only label is its selector,** the one it was made for: the service registers it with that label alone, none of GitHub's default labels such as `self-hosted`, `linux` or the architecture's, and confirms from GitHub's record of the runner that it has no other, or else deletes the runner and its machine. So a job is given one of the service's runners only if its `runs-on` is exactly a selector: a job that also names other labels, or only generic ones such as `self-hosted`, never matches one, and never takes a machine meant for the consumer's jobs only to be refused at its check. The service cancels the run of a queued job that names one of its selectors together with any other label, and logs why. A machine's labels hold its selector.

## Network

Machines join the service's network, `lanescape-runners`, in its subnetwork of the same name. The network has no firewall rules: its implicit rules apply, so nothing reaches a machine, not another machine, not the project's other machines, not SSH from outside. Each still reaches out through its own external address. Deploying refuses a change that adds any rule.

## A machine's life

Every machine runs the **supervisor**, a small program of the service's own on the base image. It registers the machine's one-job GitHub runner, starts it, waits for it to exit, then sends the service its **report**: that the job is done. Then it powers the machine off. It runs outside every job, as its own user with its own environment, and acts only after the runner has exited, by which time GitHub has the job's result. That's why it, and not the runner's job-completed hook, ends a machine's life: that hook runs before the runner has reported the result, and inside the job's environment, which the job can change. Every machine boots the base image, so the supervisor, the runner and the job-started hook are always the service's own, as it built them: nothing in a consumer's repository changes the host a job starts on.

**The service's programs are in a directory of their own.** The supervisor, the job-started hook's program and the program that mounts the work disk are the service's own Go programs, statically linked as Go builds them, in `/opt/lanescape-runners`, owned by root; the job-started hook GitHub's runner calls is a script there that only runs the hook's program, and the units and rule that start the others name them there by their full paths. GitHub's runner is in a directory of its own too. The tools they run, such as `mkfs.ext4`, are Debian's, from the base image's packages, and are updated with each rebuild of the base image. Neither the directory nor static linking protects anything: the job-started check runs before any step, when nothing on the machine has been changed, and after the first step a job with root can change anything on its machine, `/opt` included. The boundaries that matter rest on what follows: the run is bound before the first step, work disks are confined to the bound scope, saves go only to that scope, and each machine serves one job. A job that sets its machine up after asking for its work disk, as the actions document, has its disk formatted and mounted before its setup changes any system package (Setting up a machine, below).

**Jobs have passwordless sudo,** as on GitHub's runners: the runner's user may run anything as root, so a job can set its machine up as it needs (Setting up a machine, below). That doesn't weaken the boundaries that matter:

- **Each machine serves one job.** The machine is the job's alone, for that job alone, and goes when it ends, so root on it reaches nothing but the job's own machine, its own work disk, and its machine's identity, which can ask the service only for what that job may have anyway (The machine's account, below). Nothing it changes outlives its job but its own work disk: its boot disk is never saved, and its work disk is saved only in its run's own scope, and only as GitHub's conclusion for the job allows (specs/0003-disks.md).
- **The run is bound before any step runs,** at its first job's job-started check, on a fresh machine, from what GitHub told the runner, as GitHub's records confirm (Binding a run, above). No step, as root or not, can choose or change its run's scope, nor bind another run. The one exception, an unbound `pull_request_target` run's job admitted on the smallest shape, gets nothing that needs a scope until its run is bound by its contribution job's check (Unbound runs, above).
- **Work disks are confined to the bound scope.** The service chooses what a work disk starts from and where it's saved from the run's binding alone, and attaches a disk only to the machine of the job that asked for it (The work disk, below), so root on one machine reaches no other scope's disk.

It does mean a job could change anything on its own machine, the supervisor and the hook included, and could send a report of its own. So the service decides nothing from what a machine says beyond what the job could ask for itself: the hook only asks, and the service answers from GitHub's records; the report says only that the job is done, and the service saves only on GitHub's conclusion for the job, in the scope of the job's run's binding. A job that kills its supervisor, or reports early, only ends its own machine's life sooner, or loses its own save.

1. A job is queued. Unless its run is from a fork's pull request that isn't an approved contribution, the service creates a machine for it, unless as many machines are already being made or idle for that consumer and selector as there are such jobs queued: `lsr-<repository ID>-<random>`, labelled with the repository ID, its selector and its creation time. Its account is `lanescape-runners-machine`, which has no role anywhere (below). Its boot disk is made from the base image. It has no work disk: `/work` is an empty directory of the base image's, owned by root, which the runner's user can't write (The work disk, below). The supervisor registers a just-in-time runner with that selector in the consumer's runner group, with the runner's own working directory on the boot disk, starts it, and waits for it.
2. GitHub hands the runner any queued job of that consumer whose labels it matches. It need not be the job the machine was made for, and that's as it should be: nothing on the machine belongs to any run yet. Before the job's first step, the runner's job-started hook asks the service whether the job may run here (below). If the service allows it, the hook returns, and the job runs. If the service refuses, it stops the machine itself at once, and the hook, which gets no answer it can use, never returns. Nothing scope-bound reaches a machine before its actual job is admitted: a work disk comes only from the `disk` action of an admitted job, so a refused job, or one whose hook was tampered with, finds only a machine about to stop. The service cancels the run of a job it refused for coming from a fork, and makes another machine for any job still queued. A job the service fails is answered with the reason instead, and the hook prints it and waits while the service cancels the run and stops the machine (Failing a job, above).
3. When the runner has finished its job and reported the result to GitHub, it exits, and the supervisor, not a hook, reports to the service, and powers the machine off. The report, not GitHub's word that the job finished, is what starts the machine's cleanup: GitHub can show the job finished a moment before the report arrives, and only the report says that the disk is no longer being written. A report normally arrives seconds after the job ends, and the service acts on it at once. The service records every report, and saves the work disk if GitHub's conclusion for the job is success, the job asked to save it (specs/0005-interface.md), and its scope saves (specs/0003-disks.md). A disk is saved from its stopped machine: if the supervisor hasn't powered it off yet, the service stops it itself. If a finished job's report never arrives, because its machine or supervisor died, the service waits 10 minutes, then goes on without saving. Then it saves the boot log to its bucket as `logs/<machine>-<created>.txt` and deletes the machine and its disks. Machines are made with serial console logging to Cloud Logging on, since Compute Engine serves a stopped machine's console only from there: the service reads the boot log from Cloud Logging by the instance's ID, once the supervisor's last line, written as it powers the machine off, has arrived, waiting up to 10 minutes for it, then saves what's there, or records the log as missing if nothing arrived, without holding up the machine's deletion. A record of each boot log still to be read, `bootlogs/<machine>-<created>.json`, written before the machine is deleted, is what a later pass follows, and shows that the machine was made.

The supervisor runs outside every job, as its own user, with its own environment and paths; nothing a job sets, such as `GITHUB_PATH`, `GITHUB_ENV` or files it leaves, reaches it. The job-started hook does run in the job's environment, before any step, so it decides nothing: what it asks, the service answers from GitHub's records, what it reports binds a run only on a fresh machine and only as GitHub's records confirm, and what it would enforce, the service enforces by stopping the machine.

**The job-started check.** The hook asks the service, with what GitHub told the runner about the job (Binding a run, above), signed with the machine's identity token: a Compute Engine token in the full format, whose audience is the service and whose project, zone and instance ID the service checks against the machine it made. The service asks GitHub which job is running on that machine's runner, by the job's `runner_id` and `runner_name`, never what the machine says, retrying for a short while until GitHub shows the assignment, and records the binding of job to machine. It allows the job only if:

- the job's repository is the machine's consumer, and its owner is the organization;
- its run isn't from a fork's pull request, unless it's an approved contribution (specs/0001-architecture.md);
- its labels are exactly one selector, the machine's, and nothing else;
- the run is bound, by this check if it wasn't (Binding a run, above), or it's an unbound `pull_request_target` run and the selector is the smallest shape, standard;
- the service has no reason to fail it (Failing a job, above).

A runner can be taken by a job of the same consumer that was never meant for it: a fork's pull request that names one of the service's selectors after a maintainer approved its run, or a job that asked only for generic labels, if GitHub ever gave a runner more than its selector. This check is what keeps that job's steps from running. GitHub runs a fork's pull request workflows only once a maintainer approves them, the organization's setting for every outside contributor, which the service checks at deploy and refuses to run without. When the service refuses a fork's job, it records the refusal and cancels the run, retrying until GitHub shows the run finished, and force-cancels it if an ordinary cancellation hasn't finished it within a few minutes. Until then it makes no further machine for that run's jobs. A first wave of the run's jobs may still each take a machine before the first refusal, each stopped at its own; that cost is a maintainer's approval of a fork's workflow gone wrong.

**The machine's account** exists only because Compute Engine issues identity tokens only to machines with an account. It has no role on any resource, so its access tokens reach nothing that isn't open to anyone signed in to Google, and no consumer may grant it one. A job that mints its machine's identity token can only ask about the job running on its own machine, which is itself, and ask for what that job may have: its work disk and its save.

| What a pass finds | What it does |
|---|---|
| The supervisor's report is recorded | Saves the work disk if the job succeeded, asked and its scope saves; saves the boot log; deletes the machine and its disks |
| GitHub shows the job finished, but no report has arrived after 10 minutes | Goes on without saving |
| A Spot machine was preempted, or might have been | Records it, makes a resume image of its work disk if it has one and its scope saves (below), then deletes the machine and its disks |
| The machine is past 90 minutes, its age limit | Deletes it, even mid-job, without saving anything; a Spot machine whose job was admitted is stopped, if it's still running, and recorded first (below), with no resume image, and waits for its record once it's stopped. Compute Engine itself stops every machine at 2 hours |
| The machine stopped before its job started | Deletes it; another is made while the job is still queued, up to an hour from the job's first machine, after which the service makes no more for it, cancels its run and logs why |
| The machine hasn't picked up a job after 20 minutes | Deletes it, with the same hour's limit |
| A disk attached to nothing, and not recorded as being made or waiting to be attached | Deletes it |
| An offline runner registration whose machine is gone | Removes it, if it's in one of the service's groups and named after one of its machines |

**The age limit.** A job on the service should take under 30 minutes, and 60 at worst; 90 minutes is the absolute maximum. Machines are for one job each, so the limit is per job, counted from the machine's creation. If standard machines are ever reused between jobs, the clock restarts when a machine takes a new job; Spot machines are never reused, since the chance of preemption grows with a machine's age. Compute Engine's own maximum run duration, which stops the machine, is the backstop for when the service can't act, set 30 minutes above the limit so that it never races the service's own path: a pass runs within 5 minutes of a machine reaching the limit, or waits up to 10 for a lease an earlier pass holds, and has up to 7 to stop and record a Spot machine. At the limit a job is lost, as the table says; whether it should instead resume, as from a preemption, is one constant's to change.

**One pool.** Every consumer's jobs, approved contributions' included, draw on one pool of machines, whose only ceiling is the project's Compute Engine quota. Machines go to queued jobs oldest first, by when GitHub queued them, across every consumer, so no consumer or run starves another. Hitting quota or a stockout is never a job's failure: a job whose machine can't be made in any zone or machine type of its shape stays queued, and later passes try again; meanwhile no younger job gets a machine that draws on a quota the older one could have drawn on: of its machine families, such as N4, whose machines share their quota, or, if the older job asked for Spot, of the Spot quota that every family's Spot machines share. Jobs that draw on other quotas go on. Approved contributions differ from other jobs only in what they must show to run (specs/0001-architecture.md, Forks and contributions), never in capacity or priority. What stops a runaway is the limit on every machine's age (above) and the cap of 3 attempts on automatic reruns (Preemption, below); spending as a whole is watched, not capped: the project's budget alert tells the maintainer, who acts on it. Quota errors, stockouts and the zone order are the service's to handle, not the job's.

Without per-consumer limits, nothing can deadlock. GitHub queues a job only once every job it needs has finished, so a running job never waits on a queued one, and a run's admitted jobs never hold machines its queued jobs are waiting for. Every machine is for one job and goes once that job ends, or after 20 minutes if no job takes it, and every job ends within the age limit, so a job held back by quota or capacity waits only on jobs that are certain to end. A job that waits on another job of the same run some other way, such as polling for it, is the consumer's to avoid, as it would be on any runner.

## The work disk

A job asks for a work disk in a step, with the `disk` action (lanescape/actions), naming a **family**: `POST /v1/disks`, signed with its machine's identity token (specs/0005-interface.md). The job chooses the family; the service chooses everything else, from its records and GitHub's, never from what the job says: the scope is the one it bound the job's run to, the key is the family's at the run's commit, and the disk is made from that scope's restore chain's saved disk for the family, a resume image of the job's, or empty (specs/0003-disks.md). The service answers only a machine of its own whose job it admitted, while that job runs, for a run that's bound and isn't an unbound `pull_request_target` run's; and refuses, with the reason, a family `.github/runners.json` at the run's commit doesn't declare, a file it lists that doesn't exist, or a file that isn't valid. The action's step fails with that reason, and the job's other steps go on as its workflow says: nothing was attached.

**One work disk per job.** A job's first request decides its family. A later request for the same family is answered about the same disk, so a retried step carries on; a request for another family is refused. Every work disk is recorded in the bucket, with its machine, its job, its family and whether it's being made, made or attached, before it's created; a retried request carries on with the disk already recorded, unless Compute Engine confirms that the image it was to start from has gone, when its record goes and the next request chooses again; and cleanup never deletes a recorded disk that's being made or waiting to be attached.

**Attaching it.** The service makes the disk, its size the shape's or its saved disk's if that's larger, with the shape's IOPS and throughput, and attaches it to the running machine, as the device named `work`, and answers `ready` once Compute Engine shows it attached. The base image mounts it at `/work` as soon as it appears, outside every job, by a rule of its own for that device name alone, which starts the service's mount program (A machine's life, above) in the machine's own mount namespace, where the runner and the job's steps run: on the empty directory `/work`, formatting it first if it's empty, and giving its root to the runner's user. A disk is never attached to a machine before its job is admitted and has asked. The action waits until `/work`, as its own step sees it, is the mounted disk.

**Who may write it.** The disk's root belongs to the runner's user, whose UID and GID on the base image are both 1001, as on GitHub's hosted runners. Steps run as that user, with passwordless sudo.

Until the disk is mounted, `/work` is the empty directory, owned by root, so a step that writes there before asking, as the runner's user, fails at once rather than write to the boot disk where the disk would hide it. A step that writes there as root writes to the boot disk, and the disk, once mounted, hides what it wrote; that's the job's own to avoid. The disk holds only what jobs put there: toolchains, source trees, build output, whatever is slow to make again. The runner's own working directory, where checkouts and the runner's files go, is on the boot disk, so tokens that tools store beside a checkout never reach `/work`. A job that handles long-lived secrets doesn't ask to save its disk. A job that doesn't ask has no work disk, and nothing of it is ever saved.

## Setting up a machine

A job sets its machine up in its own steps, from its own commit. What it needs beyond the base image (specs/0003-disks.md, Base images), such as system packages, compilers or Docker, it installs itself, with a step early in the job, after it checks out and after its `disk` step, if it has one, such as `run: sudo ./ci/init.sh`. So a run always uses its own commit's setup, as it uses its own commit's code, and a pull request that changes the setup uses the change in its own runs and nowhere else; what setting up costs shows in the job's log, as that step's duration; and there's nothing for the service to build, nothing for a job to wait for but its own step, and nothing to fall back to. What's slow to make again, such as toolchains and dependencies that files of the commit pin, belongs on the work disk, which later jobs restore (specs/0003-disks.md); what a job installs on the boot disk goes with its machine.

The service builds no images of consumers', and jobs run directly on the machine, not in containers: software that sandboxes itself with user namespaces can't make them under Docker's default security profile, and the service wants no special container settings to allow it. GitHub's runner starts a job's `container:` and `services:` with Docker before the job's first step, and the base image has no Docker, so a job on the service's machines names neither; a job that wants containers installs Docker in a step and runs them itself.

**Possible later work, not built: images.** If measured setup costs come to justify it, consumer images could return as a layer on the base image rather than as containers: built from a consumer's own setup script, on a builder with no credentials, saved as a Compute Engine disk image keyed by the base image's version and the definition, and attached by an `image` step as `disk` attaches the work disk, then overlaid on the machine's own filesystem. Labels would stay general, and jobs would still run directly on the machine. None of this is specified.

## Preemption

Only Spot machines are preempted. Preemption is learned from either of two sources, whichever comes first: Compute Engine's event, which the reconcile endpoint records in the bucket by instance ID before acknowledging it, and the zone operations of type `compute.instances.preempted`, whose `targetId` is the instance's numeric ID. Google keeps a finished operation for as little as an hour, so the recorded event is what survives an outage of the service.

Before a stopped Spot machine is deleted, the service records in the bucket, as `preemptions/<repository ID>/<run ID>/<instance ID>.json`, its instance ID, zone, the GitHub job ID and runner ID of the job that was on it, the job's name, its run and attempt, its selector, its work disk's family, if it had one, and whether it was preempted: `yes`, or `unknown` while there's no evidence. If it has a work disk and its scope saves disks, it makes a **resume image** of that disk (specs/0003-disks.md), then deletes the machine and its disks. Passes go on looking for evidence for each `unknown` record by its instance ID after the machine is gone, for a day. The reconcile endpoint records Compute Engine's event as `events/<instance ID>.json` before acknowledging it, whether or not a pass can run then; it reads only a `compute.instances.preempted` system event of one of the service's machines, in its project and zones, and ignores a guest's own shutdown. A resume image can resume a job for a day after its machine stopped, by Compute Engine's record of when it stopped, not when a pass saw it. That day is the limit on recovery, not a finding that the machine wasn't preempted: a run whose job was lost and never shown preempted isn't rerun. A resume image goes as soon as nothing can use it: once the job it resumes has started from it, or has finished, or once its run has finished with no rerun left (specs/0003-disks.md, Expiry).

**Reruns.** Once a run has finished, if any of its latest attempt's failed jobs was a Spot job shown preempted, the service asks GitHub to rerun the run's failed jobs, rather than each lost job and its dependents, for up to 3 attempts of the run in all, counted in the bucket: it records each attempt it reruns, in `reruns/<repository ID>/<run ID>.json`, before it asks, and asks only while GitHub shows fewer than 3 attempts and it has rerun fewer than 2. An answer lost after GitHub began the next attempt counts as a rerun; GitHub's attempt number is what keeps one attempt from being rerun twice. Whether an attempt is the service's own is GitHub's record of who triggered it, the App's bot user; only those attempts' jobs keep the run's restore choices (specs/0003-disks.md). The run is read again under the disks' lease before it's rerun, so a maintainer's rerun meanwhile isn't rerun on what the pass read before. A repository no longer the organization's is no consumer: nothing of it is rerun. That reruns jobs that failed for other reasons too, and anything that depends on them; it keeps one rerun per run attempt, where rerunning lost jobs one at a time would start a new attempt with each.

**Resuming.** A resume image belongs to its run and to the job's name. When a rerun's job asks for its work disk, the service gives it its resume image if one is eligible: made in an earlier attempt of the job's run, for the same family, on the same architecture, for the job's name, within a day of its machine stopping, and in both the attempt that was preempted and the one asking, exactly one job has that name, so a name a matrix shares with its siblings never resumes. Of several, the latest attempt's is the one. The service claims the image for the asking job's ID in the bucket, `claims/<repository ID>/<image>.json`, created only if absent, under the disks' lease (specs/0003-disks.md), and makes the work disk from it. Any other job, of the same run or another, never gets it. Images are global, so a rerun's machine can be in any zone. A resume image goes once its job has started from it: its work disk is made.

Either way the job runs the same steps: a step that finds its state in `/work` carries on from it, and one that doesn't starts as it would on a new disk. A preempted disk is in whatever state its machine left it mid-write, as after a power cut; a job that asks for Spot copes with that. In the `read` scope, nothing is saved, so a preempted job is rerun on a disk made as for any job.

## To confirm on real GitHub

These are what the design relies on that GitHub's documentation doesn't settle. Each is to be checked on real GitHub, with the real runner, at the first deploy, before any consumer relies on it:

- **A just-in-time runner gets no default labels,** only the selector it's registered with; otherwise the service deletes every runner it registers, and serves nothing until the registration is changed.
- **The hook sees `GITHUB_EVENT_PATH` and `GITHUB_REF_TYPE`** and the other default `GITHUB_*` variables, as GitHub's documentation says.

And on a real machine of each architecture, booted from the base image: that a disk the service's rule mounts at `/work` after the runner started is what the job's steps see there; and that a step, as the runner's user, can make an unprivileged user namespace (specs/0003-disks.md, Base images).
