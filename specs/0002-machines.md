# Machines

## Selectors

A job asks for one label, its **selector**: a shape, and optionally Spot.

```
lanescape-<vCPUs>vcpu-linux-<amd64|arm64>[-spot]
```

```yaml
runs-on: lanescape-2vcpu-linux-amd64
runs-on: lanescape-80vcpu-linux-amd64-spot
```

A selector names a machine and nothing else: no image, disk, scope or run. Machines are general: every machine of a selector is the same, booted from the service's base image (specs/0003-disks.md), and holds nothing of any run's until the service admits a job on it. So GitHub may give a job any machine of its selector, made for whichever of its consumer's jobs, and what the job then installs and works on, it sees to in its own steps: it sets the machine up from its own commit (Setting up a machine, below), asks for a work disk, which the `disk` action attaches (The work disk, below), and restores and saves its caches with the `cache` and `save-cache` actions (specs/0003-disks.md, Caches). What a job doesn't say, the service works out for itself from GitHub's records of the run, never from anything the job says: the run's scope (below) and the key of each cache its commit declares (specs/0003-disks.md).

**Shapes.** Each names the machine types that satisfy it, in order of preference, in `config/shapes.yaml`: at least that many vCPUs of that architecture, and the memory the shape promises. A shape says nothing of a work disk, which is its job's own request (The work disk, below). For example, `lanescape-80vcpu-linux-amd64` is `n4-highcpu-80`, then `c4-highcpu-96` when N4's quota or capacity is short; `lanescape-16vcpu-linux-amd64` is `n4-highcpu-16`, then `c4-highcpu-16`, with the memory of `lanescape-16vcpu-linux-arm64`, which is `c4a-highcpu-16`. The **smallest shape** is the first in `config/shapes.yaml`, `lanescape-2vcpu-linux-amd64`. Machines are made in zones `northamerica-northeast1-a`, then `-b`. Every machine boots the service's base image for its architecture (specs/0003-disks.md) on a boot disk of `boot_disk_gb`, 100 GB, which also holds the runner's working directory and whatever the job's setup installs, with 3,000 IOPS and 400 MiB/s, and gets a work disk only when its job asks for one, of the size and performance it asks for (below).

**Provisioning.** Machines are standard unless the selector says `-spot`. Spot is each job's own choice, made in its selector, never a class of job's. A Spot machine costs less and can be preempted at any time, so it suits a job that resumes from its work disk, picking up on a rerun where its preempted machine left off (below), or that is cheap to rerun. A long job that can't resume should be made resumable, rather than run on a standard machine because it can't. A standard machine is never preempted; Compute Engine migrates it live for host maintenance. A `-spot` selector's machine is standard only when no zone has Spot capacity or quota for any of its shape's machine types: it costs more, and the job runs as on any standard machine.

**Names.** A selector is in lowercase: labels compare without regard to case, as GitHub's do, so the service works with a selector in lowercase throughout. A label that starts with `lanescape-` but isn't a selector of a shape `config/shapes.yaml` offers gets no machine: the service cancels the run of a queued job that names one, and logs why.

**Scope** is where the run may read and save caches, and it's what keeps one run's caches from reaching another's jobs:

| Scope | The run | Reads | Saves |
|---|---|---|---|
| `main` | A push to the default branch | Main's | Main's |
| `branch-<name>` | A push to a long-lived branch the consumer lists | Its branch's, then main's | Its branch's |
| `pr<number>` | A pull request's run, the repository's own or an approved contribution | Its pull request's, then its base's: the listed branch's it targets, or else main's | Its pull request's |
| `read` | Anything else | Main's | Nothing |

What a scope reads and saves are its caches (specs/0003-disks.md). What it reads, in that order, is its **restore chain**: its own scope, if it saves, then its **base**, the scope it falls back to, if it has one. A pull request's base is the listed branch it targets, or else main's; a long-lived branch's push falls back to main's, so a new branch starts warm; `read` reads main's alone, as main does.

**Long-lived branches.** A consumer lists its long-lived branches, such as release branches, in its default branch's `.github/runners.json`, under `"branches"`, each with a name for its scope (specs/0005-interface.md): `{"support/v1": "v1"}` gives pushes to `support/v1` the scope `branch-v1`, which saves and reads as main's does for the default branch. A name is 1 to 16 lowercase letters and digits, starting with a letter. The service ignores an entry for the default branch, one whose name isn't valid, and every entry whose name another entry shares, and logs why. Listing a branch trusts everyone who can push to it, as main's scope trusts everyone who can push to the default branch, so a consumer lists only branches it protects as it does the default branch.

## Binding a run

The service never takes a run's scope from a job's steps or from a label. Each run is **bound** once, in the bucket, and every decision about the run's jobs that needs its scope uses that binding. The binding is created only if absent, so nothing later changes it.

**A run is bound by its first job's check.** Nothing in a workflow has to ask. Before a job's first step, its runner's job-started hook asks the service whether the job may run (A machine's life, below). Every machine boots the service's base image, and on a fresh one nothing but the service's own programs and GitHub's runner has run yet: the machine is new, it's for one job, and the job's steps haven't started. So what the hook sends along with its question is what GitHub told the runner about the job: its event's name, `GITHUB_REF`, `GITHUB_REF_TYPE` and `GITHUB_SHA`, and from the event's payload, `GITHUB_EVENT_PATH`, a pull request's number, head repository ID and head commit. If the job's run has no binding, the service binds it from those, after checking them against GitHub's own records of the run, which it reads with the App: the run is the one GitHub shows on that runner, its event and head commit are the run's, and each rule's conditions below hold. The service keeps the facts of a machine's first check, and a retried check from that machine, asking again after the service told it to wait, is decided from those kept facts, never new ones; once a machine's job is admitted, nothing from that machine binds anything again.

- **`main`** only for a `push` whose ref is `refs/heads/<default branch>`, with ref type `branch`, whose head commit is on the default branch, by GitHub's comparison of the two. A tag, or another branch named like the default branch, fails both.
- **`branch-<name>`** the same way, for a `push` whose ref is `refs/heads/<branch>`, for a branch listed with that name in the default branch's `.github/runners.json`, read with the App, and whose head commit is on that branch.
- **`pr<number>`** for a `pull_request` run, from its ref, `refs/pull/<number>/merge`, which names the pull request that triggered it; only if GitHub's record of the run lists that pull request among its own, when it lists any, and GitHub's pull request of that number targets this repository, has the run's head repository, which is this one, and has the run's head commit among its commits. So a run of one of two stacked pull requests can't claim the other, whose commits hold its head. A same-repository pull request's author controls its workflow, so nothing the workflow's steps say is used.
- **`pr<number>`** for an approved contribution's `pull_request_target` run, whose ref is the base branch's and names no pull request, from its event's pull request: only once GitHub records an approval of the `contribution` environment for the run, and only if the pull request of that number is open, targets this repository, and has the event's head repository, with the event's head commit among its commits. Until it's approved, the run is unbound (Unbound runs, below). An approved run whose pull request fails those conditions, such as one closed or force-pushed while its run waited for approval, is bound to `read`, and its jobs are failed, saying why (Failing a job, below), its contribution job included, so nothing waiting on that job runs.
- **`read`** for anything else, and for a pull request run whose head commit and repository are the head of more than one open pull request. That pull request run's jobs are failed, saying that each head commit must be the head of one open pull request (Failing a job, below), since nothing it built would persist.

A binding also records the run's **commit**, whose files decide its caches' keys: a push's head commit, a pull request run's head commit, the pull request's own, and a contribution's head commit, the event's. A binding of a pull request also records its base: the scope of the branch it targets, by GitHub's pull request when the run is bound, if that branch is listed, or else main's. A pull request retargeted later keeps its run's base; its next run binds afresh.

If GitHub can't be reached, or limits the service's requests, while a binding is being checked, no binding is made; the check answers the hook to wait and ask again, and only a confirmed answer binds a run.

**Unbound runs.** Until it's bound, a run's queued jobs get machines like any job's, and a job admitted on one gets nothing that needs a scope: neither the `disk` action nor the cache actions are answered for an unbound run (specs/0005-interface.md). A `pull_request_target` run is bound only once a maintainer has approved it, so a consumer that runs approved contributions gives such a run one **contribution job**, which names the environment `contribution`, so that GitHub holds it until a maintainer approves, which every other job of the run on the service's machines needs, and which runs only the default branch's code. Its check binds the run. Before that, a `pull_request_target` run's job is admitted only if its selector is the smallest shape, standard: a machine with nothing saved and no work disk. That's what its contribution job needs, and what a `pull_request_target` workflow that runs only the default branch's code needs, which GitHub runs for a contributor's pull request without anyone's approval. A job of an unbound `pull_request_target` run with any other selector is failed, saying why.

**Failing a job.** When the service knows a job can't run, it stops the job, saying why, rather than leave it queued or let any of its steps run. The reason is decided for the job, at its check, from GitHub's records and the job's run, never from the machine: whichever of its selector's machines the job lands on, the check answers the hook with the reason, which the hook prints in the job's log, and then the hook waits and never returns, while the service cancels the job's run and stops the machine. A hook that exited instead would fail the job but still let GitHub's runner run every step whose condition is `always()` or `failure()`; a hook that never returns, on a machine that stops, lets none of them run. So the job ends cancelled, with the reason in its log, and so does its run, which a workflow whose jobs the service can't serve couldn't finish anyway. A job the service will fail is given a machine as any queued job is, of its own selector, so that another run's job that takes that machine instead is answered for itself, and admitted if it may run. The reasons are those above. What a job's own steps ask for, a work disk or a cache, fails in that step instead, with the service's reason, such as a cache that `.github/runners.json` doesn't declare or a file it lists that doesn't exist (specs/0005-interface.md).

**A runner's only label is its selector,** the one it was made for: the service registers it with that label alone, none of GitHub's default labels such as `self-hosted`, `linux` or the architecture's, and confirms from GitHub's record of the runner that it has no other, or else deletes the runner and its machine. So a job is given one of the service's runners only if its `runs-on` is exactly a selector: a job that also names other labels, or only generic ones such as `self-hosted`, never matches one, and never takes a machine meant for the consumer's jobs only to be refused at its check. The service cancels the run of a queued job that names one of its selectors together with any other label, and logs why. A machine's labels hold its selector.

## Network

Machines join the service's network, `lanescape-runners`, in its subnetwork of the same name. The network has no firewall rules: its implicit rules apply, so nothing reaches a machine, not another machine, not the project's other machines, not SSH from outside. Each still reaches out through its own external address. Deploying refuses a change that adds any rule.

## A machine's life

Every machine runs the **supervisor**, a small program of the service's own on the base image. It registers the machine's one-job GitHub runner, starts it, measures the machine until the runner exits, then sends the service its **report**: that the job is done, and what the machine used (What a job used, below). Then it powers the machine off. It runs outside every job, as its own user with its own environment, and acts only after the runner has exited, by which time GitHub has the job's result. That's why it, and not the runner's job-completed hook, ends a machine's life: that hook runs before the runner has reported the result, and inside the job's environment, which the job can change. Every machine boots the base image, so the supervisor, the runner and the job-started hook are always the service's own, as it built them: nothing in a consumer's repository changes the host a job starts on.

**The service's programs are in a directory of their own.** The supervisor, the job-started hook's program and the program that mounts the work disk are the service's own Go programs, statically linked as Go builds them, in `/opt/lanescape-runners`, owned by root; the job-started hook GitHub's runner calls is a script there that only runs the hook's program, and the units and rule that start the others name them there by their full paths. GitHub's runner is in a directory of its own too. The tools they run, such as `mkfs.ext4`, are Debian's, from the base image's packages, and are updated with each rebuild of the base image. Neither the directory nor static linking protects anything: the job-started check runs before any step, when nothing on the machine has been changed, and after the first step a job with root can change anything on its machine, `/opt` included. The boundaries that matter rest on what follows: the run is bound before the first step, work disks are confined to the bound scope, saves go only to that scope, and each machine serves one job. A job that sets its machine up after asking for its work disk, as the actions document, has its disk formatted and mounted before its setup changes any system package (Setting up a machine, below).

**Jobs have passwordless sudo,** as on GitHub's runners: the runner's user may run anything as root, so a job can set its machine up as it needs (Setting up a machine, below). That doesn't weaken the boundaries that matter:

- **Each machine serves one job.** The machine is the job's alone, for that job alone, and goes when it ends, so root on it reaches nothing but the job's own machine, its own work disk, and its machine's identity, which can ask the service only for what that job may have anyway (The machine's account, below). Nothing it changes outlives its job but the caches it saves, and its work disk if the job is lost: its boot disk is never saved; a cache it saves is kept only in its run's own scope, and only if GitHub's conclusion for the job is success (specs/0003-disks.md, Caches); and its work disk outlives it only as a resume image of a lost job, which resumes only that job's rerun (Preemption, below).
- **The run is bound before any step runs,** at its first job's job-started check, on a fresh machine, from what GitHub told the runner, as GitHub's records confirm (Binding a run, above). No step, as root or not, can choose or change its run's scope, nor bind another run. The one exception, an unbound `pull_request_target` run's job admitted on the smallest shape, gets nothing that needs a scope until its run is bound by its contribution job's check (Unbound runs, above).
- **Caches and work disks are confined to the bound scope.** The service chooses what a cache restores and where it's saved from the run's binding alone, and hands a job tokens only for that version's objects (specs/0003-disks.md, Caches); it chooses what a work disk starts from from its own records alone, and attaches a disk only to the machine of the job that asked for it (The work disk, below), so root on one machine reaches no other scope's caches and no other job's disk.

It does mean a job could change anything on its own machine, the supervisor and the hook included, and could send a report of its own. So the service decides nothing from what a machine says beyond what the job could ask for itself: the hook only asks, and the service answers from GitHub's records; the report says that the job is done, and what the machine used, which the service only records and logs, and the service keeps a cache only on GitHub's conclusion for the job, in the scope of the job's run's binding. A job that kills its supervisor, or reports early, only ends its own machine's life sooner.

1. A job is queued. Unless its run is from a fork's pull request that isn't an approved contribution, the service creates a machine for it, unless as many machines are already being made or idle for that consumer and selector as there are such jobs queued: `lsr-<repository ID>-<random>`, labelled with the repository ID, its selector and its creation time. Its account is `lanescape-runners-machine`, which has no role anywhere (below). Its boot disk is made from the base image; while there's none its architecture's machines may boot, the job waits queued, and no machine is made or recorded for it (specs/0003-disks.md, Which image machines boot). It has no work disk: `/work` is an empty directory of the base image's, owned by root, which the runner's user can't write (The work disk, below). The supervisor registers a just-in-time runner with that selector in the consumer's runner group, with the runner's own working directory on the boot disk, starts it, and waits for it.
2. GitHub hands the runner any queued job of that consumer whose labels it matches. It need not be the job the machine was made for, and that's as it should be: nothing on the machine belongs to any run yet. Before the job's first step, the runner's job-started hook asks the service whether the job may run here (below). If the service allows it, the hook returns, and the job runs. If the service refuses, it stops the machine itself at once, and the hook, which gets no answer it can use, never returns. Nothing scope-bound reaches a machine before its actual job is admitted: a work disk comes only from the `disk` action of an admitted job, so a refused job, or one whose hook was tampered with, finds only a machine about to stop. The service cancels the run of a job it refused for coming from a fork, and makes another machine for any job still queued. A job the service fails is answered with the reason instead, and the hook prints it and waits while the service cancels the run and stops the machine (Failing a job, above).
3. When the runner has finished its job and reported the result to GitHub, it exits, and the supervisor, not a hook, reports to the service, and powers the machine off. The report, not GitHub's word that the job finished, is what starts the machine's cleanup: GitHub can show the job finished a moment before the report arrives, and the report says the machine is done. A report normally arrives seconds after the job ends, and the service acts on it at once. The service records every report, with what the machine used. It saves nothing from the machine: a job saves its caches in its own steps, and the service keeps them by GitHub's conclusion for the job, whether or not a report arrives (specs/0003-disks.md, Caches). If a finished job's report never arrives, because its machine or supervisor died, the service waits 10 minutes, then goes on. Then it saves the boot log to its bucket as `logs/<machine>-<created>.txt` and deletes the machine and its disks. Machines are made with serial console logging to Cloud Logging on, since Compute Engine serves a stopped machine's console only from there: the service reads the boot log from Cloud Logging by the instance's ID, once the supervisor's last line, written as it powers the machine off, has arrived, waiting up to 10 minutes for it, then saves what's there, or records the log as missing if nothing arrived, without holding up the machine's deletion. A record of each boot log still to be read, `bootlogs/<machine>-<created>.json`, written before the machine is deleted, is what a later pass follows, and shows that the machine was made.

The supervisor runs outside every job, as its own user, with its own environment and paths; nothing a job sets, such as `GITHUB_PATH`, `GITHUB_ENV` or files it leaves, reaches it. The job-started hook does run in the job's environment, before any step, so it decides nothing: what it asks, the service answers from GitHub's records, what it reports binds a run only on a fresh machine and only as GitHub's records confirm, and what it would enforce, the service enforces by stopping the machine. That environment can include the workflow's own `env`, and the hook's script runs in Bash, which runs what `BASH_ENV` names, or what `SHELLOPTS` and `PS4` make it, before the script's first line; so a workflow's code, a fork's included, can run before the hook's program does. Nothing depends on its not running: what reaches the check binds only as GitHub's records confirm, the machine's identity token asks only about its own job, and nothing scope-bound reaches the machine before its job is admitted.

**The job-started check.** The hook asks the service, with what GitHub told the runner about the job (Binding a run, above), signed with the machine's identity token: a Compute Engine token in the full format, whose audience is the service and whose project, zone and instance ID the service checks against the machine it made. The service asks GitHub which job is running on that machine's runner, by the job's `runner_id` and `runner_name`, never what the machine says, retrying for a short while until GitHub shows the assignment, and records the binding of job to machine. It allows the job only if:

- the job's repository is the machine's consumer, and its owner is the organization;
- its run isn't from a fork's pull request, unless it's an approved contribution (specs/0001-architecture.md);
- its labels are exactly one selector, the machine's, and nothing else;
- the run is bound, by this check if it wasn't (Binding a run, above), or it's an unbound `pull_request_target` run and the selector is the smallest shape, standard;
- the service has no reason to fail it (Failing a job, above).

The hook asks over HTTP/1.1 alone, offering nothing else in the TLS handshake, so that nothing in the job's environment can make its client trace the token, and asks again after any answer it can't use, saying in the job's log why, without the token or the service's address, each time the reason changes.

A runner can be taken by a job of the same consumer that was never meant for it: a fork's pull request that names one of the service's selectors after a maintainer approved its run, or a job that asked only for generic labels, if GitHub ever gave a runner more than its selector. This check is what keeps that job's steps from running. GitHub runs a fork's pull request workflows only once a maintainer approves them, the organization's setting for every outside contributor, which the service checks at deploy and refuses to run without. When the service refuses a fork's job, it records the refusal and cancels the run, retrying until GitHub shows the run finished, and force-cancels it if an ordinary cancellation hasn't finished it within a few minutes. Until then it makes no further machine for that run's jobs. A first wave of the run's jobs may still each take a machine before the first refusal, each stopped at its own; that cost is a maintainer's approval of a fork's workflow gone wrong.

**The machine's account** exists only because Compute Engine issues identity tokens only to machines with an account. It has no role on any resource, so its access tokens reach nothing that isn't open to anyone signed in to Google, and no consumer may grant it one. A job that mints its machine's identity token can only ask about the job running on its own machine, which is itself, and ask for what that job may have: its work disk and its caches.

**Retiring a machine.** A pass that deletes a machine whose job wasn't admitted because it stopped before its job started, hasn't picked up a job after 20 minutes, or boots an image of other programs, first records the machine's admission as retired, only if it has none, as the check records its decision: a check that decided first keeps the machine for its job, and one that comes later finds it refused. A queued job whose machine was retired gets another, or waits for a base image it may boot. GitHub hands a runner its job before the hook asks, so a runner can take a job between a pass's listing and its claim; that job's check, coming after the claim, is refused, and the job is lost. So before it deletes a machine it retired, a pass settles its runner. It removes the runner's registration, so that GitHub gives it no further job, and GitHub's answer says whether the runner had one. Removed, it had none, though the job the machine was made for, which its runner takes most often, is read by its ID all the same. Refused, `422`, while a job is assigned to it or running, it has one, which the pass looks for, as the check does, again for a while until GitHub shows it: the job the machine was made for, then the latest attempts of the repository's runs in progress. Gone already, `404`, it counts as removed, but it may have run a job that GitHub has since ended, removing the just-in-time runner after it, so the pass looks for one: the job the machine was made for, then the latest attempts of the repository's runs of every status, those in progress and the rest, finished or waiting on another of their jobs, updated since the machine was made, as a run was when the job it lost ended. What a pass learns of the runner, that it removed it, or that GitHub refused to as it had a job, is kept with the machine's records, in `machines/<machine>/runner.json`, so that a later pass that finds it gone knows: one this service removed had no job, and its machine goes; one gone otherwise had one, since GitHub removes a just-in-time runner once its job ends, unless someone else removed it, and its machine, as one whose runner GitHub refused to remove, waits for GitHub to show the job. The runs it reads, in progress or not, are those created since 35 days, the longest GitHub lets a run last, before the machine was made; GitHub lists at most 1,000 runs for one filter, so a span holding more is split, and one that can't be counts as GitHub not answering; the check reads the runs in progress so too. It reads all of this afresh for each machine, never from what it read before the runner's removal. A job of an earlier attempt than its run's latest is past rerunning, since its run has been rerun already. A job it finds is lost: if the check would have allowed it, by the same rules, as far as they need nothing the machine reports (a fork's pull request's job, one whose labels aren't the machine's selector alone, one its run's binding fails, or an unapproved contribution's on more than the smallest shape, isn't; an approved contribution's, whose run its check would have bound, is), it's recorded as lost, in `preemptions/<repository ID>/<run ID>/<instance ID>.json`, as a preempted job is (Preemption, below), with its run, attempt, name and selector and `retired`, and its run is rerun once it has finished (Reruns, below). A job is never given a work disk before it's admitted, so the job has none to resume from, and the record is done at once. While GitHub can't be read, or limits the service's requests, or shows no job of a runner that had one, or the record can't be written, the machine isn't deleted, even if its supervisor reports meanwhile, since its job was never admitted: a later pass tries again, until the machine's age limit, when it goes all the same, and the pass logs an error that a job it took may be lost. A revision a later deploy replaced settles runners too (specs/0004-deployment.md, Which revision makes machines): it still retires idle machines, and a job lost on one is as lost whichever revision retired it.

**The age limit.** A job on the service should take under 30 minutes, and 60 at worst; 90 minutes is the absolute maximum. Machines are for one job each, so the limit is per job, counted from the machine's creation. If standard machines are ever reused between jobs, the clock restarts when a machine takes a new job; Spot machines are never reused, since the chance of preemption grows with a machine's age.

At the limit a job isn't lost: it resumes, as from a preemption, on a standard machine as on a Spot one (Preemption, below). The service stops the machine, records the job as lost at the age limit, makes a resume image of its work disk if it has one and its scope saves, and deletes the machine; once the run has finished, it's rerun, and the rerun's job of the same name starts from the resume image. A job whose supervisor reported had finished on its own, since a stop leaves the supervisor no time to report, so nothing of it is recorded: its machine is only deleted. What it saved, it saved in its own steps, as caches, before it finished. Each pass stops every machine past the limit before it changes anything else, and so before it records any machine's job, asking for every stop at once: recording one and making its resume image can take longer than a pass, and neither that nor one slow stop must hold up another machine's stop. Before the pass decides whether a machine's job was cut short, it reads the machine's admission, report and work disk's record again, after its stop, since a check, a report or a disk request may have been recorded after the pass first read them; a machine with no admission is retired then, as an idle one is (the table above), so that a check that comes later finds it refused.

Compute Engine's own maximum run duration, which stops the machine and keeps its disks, is the backstop for when the service can't act, set 30 minutes above the limit so that it never races the service's own stop: a pass runs within 5 minutes of a machine reaching the limit, or waits up to 10 for a lease an earlier pass holds, and stops it first, within its 7. What follows the stop, the record and the resume image, takes as many passes as it needs, from a machine that's no longer running. A machine the backstop stopped is recorded as any machine at the limit is, once a pass can.

What bounds a job that never finishes is the cap of 3 attempts of a run (Reruns, below), not the job's `timeout-minutes`, which GitHub counts afresh in each attempt: such a job has at most 3 machines, of 90 minutes each, and its third attempt is lost at the limit for good.

**One pool.** Every consumer's jobs, approved contributions' included, draw on one pool of machines, whose only ceiling is the project's Compute Engine quota. Machines go to queued jobs oldest first, by when GitHub queued them, across every consumer, so no consumer or run starves another. Hitting quota or a stockout is never a job's failure: a job whose machine can't be made in any zone or machine type of its shape stays queued, and later passes try again, unless the job asks for more vCPUs than all of the quota: when every placement of its shape, in every zone and machine type, Spot or standard, fails for want of a machine family's vCPUs, `CPUS_PER_VM_FAMILY`, or of Spot's, `PREEMPTIBLE_CPUS`, whose whole limit, as Compute Engine's answer gives it, is less than the vCPUs of the machine type that placement tried, no machine's ending would let it fit, so the service cancels its run, as for a shape it doesn't offer, logging why, and it holds no younger job back. While a job waits, no younger job gets a machine that draws on a quota the older one could have drawn on: of its machine families, such as N4, whose machines share their quota, for a stockout or for want of a family's vCPUs, `CPUS_PER_VM_FAMILY`; if the older job asked for Spot, of the Spot quota that every family's Spot machines share, `PREEMPTIBLE_CPUS`; and for want of any other quota, which every machine draws on, whatever its family, such as `CPUS_ALL_REGIONS`, the project's vCPUs in every region, no younger job gets a machine at all. The service knows which quota each of the job's machine types and zones ran out of by its name in Compute Engine's answer, given at once or in the request's operation; a quota the answer doesn't name is taken to be one every machine draws on. Jobs that draw on other quotas go on. A quota every machine draws on holds no job back while none of the service's machines is running, since then nothing of the service's holds it, or the older job asks for more than all of it, and holding every job back would only stop them too; what the older job lacked of its families' quotas or capacity still holds their jobs back. Approved contributions differ from other jobs only in what they must show to run (specs/0001-architecture.md, Forks and contributions), never in capacity or priority. What stops a runaway is the limit on every machine's age (above) and the cap of 3 attempts on automatic reruns (Reruns, below); spending as a whole is watched, not capped: the project's budget alert tells the maintainer, who acts on it. Quota errors, stockouts and the zone order are the service's to handle, not the job's.

Without per-consumer limits, nothing can deadlock. GitHub queues a job only once every job it needs has finished, so a running job never waits on a queued one, and a run's admitted jobs never hold machines its queued jobs are waiting for. Every machine is for one job and goes once that job ends, or after 20 minutes if no job takes it, and every job ends within the age limit, so a job held back by quota or capacity waits only on jobs that are certain to end. A job that waits on another job of the same run some other way, such as polling for it, is the consumer's to avoid, as it would be on any runner.

## What a job used

While the runner runs, the supervisor measures the whole machine, which serves that one job, from the kernel's own counters, and sends the totals with its report:

- **CPU:** how many CPUs the machine has, and the CPU time, summed over all of them, spent running anything, idle waiting for I/O, and taken by the hypervisor, from `/proc/stat`.
- **Memory:** the machine's total, and the most in use at any sample, as `MemTotal` less `MemAvailable`, so that the page cache, which the kernel gives back when it's wanted, doesn't count; the most swap in use; and how many processes the kernel killed for want of memory, `oom_kill` in `/proc/vmstat`.
- **Disks:** the bytes read from and written to the machine's whole disks, from `/proc/diskstats`, a work disk attached during the job included; and for the boot disk's filesystem, and the work disk's once it's mounted at `/work`, its size and the most in use at any sample.
- **Pressure:** how long some, or all, of the machine's runnable work was stalled for want of CPU, memory or I/O, from the kernel's pressure stall information, when the kernel has it.
- When the runner started and exited, by the machine's clock, and how many samples were taken. Memory and filesystems are sampled every second.

It's the whole machine's, not the runner's unit's: a job's processes needn't stay in that unit, as Docker's containers don't, and a unit's memory counts its page cache, so its peak would say little about how near a job came to running out. It holds numbers alone, never a process, command line, path or anything else a job's steps name, so nothing a job runs can put a credential in it. Something the kernel doesn't offer, or a counter it couldn't read at the start, is left out, rather than given as a total since boot. Measuring never holds up the report: it runs on its own, and if it hasn't finished within 10 seconds of the runner's exit, as when a filesystem doesn't answer, the report goes without it.

It's measured on a machine whose job can change anything, the supervisor included, so the service decides nothing from it. It checks only that the usage is one a machine could have measured, with no number negative and the end not before the start, and records the report without it if not. It keeps the usage in the report, `machines/<machine>/report.json`, with what its log needs, read as the report is recorded, since the machine and its other records may be gone by the time it's logged: the machine's zone, machine type, whether it's Spot, its selector and repository ID, and, if its check admitted a job, the job's run ID, attempt, job ID and name. If the check's record can't be read then, the report isn't recorded, and the supervisor sends it again. A pass deletes a machine before its records, so a machine with no record of a check either had no job admitted, or is gone, and the report outlived it, its request having stalled while a pass cleaned up; the service looks for the machine again, and refuses a report that outlived it rather than record its usage without its job. The first report recorded is the record, and a later one changes nothing. The service logs it as `job usage`, from the report alone, when a pass drops the machine's records, after the machine is deleted, so every report recorded is logged, whether or not its sender heard back. A report a pass can't read is left for a later pass, which logs it and drops it once it can. A pass that logs it but can't drop the records logs it again, at the next; the machine, which serves one job, tells the entries apart. That log entry, in Cloud Logging with the service's others, is where to look; a moment in it matches a step by the step's times in GitHub's record of the job. The supervisor writes the same numbers to its own log too, so they're in the machine's boot log even if the report never arrives.

A service from before usage was reported refuses a report that has it, as a field it doesn't know, so the supervisor sends the report again without it: a report is never lost for its usage. While the deploy that brought usage moves over, a pass of the revision it replaced can drop a report without logging what it used; that report still counts as the job's end. A job whose machine was preempted, or stopped at its age limit, sends no report, so nothing of what it used is recorded.

## The work disk

A job asks for a work disk in a step, with the `disk` action (specs/0007-actions.md): `POST /v1/disks`, signed with its machine's identity token (specs/0005-interface.md), saying how large it is to be and its provisioned IOPS and throughput, or leaving any of them to the service's defaults in `config/shapes.yaml`: 50 GB, 3,000 IOPS and 400 MiB/s. The service chooses what it starts from, from its records and GitHub's, never from what the job says: a resume image of the job's, for the rerun of a job lost to a preemption or the age limit (Resuming, below), or nothing. What a job keeps from run to run it restores onto the disk and saves from it in its own steps, as caches (specs/0003-disks.md, Caches). The service answers only a machine of its own whose job it admitted, while that job runs: while the machine runs, its supervisor hasn't reported, and GitHub shows the job in progress, so a job GitHub shows completed gets nothing more even if its supervisor never reports; for a run that's bound and isn't an unbound `pull_request_target` run's. The action's step fails with that reason, and the job's other steps go on as its workflow says: nothing was attached.

**What a job may ask for.** A disk's size and performance cost only the job's own consumer, so they're the job's to say, whatever its shape, as its shape is, and nothing in the service tunes them to a kind of job. What Compute Engine allows is Compute Engine's to say, and the service keeps no table of it that could fall behind. Before making the disk, it asks Compute Engine for what it reports: the sizes the work disk's type, `hyperdisk-balanced`, may be, and the most the disks of the job's machine's own type may hold in all, its boot disk included; a request outside either is refused, saying so. Compute Engine reports no limits on provisioned IOPS and throughput through its API, so the service sends what the job asked for, and a disk Compute Engine refuses to make, such as one with more IOPS than its size allows, fails the request with Compute Engine's own message, as does every later request of the job, without asking it again. Each setting must be a positive whole number. A machine type's documentation also lists the most disk performance its machines can use, which Compute Engine doesn't enforce: a job that asks for more than its machine can use gets a disk that's no faster for it and pays for the rest.

**One work disk per job.** A later request is answered about the same disk, so a retried step carries on, and must ask for what the first did, with any setting it names: one that names another is refused. A disk recorded before jobs asked for their disks' settings was asked for with none, so a later request for it that names any is refused. Every work disk is recorded in the bucket, with its machine, its job, what the job asked for, where it came from and whether it's being made, made, attached or refused, before it's created; a retried request carries on with the disk already recorded, unless Compute Engine confirms that the image it was to start from has gone, when its record goes and the next request chooses again; and cleanup never deletes a recorded disk that's being made or waiting to be attached.

**Attaching it.** The service makes the disk, its size what the job asked for or its resume image's if that's larger, with the IOPS and throughput the job asked for, and attaches it to the running machine, as the device named `work`, and answers `ready` once Compute Engine shows it attached. The base image mounts it at `/work` as soon as it appears, outside every job, by a rule of its own for that device name alone, which starts the service's mount program (A machine's life, above) in the machine's own mount namespace, where the runner and the job's steps run: on the empty directory `/work`, formatting it first if it's empty, or else growing its filesystem to the whole disk, online, with Debian's `resize2fs`, since a disk made from a resume image at a larger size keeps the image's smaller filesystem until it's grown, and giving its root to the runner's user, all before it's mounted there: a filesystem that can't be grown is never mounted at `/work`, where its job would find less room than it asked for. A disk is never attached to a machine before its job is admitted and has asked. The action waits until `/work`, as its own step sees it, is the mounted disk.

**Who may write it.** The disk's root belongs to the runner's user, whose UID and GID on the base image are both 1001, as on GitHub's hosted runners. Steps run as that user, with passwordless sudo.

Until the disk is mounted, `/work` is the empty directory, owned by root, so a step that writes there before asking, as the runner's user, fails at once rather than write to the boot disk where the disk would hide it. A step that writes there as root writes to the boot disk, and the disk, once mounted, hides what it wrote; that's the job's own to avoid. The disk holds only what jobs put there: toolchains, source trees, build output, whatever is slow to make again. The runner's own working directory, where checkouts and the runner's files go, is on the boot disk, so tokens that tools store beside a checkout never reach `/work`. A job that handles long-lived secrets doesn't ask to save its disk. A job that doesn't ask has no work disk, and nothing of it is ever saved.

## Setting up a machine

A job sets its machine up in its own steps, from its own commit. What it needs beyond the base image (specs/0003-disks.md, Base images), such as system packages, compilers or Docker, it installs itself, with a step early in the job, after it checks out and after its `disk` step, if it has one, such as `run: sudo ./ci/init.sh`. So a run always uses its own commit's setup, as it uses its own commit's code, and a pull request that changes the setup uses the change in its own runs and nowhere else; what setting up costs shows in the job's log, as that step's duration; and there's nothing for the service to build, nothing for a job to wait for but its own step, and nothing to fall back to. What's slow to make again, such as toolchains and dependencies that files of the commit pin, belongs on the work disk, which later jobs restore (specs/0003-disks.md); what a job installs on the boot disk goes with its machine.

The service builds no images of consumers', and jobs run directly on the machine, not in containers: software that sandboxes itself with user namespaces can't make them under Docker's default security profile, and the service wants no special container settings to allow it. GitHub's runner starts a job's `container:` and `services:` with Docker before the job's first step, and the base image has no Docker, so a job on the service's machines names neither; a job that wants containers installs Docker in a step and runs them itself.

**Possible later work, not built: images.** If measured setup costs come to justify it, consumer images could return as a layer on the base image rather than as containers: built from a consumer's own setup script, on a builder with no credentials, saved as a Compute Engine disk image keyed by the base image's version and the definition, and attached by an `image` step as `disk` attaches the work disk, then overlaid on the machine's own filesystem. Labels would stay general, and jobs would still run directly on the machine. None of this is specified.

## Preemption

Only Spot machines are preempted. Preemption is learned from either of two sources, whichever comes first: Compute Engine's event, which the reconcile endpoint records in the bucket by instance ID before acknowledging it, and the zone operations of type `compute.instances.preempted`, whose `targetId` is the instance's numeric ID. Google keeps a finished operation for as little as an hour, so the recorded event is what survives an outage of the service.

Before a stopped Spot machine is deleted, the service records in the bucket, as `preemptions/<repository ID>/<run ID>/<instance ID>.json`, its instance ID, zone, the GitHub job ID and runner ID of the job that was on it, the job's name, its run and attempt, its selector, its architecture, and whether it was preempted: `yes`, or `unknown` while there's no evidence. If it has a work disk and its scope saves, it makes a **resume image** of that disk (specs/0003-disks.md, Resume images), then deletes the machine and its disks. A machine the service stopped at its age limit with its job unfinished (The age limit, above), Spot or standard, is recorded the same way, with its resume image made the same way, and the record also says `age_limit`; a standard machine's says `no` for whether it was preempted, since only Spot machines are. Passes go on looking for evidence for each `unknown` record that isn't at the age limit by its instance ID after the machine is gone, for a day. The reconcile endpoint records Compute Engine's event as `events/<instance ID>.json` before acknowledging it, whether or not a pass can run then; it reads only a `compute.instances.preempted` system event of one of the service's machines, in its project and zones, and ignores a guest's own shutdown. A resume image can resume a job for a day after its machine stopped, by Compute Engine's record of when it stopped, not when a pass saw it. That day is the limit on recovery, not a finding that the machine wasn't preempted: a run whose job was lost and never shown preempted isn't rerun. A resume image goes as soon as nothing can use it: once the job it resumes has started from it, or has finished, or once its run has finished with no rerun left (specs/0003-disks.md, Deletion).

**Reruns.** Once a run has finished, if any of its latest attempt's failed jobs was a Spot job shown preempted, a job lost at the age limit, or a job lost on a retired machine (Retiring a machine, above), the service asks GitHub to rerun the run's failed jobs, rather than each lost job and its dependents, for up to 3 attempts of the run in all, counted in the bucket: it records each attempt it reruns, in `reruns/<repository ID>/<run ID>.json`, before it asks, and asks only while GitHub shows fewer than 3 attempts and it has rerun fewer than 2. An answer lost after GitHub began the next attempt counts as a rerun; GitHub's attempt number is what keeps one attempt from being rerun twice. Whether an attempt is the service's own is GitHub's record of who triggered it, the App's bot user; only those attempts' jobs keep the run's restore choices (specs/0003-disks.md). The run is read again under the disks' lease before it's rerun, so a maintainer's rerun meanwhile isn't rerun on what the pass read before. A repository no longer the organization's is no consumer: nothing of it is rerun. Rerunning the failed jobs reruns every lost job of the attempt at once, so the run is rerun only once each is ready to resume: every failed job's record is done, which the record says as `done` once its resume image is ready or it gets none, and no machine of the run whose job was admitted is still unreported, such as one stopped whose record isn't written yet. Until then the run waits, still due its rerun, so that no rerun job asks for its work disk before the resume image it would start from is ready; a day after a machine stopped, when its image could no longer resume the job, the service stops trying to make the image, marks the record done without one, and deletes the machine, so it no longer holds the run back. That reruns jobs that failed for other reasons too, and anything that depends on them; it keeps one rerun per run attempt, where rerunning lost jobs one at a time would start a new attempt with each.

**Resuming.** A resume image belongs to its run and to the job's name. When a rerun's job asks for its work disk, the service gives it its resume image if one is eligible: made in an earlier attempt of the job's run, on the same architecture, for the job's name, within a day of its machine stopping, and in both the attempt that lost it and the one asking, exactly one job has that name, so a name a matrix shares with its siblings never resumes. Of several, the latest attempt's is the one. The service claims the image for the asking job's ID in the bucket, `claims/<repository ID>/<image>.json`, created only if absent, under the disks' lease (specs/0003-disks.md), and makes the work disk from it. Any other job, of the same run or another, never gets it. Images are global, so a rerun's machine can be in any zone. A resume image goes once its job has started from it: its work disk is made.

Either way the job runs the same steps: a step that finds its state in `/work` carries on from it, and one that doesn't starts as it would on a new disk. A preempted disk is in whatever state its machine left it mid-write, as after a power cut; a job that asks for Spot copes with that. A disk stopped at the age limit is in whatever state the machine's shutdown left it, its job's steps killed mid-step, so a job that might run that long copes with it the same way. In the `read` scope, nothing is saved, so a lost job is rerun on a disk made as for any job.

Saving is unchanged by either. A lost job saves nothing: no report follows its machine's stop, and GitHub's conclusion for it isn't success. Its rerun's job saves its caches in its own steps, as any job does, and they're kept, in its run's own scope, if it succeeds (specs/0003-disks.md); what it saves is whatever its steps made of the disk it resumed from, which is how a resumed job's work reaches its scope's caches, and the only way. A resume image itself is never a cache.

## To confirm on real GitHub

These are what the design relies on that GitHub's documentation doesn't settle. Each is to be checked on real GitHub, with the real runner, at the first deploy, before any consumer relies on it:

- **A just-in-time runner gets no default labels,** only the selector it's registered with; otherwise the service deletes every runner it registers, and serves nothing until the registration is changed.
- **The hook sees `GITHUB_EVENT_PATH` and `GITHUB_REF_TYPE`** and the other default `GITHUB_*` variables, as GitHub's documentation says; and whether it sees the workflow's own `env`, such as `BASH_ENV`, which the design doesn't rely on either way (A machine's life, above).
- **GitHub refuses to remove a runner with a job,** `422`, from the moment it assigns the job, not only once the runner has taken it, so that a removal it accepts leaves no job behind on a retired machine's runner; removes a just-in-time runner itself once its job has ended; and fails a job whose runner went, so that rerunning the run's failed jobs reruns it (Retiring a machine, above).

And on Compute Engine, for each architecture: that Debian's guest environment runs the builder's script as its startup script, with no account on the machine, and that its result line reaches the serial console the service reads (specs/0003-disks.md, Making a base image); and on a real machine booted from the base image: that its root filesystem fills its 100 GB boot disk, that nothing holds the package manager's lock when a job's first step runs, that a disk the service's rule mounts at `/work` after the runner started is what the job's steps see there, and that a step, as the runner's user, can make an unprivileged user namespace (specs/0003-disks.md, Base images).
