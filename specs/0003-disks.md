# Images and saved disks

Every machine boots the service's own base image. What a consumer's jobs need beyond it lives on their work disks, which a job can save when it finishes, so that later jobs start from it. A saved disk serves the run's scope and no other (specs/0002-machines.md): main's disks are saved only by pushes to the default branch, a long-lived branch's only by pushes to it, a pull request's only by its own runs, and nothing of a pull request's ever reaches main, a long-lived branch or another pull request. Runners outside the service start warm from the cache instead, which keeps the same scopes (specs/0006-cache.md).

## Base images

The service's own images, one per architecture, `lsr-base-<amd64|arm64>-<key>`: Ubuntu 26.04's current image; the GitHub runner at the version in `config/runner.yaml`, checked against its published SHA-256, which runs as the runner's user, `runner`, who has passwordless sudo, as on GitHub's runners (specs/0002-machines.md); the supervisor and the job-started hook; the directory `/var/lib/lanescape-runners`, which the runner's user may write (specs/0005-interface.md); and git, curl, jq, python3, zstd, pigz and Go at the version this repository's `go.mod` names. The key covers the Ubuntu image's name, the runner version, the Go version, the text of what installs them, and the digest of every program of the service's baked into the image, so a change to the supervisor or the hook alone makes a new image. When a deploy changes the key, the service makes the new one itself, on a builder machine that runs only the service's own script, and machines keep booting the previous one until it's ready. No consumer's code ever runs on a base image's builder, and no consumer can make or change a base image.

## Saved disks

A selector's `-disk-<family>-<key>` asks for a work disk made from a saved one. The service picks the first that exists of:

1. a disk saved in the first scope of the run's restore chain (specs/0002-machines.md, Scope) for that family and key;
2. the newest disk saved in that scope for that family, whatever its key;
3. if the chain has a second scope, its base, the same two in it;
4. none: the work disk starts empty.

For a pull request, that's its own disk for the key, its own newest, then its base's for the key and its base's newest; for main, main's for the key, then main's newest; for a long-lived branch's push, its own two, then main's two; for a `read` run, main's two.

Families are kept apart by architecture: a family's disks saved from `amd64` machines are never restored on `arm64` ones, or the other way round. The newest disk of a family is how a job whose key has changed, such as a pull request that moves a dependency, still starts from the state nearest to its own and rebuilds only what changed; a consumer's job must check what it restored and rebuild what's out of date, since a key miss restores older state. Every job of a run that uses the same selector starts from the same choice: the service picks once per run and selector, the first time it admits a job with it, and records the exact image version in the bucket, as `choices/<repository ID>/<run ID>/<selector hash>.json`, or that there was none, so the run's other jobs start empty too. **What each restore found** is recorded, so the order and what's kept can be tuned from evidence: the choice's record names the step of the order it came from, `pull_request_exact`, `pull_request_newest`, `main_exact`, `main_newest`, `branch_exact`, `branch_newest` or `none`, with its family, architecture and scope, and the service writes the same in a structured log line, `restore choice`. A pull request's choice is also recorded as its **most recent choice** for the family and architecture, `recent/<repository ID>/<scope>/<hash>.json`, which outlives its run's choice, until the pull request closes (Expiry, below). Picking and recording a choice, reading a recorded one, claiming a resume image, dropping a finished run's choices, asking for an automatic rerun, and marking an image for deletion, each happen under a short lease of their own in the bucket, `leases/disks/<repository ID>`, apart from the pass's, valid for a minute and held only for that step, which waits for it and finishes within 30 seconds, so no image is chosen as it's being marked, nor marked once chosen. A choice, each reading of it, and a claim also rewrite the image's record, and marking writes the record only at the generation it was read at when the decision to delete it was made, before the choices and claims were read, so a mark can't succeed past a choice or a use even if the lease were lost. A run's choices are dropped only once GitHub, read under the lease, still shows the run finished. A deletion that fails is asked for again under a new request ID. An image whose making was abandoned, an hour after a pass first found its machine gone, goes too. Which version of a series, or which disk of a main family, is newest is read only from the images Compute Engine has ready, never from a record of one that has gone. A repository transferred out of the organization gets no work disk from a retried check, saves nothing and gets no resume image. An image is made only once Compute Engine shows it ready: one still being made is waited for, and one that failed is deleted and made again, while its machine waits. An image is deleted only after it's marked, and an image marked for deletion is never chosen; one of the service's names with no record is recorded as marked, under the lease, unless a choice or claim names it, before it's deleted. A recorded choice whose image is gone, which only happens if someone else deleted it, is picked again. Labels on images and records hold hashes of selectors, families and job names wherever a value could be longer or freer than a Compute Engine label allows; the bucket holds the values themselves, in `images/<repository ID>/<image>.json`, written before the image is made.

A job asks to save its work disk, through the `save-disk` action (specs/0005-interface.md). When the job has finished, the service saves it only if:

- the job succeeded, by GitHub's conclusion for it;
- the run's scope saves: main's for a push to the default branch, a long-lived branch's for a push to it, a pull request's for that pull request's runs, never `read`;
- the job's selector names a family and key.

It makes an image of the stopped machine's work disk, `lsr-<repository ID>-<series>-<save time>-<machine>`: the series is the first 20 hex digits of the SHA-256 of the scope, the architecture, the family and the key, joined by NUL characters, so that each architecture's family is a series of its own; the save time is in Unix seconds; and the machine is the random part of the machine's name, since two jobs can save the same series in one second. It's labelled `lsr-kind` `saved`, with the repository ID, the architecture, and hashes of the scope, family and key, since Compute Engine labels are short and allow few characters, and with `lsr-saved` and `lsr-last-used` dates. Saving again for the same scope, architecture, family and key makes a new version, which later restore choices pick; what a new version replaces goes as Expiry says. Only the work disk is saved, as the job left it. The runner's directory, with its checkouts and any credentials tools left beside them, is on the boot disk, which is never saved.

**Resume images** are the same kind of image, made from a preempted Spot machine's work disk, `lsr-<repository ID>-resume-<instance ID>`, labelled `lsr-kind` `resume` with the run and hashes of the selector and the job's name, the full values being in the bucket's record of the preemption, and used only to resume that one job (specs/0002-machines.md). They're never a scope's saved disk, so a disk left mid-write by a preemption is never what a later run starts from.

## What reads what

Main's disks are read by main's pushes, by every pull request of the consumer into any branch but a listed long-lived one, approved contributions included, and by its `read` runs. A long-lived branch's are read by its pushes and the pull requests into it. A pull request's disks are read only by that pull request's later runs. A contributor's code can therefore change what its own pull request's later runs start from, and nothing else. A pull request's disk that main's code would want, such as a dependency it built for a new pin, is built again by main after the merge: that costs a second build, and in return main never starts from anything a pull request wrote.

## Expiry

Saved disks have no size limits. Instead, each goes as early as nothing needs it, by the rules below. Every rule still keeps an image version that an unfinished run's recorded restore choice names, or that a run still due an automatic rerun needs, and lets it go the moment that stops being true. Each goes by marking, under the disks' lease, then deletion (Saved disks, above).

- **Superseded versions.** Once a new version of a scope, architecture, family and key is ready, the older ones go.
- **A pull request keeps one disk of each family and architecture.** When it saves a family, its earlier disks of that family go, whatever their key. The restore order is unchanged. A family is one lineage: jobs that need several keys alive at once use separate families, or each replaces the others.
- **A closed pull request's scope goes at once,** merged or not. The service acts on GitHub's `pull_request` delivery with action `closed`, and each pass reads the pull request of every scope it holds disks of, or a most recent choice for, in case a delivery was lost. Its most recent choices go with it. The service records each pull request it sees closed, in `closures/<repository ID>/<scope>.json`, with the last time it saw it closed: from the `closed` delivery, recorded before it's acknowledged, as the second after GitHub's `closed_at`, and from every pass that still finds it closed. A disk saved by a run bound up to then is never chosen again, even once the pull request is reopened, replaces none of the pull request's other disks, and goes as soon as no unfinished run's choice names it. So a reopened pull request starts again from its base scope, even one reopened before any pass ran. A saved disk's record holds when its run was bound, for this. Every closure is written under the disks' lease, and only ever moves forward; whether a disk that replaces another is retired is read again under the lease before the other is marked, by a save or a pass, since a closing may be recorded meanwhile. A closure goes once its scope holds no disks, no cache entries and no most recent choices, and 35 days, GitHub's longest run, have passed. An open pull request's disks go 14 days after their last use, for one abandoned and never closed.
- **Main keeps the two newest keys of each family and architecture,** the newest and the one before it, by when their newest versions were saved, and any older key that an open pull request's most recent choice names. That's checked again in every pass, so whenever main saves, a pull request chooses or one closes. The previous key is kept for a pull request branched before main's dependencies moved that hasn't run since, and so has no choice recorded yet, and for main reverting a move: either would otherwise rebuild from nothing. A family of main's that nobody has used for 90 days goes, newest included: it's been retired. Its last use is recorded apart from its versions, in `families/<repository ID>/<hash>.json`, written under the lease before the version used is touched, so that deleting a version never makes the family look unused for longer than it has been, and read again under the lease before any of the family is marked, so that a use of one of its keys during a pass keeps all of them.
- **A long-lived branch's scope** keeps what main's does, for its own pushes and the pull requests into it, and goes at once when its branch is no longer listed in the default branch's `.github/runners.json`, or no longer exists.
- **Resume images** go once the job they resume has started from one, its work disk made, or has finished, or once their run has finished with no rerun left (specs/0002-machines.md, Preemption).

Starting a machine from a saved disk marks it used, at most once a day, in its record, which expiry reads, in the same write under the lease that the choice's use makes, and then in its `lsr-last-used` label. A new version counts as used when it's saved. A run's restore choices are dropped once it has finished and has no automatic rerun left; a later rerun of it, by a maintainer, picks again, as a new run would, even if its choices haven't been dropped yet: a choice records the attempt it was picked in, and holds only for the attempts after it that the service's own reruns started, by GitHub's record of who triggered each. A run with a machine whose job was admitted and that hasn't reported, such as a stopped Spot machine a pass hasn't yet recorded, counts as unfinished: it may be due a rerun that needs its choices.
