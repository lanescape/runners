# Base images, caches and resume images

Every machine boots the service's own base image, and a consumer's jobs set up the rest in their own steps (specs/0002-machines.md, Setting up a machine). What they need that's slow to make again they keep as **caches**: a job restores a cache, by name, onto its work disk in a step, and saves it in another, as archives it uploads itself to the service's caches' bucket, so that later jobs start from it. A cache serves the run's scope and no other (specs/0002-machines.md): main's caches are saved only by pushes to the default branch, a long-lived branch's only by pushes to it, a pull request's only by its own runs, and nothing of a pull request's ever reaches main, a long-lived branch or another pull request. A job's work disk itself is never kept: it starts empty, except for the rerun of a job lost to a preemption or the age limit, which starts from its **resume image** (below).

## Base images

The service's own images, one per architecture, `lsr-base-<amd64|arm64>-<key>`: Debian 13's image for that architecture, trixie, with its Linux 6.12 LTS kernel (specs/0004-deployment.md, Supported systems), from Google's `debian-cloud` project, as `config/base.yaml` names it, with Debian's updates as of the build; the GitHub runner at the version in `config/runner.yaml`, checked against its published SHA-256, in a directory of its own, `/opt/actions-runner`, which runs as the runner's user, `runner`, UID and GID 1001, who has passwordless sudo, as on GitHub's runners (specs/0002-machines.md), with the packages the runner's own `installdependencies.sh` installs; the service's own directory, `/opt/lanescape-runners`, with the supervisor, the job-started hook and the program that mounts a work disk at `/work`, and the rule that starts it for the device `work` (specs/0002-machines.md, A machine's life, The work disk); the empty directory `/work`, owned by root; Debian's e2fsprogs, whose `mkfs.ext4` and `resize2fs` the mount program runs; git, curl, jq, GitHub's CLI `gh`, zip, unzip, xz, python3, zstd and pigz, Debian's certificate authorities (`ca-certificates`), and `build-essential`: gcc, g++, make and the C library's headers, all from Debian; and Go, from Go's own release, at the version this repository's `go.mod` names, checked against the SHA-256 `config/base.yaml` gives for it, on `PATH` as `go` and `gofmt`. It has no Docker: a job that wants it installs it in a step (specs/0002-machines.md, Setting up a machine). Debian's timers that update packages by themselves, `apt-daily` and `apt-daily-upgrade`, are off, and so is `unattended-upgrades`, so that nothing holds the package manager's lock while a job's first step installs what it needs: a machine lives for one job, and its packages are those of its base image's build.

**Unprivileged user namespaces stay enabled,** as Debian enables them by default: the base image sets no sysctl and installs no security profile that restricts them, so software that sandboxes itself with user namespaces runs in a job's steps as the runner's user, without sudo. The builder checks it before it reports success (below).

**The key** is the first 20 hex digits of the SHA-256 of these parts, in this order, each written as its length in bytes, an unsigned 64-bit big-endian number, followed by its bytes, as families' keys are (Keys, below): the architecture; the Debian image's name; the runner's version and its SHA-256 for the architecture; Go's version and its SHA-256 for the architecture; the text of the builder's script, `machine/build-base.sh`; and the digest of the service's programs and the files the image installs with them, over each file's path and contents (`machine.Digest`). So a new Debian image, runner, Go, script, or change to the supervisor, the hook, the mount program or their units and rule alone makes a new image. `config/base.yaml` names each architecture's Debian image exactly, so the key, and so the image, changes only with a deploy: a pull request moves it to Debian 13's current image, as `gcloud compute images describe-from-family debian-13 --project=debian-cloud` and `debian-13-arm64` give it, as one moves the runner's version. It also gives Go's SHA-256 for each architecture, from Go's published checksums, for the version `go.mod`'s `toolchain` line names, which a test holds it to.

**Making a base image.** When a deploy changes the key, the service makes the new image itself, and no consumer's code ever runs on a base image's builder: no consumer can make or change a base image. Each pass, for each architecture whose image for the current key isn't ready, the service moves its build on:

1. With no builder, it first records the attempt in `bases/<arch>-<key>.json`, so that every builder counts towards the limit below, even one whose answer was lost, then makes one, `lsr-build-<amd64|arm64>-<key>`: a standard machine of the first of the architecture's builder machine types in `config/base.yaml`, then the next, in the shapes' zones in order (specs/0002-machines.md, Shapes), whichever has capacity, or takes the attempt back if none had any, and then holds queued jobs back for the rest of the pass (specs/0001-architecture.md, Passes), booted from the Debian image on a 10 GB boot disk of the shapes' disk type, in the service's subnetwork with an external address, with serial console logging to Cloud Logging on, so the maintainer can follow a build in the project's logs, and labelled `lsr-kind` `builder`, with its architecture and key. It has **no account at all**, so it has no identity and no credential of anyone's, never registers a runner, and is never given a job. Its metadata holds the builder's script as its `startup-script`, which Debian's guest environment runs as root once it has booted, and what the script installs: the architecture and key, the runner's version and SHA-256, Go's version and SHA-256, and, as `lsr-files`, in base64, a gzipped tar of the service's programs' sources and the files the image installs as they are, made from what's embedded in the service's binary (specs/0004-deployment.md, Code), which a test holds within a metadata value's 256 KiB. Compute Engine deletes a running builder at 90 minutes, its maximum run duration, if the service hasn't; a stopped one it no longer counts, and the service deletes it within the build's 2 hours (below).
2. The script, the service's own, installs everything above, from Debian's packages and from the runner's and Go's releases, each checked against its SHA-256, and builds the service's programs from their sources with that Go, statically. It makes the runner's user, UID and GID 1001, in no other group. Google's guest agent makes groups of its own as it starts, usually before the script runs, each only if no group of its name exists, with `groupadd`'s next GID from 1000, above the highest in use: `google-sudoers`, then those of the groups it puts the accounts it makes in that Debian's image lacks, `docker` and `lxd`, so `docker` holds GID 1001. A group holding GID 1001 that has no members, is no user's primary group and owns no file on the boot disk, as one just made at boot, moves to the highest free GID of the system groups' range, 101 to 999, as `groupadd --system` would have made it, and as Debian's Docker package makes its `docker` group when it's missing. It keeps its name, so at every boot of a machine made from the image the guest agent finds it and makes nothing, and leaves the runner's user alone. If the agent is still making its groups and takes GID 1001 again once it's freed, before `groupadd` looks for it, `groupadd` says the GID isn't unique, and the group that took it is looked at and moved in turn, up to 8 times, more than the 7 groups the agent makes by default; if after, since `groupadd` looks before it locks the group file, both hold GID 1001, and the agent's group is looked at and moved once `runner` is made, after which the agent finds GID 1001 taken. `useradd` looks for a taken UID only once it has locked the user file, so the runner's UID is never shared. Anything else holding UID or GID 1001 fails the build, naming it: a user, or a group with members, that's a user's primary group or that owns a file; so does a lookup in the account database that fails other than by finding nothing. Then it checks what it made: each tool is there, Go is the version asked for, each program is statically linked, the runner's user is UID and GID 1001, GID 1001 is the group `runner`'s alone, and the runner's user is in no other group and has passwordless sudo, `/work` is empty and owned by root, there's no Docker, and the runner's user can make an unprivileged user namespace. It clears what's of the builder alone, such as its machine ID and package caches, and writes its result to the serial console as one line: `lanescape-runners base image: built <arch>-<key>`, or `lanescape-runners base image: failed: <why>`. Then it waits; it never powers the machine off, since Compute Engine serves a running machine's console, and the service's own records say what happened.
3. The service reads the running builder's serial console. When it finds that it was built, it records that, for the builder's instance ID, in `bases/<arch>-<key>.json`, then stops the builder, and once Compute Engine shows it stopped, asks for the image from its boot disk, without waiting for it to be made, labelled `lsr-kind` `base` with its architecture, key and programs, `lsr-programs`, the first 20 hex digits of `machine.Digest` (Which image machines boot, below). Once a pass finds the image ready, it deletes the builder and the record.

A build fails if its builder says so, still hasn't said it was built when a pass reads its console 60 minutes or more after it was made, stops or goes before its success was recorded, or hasn't given a ready image within 2 hours of its attempt being counted, whatever has become of its builder by then; a success a pass finds is taken whenever it finds it, since a pass reads the console only when it runs, and Compute Engine deletes a builder still running at 90 minutes anyway; and an image that Compute Engine shows failed is deleted and made again from the stopped builder. When a build fails, the service saves the builder's console to its bucket as `logs/<builder>-<created>.txt`, while Compute Engine still serves it, a running builder's, since the service's own view of the serial consoles holds only job machines' (the project's logs keep it either way), logs why, records the failure, once for each builder, and deletes the builder; nothing waits on the console. The next pass tries again, with a new builder, up to 3 builders for a key in all. Each try at making a builder or an image, or deleting one, is a request of its own to Compute Engine, which never answers a later try from its memory of an earlier one, and the builder's and the image's names keep either from being made twice. After the third has failed, it makes no more for that key, and logs an error at every pass, until a deploy changes the key or the maintainer deletes the key's record, which lets it make up to 3 more. The error names the image machines of the architecture boot meanwhile, or says that there's none they may, so that no machine of it is made and its jobs wait queued (below).

While Cloud Run moves a deploy's traffic over, and for a while after, a revision of the service a deploy replaced can still run a pass, with its own key as the current one, so no pass undoes another key's build while it might still be going: a builder of a key that isn't the pass's is deleted only once it's 2 hours old, past any build's limit, and a record of one only once nothing has written it for a day.

**Which image machines boot.** A machine boots its architecture's image for the current key once it's ready. Until then, it boots the newest ready base image of its architecture made for an earlier key with the same programs as the service's own: one whose `lsr-programs` label is the first 20 hex digits of the service's `machine.Digest`. So a deploy that changes only Debian's image, the runner, Go or the builder's script keeps machines booting the previous image until the new one is ready. An image whose label names other programs, or that has none, is never booted in the current key's image's place: the supervisor, the job-started hook and the mount program on a machine decide whether its job can start and get its work disk, and a service a deploy replaced may have shipped ones that don't work with this one, so a job on such a machine could fail or hang, where waiting costs only the build. Every base image the service makes has the label, and when a pass finds the current key's ready image without it, as images made before they had it are, or with another, it labels it with the service's programs, which the key covers, keeping its other labels; no other image is given a label it lacks. With no image a machine may boot, the service makes no machine of that architecture: it registers no runner and records no machine for its jobs, which wait queued, as they do at the first deploy, and the wait doesn't count towards the hour a job's machines have to start from its first (specs/0002-machines.md, A machine's life): a job that already had a machine has on its record, `jobs/<repository ID>/<job ID>.json`, when it began to wait, and once it no longer does, how long it waited. Only the wait from when the record took it is left out of the hour: a wait the record couldn't take, as when the bucket refused the write, counts towards it once the job no longer waits. A job that waits is never refused for its hour meanwhile; and a job whose record can't be brought up to date, or whose wait isn't known, since the images couldn't be listed, is neither refused nor given a machine until a pass can bring it up to date, so it gets no machine its record would refuse. Meanwhile the one builder of the key goes on (Making a base image, above); a pass logs, for each such job, `a job waits for a base image its machine may boot`, with the image it waits for and the newest one it may not boot and why. From the first pass that finds the image ready, the jobs get their machines as any queued job does, quota and capacity allowing (specs/0002-machines.md, One pool). So a deploy that changes the service's programs, the supervisor, the hook, the mount program, or their units or rule, holds each architecture's queued jobs until its new image is ready. If every builder of the key fails, they wait until a deploy changes the key or the maintainer deletes the key's record, which the error logged at every pass says, or until GitHub ends them at its own limit on how long a job waits for a self-hosted runner, 24 hours. Jobs of the other architecture, whose image is ready, go on: a job that waits for its image holds back no other, though a builder that can't be made holds jobs back as it always does (Making a base image, above). A machine made before the deploy from an image of other programs, that no job was admitted on, is retired at the next pass, so that no job is admitted on it once the pass has claimed it, and a job its runner took just before is recorded as lost, so that its run is rerun (specs/0002-machines.md, Retiring a machine); a machine of an earlier image with the service's programs stays, and a revision the deploy replaced makes no machines or builders once the deploy's revision has run a pass (specs/0004-deployment.md, Which revision makes machines). Once the current key's image of an architecture is ready, every other base image of that architecture goes, once both it and the current one are more than a day old by Compute Engine's records of when they were made: so a deploy reverted while its earlier image is still there, as it is within a day of the later image's making, boots it again at once, and no pass of a service since replaced can still be running to make an image again of a key it alone wanted.

## Caches

A cache is a consumer's, named as its `.github/runners.json` declares it (Keys, below), and kept as **versions**: each version is what one job saved, in its run's scope, on its machine's architecture, with the cache's key for the run's commit. A version is a set of objects in the caches' bucket, `lanescape-runners-caches`, under `<repository ID>/<version>/`, which the job uploaded itself, and a record in the service's bucket, `caches/<repository ID>/<version>.json`, apart from images' records so that a revision of the service from before caches, still running passes while a deploy moves traffic over, never reads one as an image's and drops it, written before anything of it is uploaded, that names its scope, architecture, cache, key, run, attempt and job, and once it's committed, its objects. The version's name is `lsr-<repository ID>-<series>-<save time>-<machine>`: the series is the first 20 hex digits of the SHA-256 of the scope, the architecture, the cache and the key, joined by NUL characters, so that each architecture's cache is a series of its own; the save time is in Unix seconds; and the machine is the random part of the machine's name, since two jobs can save the same series in one second. What a version holds, and in what form, is the job's own: the service never reads its objects, and the actions (specs/0005-interface.md, Caches) keep a tree as tar archives compressed with zstd, which restore exactly what was saved.

**Restoring.** A job asks to restore a cache, through the `cache` action, `POST /v1/caches/restore` (specs/0005-interface.md), naming the cache: the job chooses the cache, never the scope or the key. A job can also only check where a restore would come from, through the `cache` action with `check-only`, `POST /v1/caches/check`: the service answers the run's choice, if it has one that still stands, `none` included, or else the step of the order below that a restore would pick now, and records nothing, not even the rewrite of a version's record that a restore's reading of a choice makes, so a job can learn, say, whether its run's scope or base has a version for the key before it decides to make one, without fixing the run's choice to an older version. The service picks the first that exists of:

1. a version saved in the first scope of the run's restore chain (specs/0002-machines.md, Scope) for that cache and key;
2. the newest version saved in that scope of that cache, whatever its key;
3. if the chain has a second scope, its base, the same two in it;
4. none: the job restores nothing.

For a pull request, that's its own version for the key, its own newest, then its base's for the key and its base's newest; for main, main's for the key, then main's newest; for a long-lived branch's push, its own two, then main's two; for a `read` run, main's two. The answer names the version's objects, as Cloud Storage held them when it was committed, each with its size, CRC32C and generation, and gives a token that may read those objects alone, for an hour; the caller reads each at its generation and checks its CRC32C, so that what it restores is what was committed.

Caches are kept apart by architecture: a cache saved on `amd64` machines is never restored on `arm64` ones, or the other way round. The newest version of a cache is how a job whose key has changed, such as a pull request that moves a dependency, still starts from the state nearest to its own and rebuilds only what changed; a consumer's job must check what it restored and rebuild what's out of date, since a key miss restores older state. Every job of a run that restores the same cache on the same architecture gets the same choice: the service picks once per run, cache and architecture, the first time one of its jobs asks, and records the exact version in the bucket, as `choices/<repository ID>/<run ID>/<hash>.json`, the hash being of the cache and architecture, or that there was none, so the run's other jobs restore nothing too. **What each restore found** is recorded, so the order and what's kept can be tuned from evidence: the choice's record names the step of the order it came from, `pull_request_exact`, `pull_request_newest`, `main_exact`, `main_newest`, `branch_exact`, `branch_newest` or `none`, with its cache, key, architecture and scope, and the service writes the same in a structured log line, `restore choice`. Picking and recording a choice, reading a recorded one, claiming a resume image, dropping a finished run's choices, asking for an automatic rerun, and marking a version or image for deletion, each happen under a short lease of their own in the bucket, `leases/disks/<repository ID>`, apart from the pass's, valid for a minute and held only for that step, which waits for it and finishes within 30 seconds, so no version is chosen as it's being marked, nor marked once chosen. A choice, each reading of it, and a claim also rewrite the version's or image's record, and marking writes the record only at the generation it was read at when the decision to delete it was made, before the choices and claims were read, so a mark can't succeed past a choice or a use even if the lease were lost. A run's choices are dropped only once GitHub, read under the lease, still shows the run finished. A version is chosen only once it's ready (Saving, below), and a version marked for deletion is never chosen. A recorded choice whose version is gone, which only happens if someone else deleted it, is picked again.

**Saving.** A job asks to save a cache, through the `save-cache` action, `POST /v1/caches/save`, naming it. In a scope that saves, main's for a push to the default branch, a long-lived branch's for a push to it, a pull request's for that pull request's runs, never `read`, the service records the one version the job saves of that cache, and answers where it goes, the caches' bucket and the version's prefix, with a token that may only create objects under that prefix, for an hour: it can't read, overwrite or delete anything, there or anywhere else. A repeat names the same version, with a fresh token, until the job commits it; a job saves a cache once. In a scope that saves nothing, the answer says so, and why. The job uploads the version's objects, then commits it, `POST /v1/caches/commit`: the service lists what's under the prefix and records each object's name, size, CRC32C and generation as the version's, and refuses a commit with nothing uploaded, or with more than a version holds: 1,000 objects, whose list, as the record holds it in JSON, takes no more than 512 KiB, so that every version's record, which every pass reads, stays small. A commit's record is what a restore reads: an object uploaded after it is no part of the version, and goes with it.

A committed version becomes **ready** only once its job has finished and GitHub's conclusion for it is success, which a pass reads (specs/0001-architecture.md, Passes): so a run's later jobs, and later runs, restore it from the first pass after its job ends, which comes within 5 minutes, or sooner on a webhook. A version whose job finished otherwise, failed, cancelled, or without committing it, is deleted, objects and record; so is one whose committed objects aren't all there, at the generations recorded, when it would become ready, which only happens if someone else deleted or replaced them: it replaces nothing. A pass checks every version's objects against its listing of the bucket, whatever any clock says, and confirms one that looks incomplete with a fresh listing of its prefix before anything goes, since the version may have been committed after the pass listed the bucket; if that listing fails, the version waits for a later pass. A version that goes is marked under the disks' lease, once GitHub, read again under it, still shows its repository as the organization's (Deletion, below). A version saved by a job whose repository GitHub no longer shows as the organization's waits, as everything of such a repository does (Deletion, below). Saving again for the same scope, architecture and cache makes a new version, which later restore choices pick, and which replaces what came before it (Deletion, below). Only what the job uploaded is kept. The runner's directory, with its checkouts and any credentials tools left beside them, is on the boot disk, which is never saved; a consumer saves what it chooses, and never anything a later run of another scope could read (What reads what, below).

**Tokens.** A token is an OAuth access token the service mints from its own credentials with a Credential Access Boundary, narrowed to the caches' bucket and to objects whose names start with the one version's prefix, with Cloud Storage's object viewer role for a restore and object creator for a save. Its lifetime is the service's own token's, at most an hour; a job that needs longer asks again. A token is a credential: the service never logs one, and the actions never log, print or hand one on.

**Resume images** are images the service makes of the work disk of a preempted Spot machine, or of a machine stopped at its age limit with its job unfinished, `lsr-<repository ID>-resume-<instance ID>`, labelled `lsr-kind` `resume` with the run and a hash of the job's name, the full values being in the bucket's record of the preemption, and used only to resume that one job (specs/0002-machines.md, Preemption): the rerun's job of the same name, on the same architecture, asks for its work disk and gets one made from it. A pass asks Compute Engine for the image and goes on, without waiting for it to be made, which can take minutes for a large disk, while the pass's lease holds up every queued job (specs/0001-architecture.md, Passes); the stopped machine waits, with its work disk, and the first pass that finds the image ready records it ready, and only then deletes the machine, and the job's run is rerun only once it is. A resume image is never a scope's cache, so a disk left mid-write by a preemption or a stop at the age limit is never what a later run starts from. Records of work disks and preemptions, and resume images' records and labels, still carry a family, always `work`, which nothing reads: a revision from before caches, cleaning up while a deploy moves traffic over, makes a lost job's resume image only for a record that names a family; the service matches a resume image without it. An image Compute Engine shows failed is deleted and made again, while its machine waits; a request whose image is gone, as when someone deleted one that was made, asks again under a new request ID.

## Keys

A cache's **key** says what its contents depend on, so that a run restores a version saved for the same dependencies, where its scope or base has one, before one saved for others. Keys don't keep versions apart: a save under any key replaces its scope's older versions of the cache (Deletion, below). The service makes it, for each run and cache, from the run's commit (specs/0002-machines.md, Binding a run), never from anything a job says. The consumer declares each cache its jobs restore or save in `.github/runners.json` at that commit, under `"caches"`, with `"from"`, the files its contents depend on, such as a list of dependency versions and a toolchain file:

```json
{"caches": {"build": {"from": ["deps/versions.json", "rust-toolchain.toml"]}}}
```

The key is the first 20 hex digits of the SHA-256 of these parts, in this order: the cache's name, then each listed path and its contents, in the order listed. Each part is written as its length in bytes, an unsigned 64-bit big-endian number, followed by its bytes: the name and paths in UTF-8, and contents exactly as the file's bytes at that commit. For example, cache `build`, `deps/versions.json` holding `café 1.0` and a newline, and an empty `rust-toolchain.toml`, give the key `be05417a720fa890bf52`. So the key changes when a listed file's contents do, and also when the name, the paths or their order do. A listed path is relative to the repository's root, with no leading or trailing slash, no `.`, `..` or empty segment and no backslash, and is listed once. A cache declared without `"from"`, as `{}`, has one key, `00000000000000000000`: a save makes a newer version of it, and later runs restore the newest, which is enough for a job that redoes only what's out of date. The service reads the file and the listed files with the App, at the run's commit, once per run, and records the keys it made, as `runs/<repository ID>/<run ID>/caches.json`. It adds each listed file to the key's hash as it reads it, before it reads the next, so it holds no more than one file's contents at a time, however many files a cache lists. For a cache the file doesn't declare, a listed file that doesn't exist, or a file that isn't valid, the service refuses the request to restore or save it, saying why, and the action's step fails with that reason. A cache's declaration also keeps its versions: main's while the default branch's file declares it, and a long-lived branch's while that branch's own file does (Deletion, below).

## What reads what

Main's caches are read by main's pushes, by every pull request of the consumer into any branch but a listed long-lived one, approved contributions included, and by its `read` runs. A long-lived branch's are read by its pushes and the pull requests into it. A pull request's caches are read only by that pull request's later runs. A contributor's code can therefore change what its own pull request's later runs start from, and nothing else. A pull request's cache that main's code would want, such as a dependency it built for a new pin, is built again by main after the merge: that costs a second build, and in return main never starts from anything a pull request wrote.

## Deletion

Caches are the consumer's to manage: a consumer makes a cache's versions by declaring the cache in `.github/runners.json` and saving, and deletes them by removing the declaration. Nothing goes for want of use or for its age, and there are no size limits. A version goes only by the rules below: a consumer's own act, a save replacing what came before it, or the end of the pull request or long-lived branch whose scope it's in, besides a version that never became ready (Caches, Saving, above); and none goes while GitHub doesn't show its repository as the organization's. Every rule still keeps a version that an unfinished run's recorded restore choice names, or that a run still due an automatic rerun needs, and lets it go the moment that stops being true. Each goes by marking, under the disks' lease, then deletion: its objects, then its record (Caches, above).

- **Removing a declaration deletes the cache.** Main's versions of a cache are kept while the default branch's `.github/runners.json` declares the cache, under `"caches"`. Once it doesn't, every version of the cache in main's scope goes, of every key and both architectures. A long-lived branch's scope is kept the same way, by that branch's own file. There's no grace period, and nothing keeps a cache for an open pull request whose commit still declares it: such a pull request's runs no longer find its base's versions of the cache, and a consumer relies on that, not on a version outliving its declaration. Each pass reads the files with the App, at the head of the default branch, and of each listed long-lived branch whose scope holds versions, for every consumer with versions in main's scope or a long-lived branch's. A file that's absent declares nothing. Deleting nothing is the safe failure: if GitHub can't be read, limits the service's requests, or gives any answer but the file or its absence, or if a branch's file isn't valid, the pass deletes nothing of that scope by this rule, and logs why; and a default branch's file that isn't valid confirms nothing, for main's scope or any long-lived branch's, so a mistake in it never deletes everything. A 404 for the file itself, in a repository GitHub still shows as the organization's when asked again, is the file's absence, which declares nothing; a 404 for the repository is not (below).
- **A save replaces what came before it,** in its scope and architecture. Once a new version of a cache is ready, the scope's older versions of that cache go, of the same key and every other key alike, so each scope keeps one version of each cache and architecture: its newest save. The maintainer decided this for caches with `"from"` keys: a newer key's save replaces the older keys' versions, since saving is the consumer's own act. A cache is one lineage: jobs that need several keys alive at once use separate caches, or each replaces the others. A pull request branched before its base saved a new key no longer finds its base's version of its own key, and restores its base's newest, as the restore order says, which is unchanged. Which version is newer is by when it was saved.
- **A long-lived branch's scope** goes at once when its branch is no longer listed in the default branch's `.github/runners.json`, or no longer exists.
- **A closed pull request's scope goes at once,** merged or not. The service acts on GitHub's `pull_request` delivery with action `closed`, and each pass reads the pull request of every scope it holds versions of, in case a delivery was lost. The service records each pull request it sees closed, in `closures/<repository ID>/<scope>.json`, with the last time it saw it closed: from the `closed` delivery, as the second after GitHub's `closed_at`, recorded by the webhook before it publishes the delivery and again by the reconcile endpoint before it acknowledges the push, and from every pass that still finds it closed. The webhook records it first because GitHub doesn't send again a delivery that failed: one that Pub/Sub refuses is still recorded, and one the webhook can't record within 5 seconds is still published, for its push to record. A version saved by a run bound up to then is never chosen again, even once the pull request is reopened, replaces none of the pull request's other versions, and goes as soon as no unfinished run's choice names it. So a reopened pull request starts again from its base scope, even one reopened before any pass ran. A version's record holds when its run was bound, for this. Every closure is written under the disks' lease, and only ever moves forward; whether a version that replaces another is retired is read again under the lease before the other is marked, by a pass, since a closing may be recorded meanwhile. **What can't be recovered:** a closing whose delivery the service never recorded, because its webhook couldn't be reached, or could neither record nor publish it, such as during an outage of Cloud Run or of the bucket, is seen only by a pass that finds the pull request still closed. One reopened before any pass ran looks to the service as if it had never closed, since GitHub's current record of it no longer shows the closing, and its later runs restore what its runs saved before. A maintainer who knows of such an outage can redeliver its failed `pull_request` deliveries from the App's settings, as GitHub allows for 3 days, and the webhook records them as it would have. A closure goes once its scope holds no versions and 35 days, GitHub's longest run, have passed. An open pull request's versions are kept until it closes, or its own later save replaces them: declarations don't keep or delete them, since its runs can only ask for the caches its own commit declares, and its scope goes with it.
- **A repository GitHub doesn't show as the organization's loses nothing.** None of a repository's versions or resume images goes by any rule here, or as orphaned, unless GitHub shows the repository as the organization's in that pass; if GitHub can't be read for it, the pass deletes none of them, and logs why; its versions being saved wait to be settled. If GitHub answers 404 for the repository itself, as it does for a deleted repository but also for one the App can no longer read, such as after a change to the App's installation, or shows it as another owner's, transferred, a pass deletes none of its versions or images, counts none of its pull requests as closed, and decides nothing of its runs, so it drops none of their restore choices or records, until GitHub shows the repository as the organization's again. A mistake in the App's access must never delete what consumers have saved. Since GitHub answers 404 for everything of a repository the App can't read, a 404 for one of its pull requests, runs, jobs, branches or files counts as that thing's absence only if GitHub, asked again, still shows the repository as the organization's; a pass that finds it doesn't, or can't read it then, deletes nothing more of the repository's and decides nothing more of its runs, even from what it read before. A pass also reads the repository again just before it marks any of its versions or images or drops any of its runs' restore choices, under the disks' lease, and before it drops any other record of its runs, once it has read them, and acts only if GitHub still shows it as the organization's; so does settling a ready version, under the lease, before it marks what it replaces, which a later pass deletes instead once GitHub shows the repository again. A transfer is treated the same way, since the service reads nothing of a repository that isn't the organization's, so has no declarations to go by, and a repository keeps its ID through a transfer, which can be undone. Only a version or image already marked for deletion, and a resume image whose making was abandoned, which never became a disk, still go. Each pass logs a warning, `a repository with records isn't the organization's by GitHub's answer`, with the repository's ID and why: GitHub's 404, or another owner. A maintainer who has confirmed that the repository is deleted, or won't come back, removes its versions' objects and its resume images by hand, the images by the `lsr-repository` label every one of them has, then the records of its versions and its runs that are left:

  ```sh
  gcloud storage rm --recursive "gs://lanescape-runners-caches/<repository ID>/"
  gcloud compute images list --project=lanescape-dev --no-standard-images \
    --filter='labels.lsr-repository=<repository ID>' --format='value(name)' |
    xargs -r gcloud compute images delete --project=lanescape-dev --quiet
  for prefix in caches images claims choices closures preemptions reruns savings; do
    gcloud storage rm --recursive "gs://lanescape-runners/$prefix/<repository ID>/"
  done
  ```

  Until those records are gone, each pass goes on reading the repository, and warning.
- **Objects no version's record describes go,** once GitHub shows their repository as the organization's: a version's record is written before anything of it is uploaded, and a pass lists the caches' bucket before it reads the records, so nothing being saved is among them. A ready version whose objects are gone, which only happens if someone else deleted them, restores nothing, and its record goes.
- **Saved disks' images,** from before caches replaced saved disks, go, with their records, under the same rules of marking and of repositories GitHub doesn't show as the organization's: nothing chooses them any more.
- **Resume images** go once the job they resume has started from one, its work disk made, or has finished, or once their run has finished with no rerun left (specs/0002-machines.md, Preemption). They're the service's own, never a consumer's cache.

A run's restore choices are dropped once it has finished and has no automatic rerun left; a later rerun of it, by a maintainer, picks again, as a new run would, even if its choices haven't been dropped yet: a choice records the attempt it was picked in, and holds only for the attempts after it that the service's own reruns started, by GitHub's record of who triggered each. A run with a machine whose job was admitted and that hasn't reported, such as a stopped Spot machine, or one stopped at its age limit, that a pass hasn't yet recorded, counts as unfinished: it may be due a rerun that needs its choices.
