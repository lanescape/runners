# Images and saved disks

Every machine boots the service's own base image. What a consumer's jobs need beyond it lives on their work disks, which a job can save when it finishes, so that later jobs start from it. A saved disk serves the run's scope and no other (specs/0002-machines.md): main's disks are saved only by pushes to the default branch, a pull request's only by its own runs, and nothing of a pull request's ever reaches main or another pull request.

## Base images

The service's own images, one per architecture, `lsr-base-<amd64|arm64>-<key>`: Ubuntu 26.04's current image; the GitHub runner at the version in `config/runner.yaml`, checked against its published SHA-256, which runs as the runner's user, `runner`, who has passwordless sudo, as on GitHub's runners (specs/0002-machines.md); the supervisor and the job-started hook; the directory `/var/lib/lanescape-runners`, which the runner's user may write (specs/0005-interface.md); the proxy's local forwarder (specs/0006-proxy.md); and git, curl, jq, python3, zstd, pigz and Go at the version this repository's `go.mod` names. The key covers the Ubuntu image's name, the runner version, the Go version, the text of what installs them, and the digest of every program of the service's baked into the image, so a change to the supervisor, the hook or the forwarder alone makes a new image. When a deploy changes the key, the service makes the new one itself, on a builder machine that runs only the service's own script, and machines keep booting the previous one until it's ready. No consumer's code ever runs on a base image's builder, and no consumer can make or change a base image.

## Saved disks

A selector's `-disk-<family>-<key>` asks for a work disk made from a saved one. The service picks the first that exists of:

1. in a pull request's scope only, a disk saved in that pull request's scope for that family and key;
2. in a pull request's scope only, the newest disk saved in that pull request's scope for that family, whatever its key;
3. a disk saved in main's scope for that family and key;
4. the newest disk saved in main's scope for that family;
5. none: the work disk starts empty.

Families are kept apart by architecture: a family's disks saved from `amd64` machines are never restored on `arm64` ones, or the other way round. The newest disk of a family is how a job whose key has changed, such as a pull request that moves a dependency, still starts from the state nearest to its own and rebuilds only what changed; a consumer's job must check what it restored and rebuild what's out of date, since a key miss restores older state. Every job of a run that uses the same selector starts from the same choice: the service picks once per run and selector, the first time it admits a job with it, and records the exact image version in the bucket, as `choices/<repository ID>/<run ID>/<selector hash>.json`, or that there was none, so the run's other jobs start empty too. Picking and recording a choice, reading a recorded one, claiming a resume image, dropping a finished run's choices, and marking an image for deletion, each happen under a short lease of their own in the bucket, `leases/disks/<repository ID>`, apart from the pass's, valid for a minute and held only for that step, which waits for it and finishes within 30 seconds, so no image is chosen as it's being marked, nor marked once chosen. A choice, each reading of it, and a claim also rewrite the image's record, and marking writes the record only at the generation it was read at when the decision to delete it was made, before the choices and claims were read, so a mark can't succeed past a choice or a use even if the lease were lost. A run's choices are dropped only once GitHub, read under the lease, still shows the run finished. A deletion that fails is asked for again under a new request ID. An image whose making was abandoned, an hour after a pass first found its machine gone, goes too. Which version of a series, or which disk of a main family, is newest is read only from the images Compute Engine has ready, never from a record of one that has gone. A repository transferred out of the organization gets no work disk from a retried check, saves nothing and gets no resume image. An image is made only once Compute Engine shows it ready: one still being made is waited for, and one that failed is deleted and made again, while its machine waits. An image is deleted only after it's marked, and an image marked for deletion is never chosen. A recorded choice whose image is gone, which only happens if someone else deleted it, is picked again. Labels on images and records hold hashes of selectors, families and job names wherever a value could be longer or freer than a Compute Engine label allows; the bucket holds the values themselves, in `images/<repository ID>/<image>.json`, written before the image is made.

A job asks to save its work disk, through the `save` action (specs/0005-interface.md). When the job has finished, the service saves it only if:

- the job succeeded, by GitHub's conclusion for it;
- the run's scope saves: main's for a push to the default branch, a pull request's for that pull request's runs, never `read`;
- the job's selector names a family and key.

It makes an image of the stopped machine's work disk, `lsr-<repository ID>-<series>-<save time>-<machine>`: the series is the first 20 hex digits of the SHA-256 of the scope, the architecture, the family and the key, joined by NUL characters, so that each architecture's family is a series of its own; the save time is in Unix seconds; and the machine is the random part of the machine's name, since two jobs can save the same series in one second. It's labelled `lsr-kind` `saved`, with the repository ID, the architecture, and hashes of the scope, family and key, since Compute Engine labels are short and allow few characters, and with `lsr-saved` and `lsr-last-used` dates. Saving again for the same scope, architecture, family and key makes a new version, which later restore choices pick. An older version is deleted once the new one is ready and no unfinished run's recorded restore choice names it. Only the work disk is saved, as the job left it. The runner's directory, with its checkouts and any credentials tools left beside them, is on the boot disk, which is never saved.

**Resume images** are the same kind of image, made from a preempted Spot machine's work disk, `lsr-<repository ID>-resume-<instance ID>`, labelled `lsr-kind` `resume` with the run and hashes of the selector and the job's name, the full values being in the bucket's record of the preemption, and used only to resume that one job (specs/0002-machines.md). They're never a scope's saved disk, so a disk left mid-write by a preemption is never what a later run starts from.

## What reads what

Main's disks are read by every pull request of the consumer, approved contributions included, and by its `read` runs. A pull request's disks are read only by that pull request's later runs. A contributor's code can therefore change what its own pull request's later runs start from, and nothing else. A pull request's disk that main's code would want, such as a dependency it built for a new pin, is built again by main after the merge: that costs a second build, and in return main never starts from anything a pull request wrote.

## Expiry and limits

Starting a machine from a saved disk marks it used, at most once a day, in its record, which expiry reads, and its `lsr-last-used` label. A new version counts as used when it's saved. A pull request's disks are deleted 14 days after their last use, or once the pull request has been closed for a day. Main's are deleted 90 days after their last use, except the newest of each family. Resume images go as specs/0002-machines.md says. No deletion of any kind removes an image version that an unfinished run's recorded restore choice names, or that a run still due an automatic rerun needs. A run's restore choices are dropped once it has finished and has no automatic rerun left; a later rerun of it, by a maintainer, picks again, as a new run would, even if its choices haven't been dropped yet: a choice records the attempt it was picked in, and holds only for the attempts the service's own reruns started from it.

Each consumer has two limits on the total size of its saved disks, in `config/limits.yaml`: one for main's and one for all its pull requests' together, counting each disk at the size of the disk it was made from, and counting one marked for deletion until Compute Engine confirms it's deleted, but not a record of a ready image that Compute Engine confirms is gone. A save that would pass its scope's limit first deletes that scope's least recently used disks, never another scope's: a pull request's save deletes only that pull request's disks, though the limit counts all of them. It never deletes the newest of a main family, other than the one the save replaces as newest, nor a version an unfinished run's restore choice names; the saving job's own run has often just finished with its choice still recorded, so a choice of a run that GitHub shows finished, with no automatic rerun due, is dropped first, under the lease, and its image may go. A run with a machine other than the saving one whose job was admitted and that hasn't reported, such as a stopped Spot machine a pass hasn't yet recorded, counts as unfinished: it may be due a rerun that needs its choices. If that isn't enough, nothing is deleted, the save is skipped, and the service's log says why, with the job's ID: the job has ended by then, so its own log can't. So a pull request can never push main's disks out, nor another pull request's.
