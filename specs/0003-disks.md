# Base images and saved disks

Every machine boots the service's own base image, and a consumer's jobs set up the rest in their own steps (specs/0002-machines.md, Setting up a machine). What they need that's slow to make again lives on their work disks, which a job asks for in a step, by family, and can save when it finishes, so that later jobs start from it. A saved disk serves the run's scope and no other (specs/0002-machines.md): main's disks are saved only by pushes to the default branch, a long-lived branch's only by pushes to it, a pull request's only by its own runs, and nothing of a pull request's ever reaches main, a long-lived branch or another pull request.

## Base images

The service's own images, one per architecture, `lsr-base-<amd64|arm64>-<key>`: Debian 13's image for that architecture, from Google's `debian-cloud` project, as `config/base.yaml` names it, with Debian's updates as of the build; the GitHub runner at the version in `config/runner.yaml`, checked against its published SHA-256, in a directory of its own, `/opt/actions-runner`, which runs as the runner's user, `runner`, UID and GID 1001, who has passwordless sudo, as on GitHub's runners (specs/0002-machines.md), with the packages the runner's own `installdependencies.sh` installs; the service's own directory, `/opt/lanescape-runners`, with the supervisor, the job-started hook and the program that mounts a work disk at `/work`, and the rule that starts it for the device `work` (specs/0002-machines.md, A machine's life, The work disk); the empty directory `/work`, owned by root; Debian's e2fsprogs, whose `mkfs.ext4` the mount program runs; git, curl, jq, python3, zstd and pigz, from Debian; and Go, from Go's own release, at the version this repository's `go.mod` names, checked against the SHA-256 `config/base.yaml` gives for it, on `PATH` as `go` and `gofmt`. It has no Docker: a job that wants it installs it in a step (specs/0002-machines.md, Setting up a machine). Debian's timers that update packages by themselves, `apt-daily` and `apt-daily-upgrade`, are off, and so is `unattended-upgrades`, so that nothing holds the package manager's lock while a job's first step installs what it needs: a machine lives for one job, and its packages are those of its base image's build.

**Unprivileged user namespaces stay enabled,** as Debian enables them by default: the base image sets no sysctl and installs no security profile that restricts them, so software that sandboxes itself with user namespaces runs in a job's steps as the runner's user, without sudo. The builder checks it before it reports success (below).

**The key** is the first 20 hex digits of the SHA-256 of these parts, in this order, each written as its length in bytes, an unsigned 64-bit big-endian number, followed by its bytes, as families' keys are (Keys, below): the architecture; the Debian image's name; the runner's version and its SHA-256 for the architecture; Go's version and its SHA-256 for the architecture; the text of the builder's script, `machine/build-base.sh`; and the digest of the service's programs and the files the image installs with them, over each file's path and contents (`machine.Digest`). So a new Debian image, runner, Go, script, or change to the supervisor, the hook, the mount program or their units and rule alone makes a new image. `config/base.yaml` names each architecture's Debian image exactly, so the key, and so the image, changes only with a deploy: a pull request moves it to Debian 13's current image, as `gcloud compute images describe-from-family debian-13 --project=debian-cloud` and `debian-13-arm64` give it, as one moves the runner's version. It also gives Go's SHA-256 for each architecture, from Go's published checksums, for the version `go.mod`'s `toolchain` line names, which a test holds it to.

**Making a base image.** When a deploy changes the key, the service makes the new image itself, and no consumer's code ever runs on a base image's builder: no consumer can make or change a base image. Each pass, for each architecture whose image for the current key isn't ready, the service moves its build on:

1. With no builder, it first records the attempt in `bases/<arch>-<key>.json`, so that every builder counts towards the limit below, even one whose answer was lost, then makes one, `lsr-build-<amd64|arm64>-<key>`: a standard machine of the first of the architecture's builder machine types in `config/base.yaml`, then the next, in the shapes' zones in order (specs/0002-machines.md, Shapes), whichever has capacity, or takes the attempt back if none had any, and then holds queued jobs back for the rest of the pass (specs/0001-architecture.md, Passes), booted from the Debian image on a 10 GB boot disk of the shapes' disk type, in the service's subnetwork with an external address, with serial console logging to Cloud Logging on, so the maintainer can follow a build in the project's logs, and labelled `lsr-kind` `builder`, with its architecture and key. It has **no account at all**, so it has no identity and no credential of anyone's, never registers a runner, and is never given a job. Its metadata holds the builder's script as its `startup-script`, which Debian's guest environment runs as root once it has booted, and what the script installs: the architecture and key, the runner's version and SHA-256, Go's version and SHA-256, and, as `lsr-files`, in base64, a gzipped tar of the service's programs' sources and the files the image installs as they are, made from what's embedded in the service's binary (specs/0004-deployment.md, Code), which a test holds within a metadata value's 256 KiB. Compute Engine deletes a running builder at 90 minutes, its maximum run duration, if the service hasn't; a stopped one it no longer counts, and the service deletes it within the build's 2 hours (below).
2. The script, the service's own, installs everything above, from Debian's packages and from the runner's and Go's releases, each checked against its SHA-256, and builds the service's programs from their sources with that Go, statically. Then it checks what it made: each tool is there, Go is the version asked for, each program is statically linked, the runner's user is UID and GID 1001 with passwordless sudo, `/work` is empty and owned by root, there's no Docker, and the runner's user can make an unprivileged user namespace. It clears what's of the builder alone, such as its machine ID and package caches, and writes its result to the serial console as one line: `lanescape-runners base image: built <arch>-<key>`, or `lanescape-runners base image: failed: <why>`. Then it waits; it never powers the machine off, since Compute Engine serves a running machine's console, and the service's own records say what happened.
3. The service reads the running builder's serial console. When it finds that it was built, it records that, for the builder's instance ID, in `bases/<arch>-<key>.json`, then stops the builder, and once Compute Engine shows it stopped, makes the image from its boot disk, labelled `lsr-kind` `base` with its architecture and key. Once the image is ready, it deletes the builder and the record.

A build fails if its builder says so, still hasn't said it was built when a pass reads its console 60 minutes or more after it was made, stops or goes before its success was recorded, or hasn't given a ready image within 2 hours of its attempt being counted, whatever has become of its builder by then; a success a pass finds is taken whenever it finds it, since a pass reads the console only when it runs, and Compute Engine deletes a builder still running at 90 minutes anyway; and an image that Compute Engine shows failed is deleted and made again from the stopped builder. When a build fails, the service saves the builder's console to its bucket as `logs/<builder>-<created>.txt`, while Compute Engine still serves it, a running builder's, since the service's own view of the serial consoles holds only job machines' (the project's logs keep it either way), logs why, records the failure, once for each builder, and deletes the builder; nothing waits on the console. The next pass tries again, with a new builder, up to 3 builders for a key in all. Each try at making a builder or an image, or deleting one, is a request of its own to Compute Engine, which never answers a later try from its memory of an earlier one, and the builder's and the image's names keep either from being made twice. After the third has failed, it makes no more for that key, and logs an error at every pass, until a deploy changes the key or the maintainer deletes the key's record.

While Cloud Run moves a deploy's traffic over, and for a while after, a revision of the service a deploy replaced can still run a pass, with its own key as the current one, so no pass undoes another key's build while it might still be going: a builder of a key that isn't the pass's is deleted only once it's 2 hours old, past any build's limit, and a record of one only once nothing has written it for a day.

**Which image machines boot.** A machine boots its architecture's image for the current key once it's ready; until then, the newest ready base image of its architecture, made for an earlier key, so machines keep booting the previous image until the new one is ready. With none, the service makes no machine of that architecture, and its jobs wait queued for it, as they do at the first deploy. Once the current key's image of an architecture is ready, every other base image of that architecture goes, once both it and the current one are more than a day old by Compute Engine's records of when they were made: so a deploy reverted while its earlier image is still there, as it is within a day of the later image's making, boots it again at once, and no pass of a service since replaced can still be running to make an image again of a key it alone wanted.

## Saved disks

A job's `disk` action asks for a work disk of a family (specs/0002-machines.md, The work disk), made from a saved one of that family, with the family's key for the run (Keys, below), in the scope the service bound the job's run to: the job chooses the family, never the scope. The service picks the first that exists of:

1. a disk saved in the first scope of the run's restore chain (specs/0002-machines.md, Scope) for that family and key;
2. the newest disk saved in that scope for that family, whatever its key;
3. if the chain has a second scope, its base, the same two in it;
4. none: the work disk starts empty.

For a pull request, that's its own disk for the key, its own newest, then its base's for the key and its base's newest; for main, main's for the key, then main's newest; for a long-lived branch's push, its own two, then main's two; for a `read` run, main's two.

Families are kept apart by architecture: a family's disks saved from `amd64` machines are never restored on `arm64` ones, or the other way round. The newest disk of a family is how a job whose key has changed, such as a pull request that moves a dependency, still starts from the state nearest to its own and rebuilds only what changed; a consumer's job must check what it restored and rebuild what's out of date, since a key miss restores older state. Every job of a run that asks for the same family on the same architecture starts from the same choice: the service picks once per run, family and architecture, the first time one of its jobs asks, and records the exact image version in the bucket, as `choices/<repository ID>/<run ID>/<hash>.json`, the hash being of the family and architecture, or that there was none, so the run's other jobs start empty too. **What each restore found** is recorded, so the order and what's kept can be tuned from evidence: the choice's record names the step of the order it came from, `pull_request_exact`, `pull_request_newest`, `main_exact`, `main_newest`, `branch_exact`, `branch_newest` or `none`, with its family, architecture and scope, and the service writes the same in a structured log line, `restore choice`. A pull request's choice is also recorded as its **most recent choice** for the family and architecture, `recent/<repository ID>/<scope>/<hash>.json`, which outlives its run's choice, until the pull request closes (Expiry, below). Picking and recording a choice, reading a recorded one, claiming a resume image, dropping a finished run's choices, asking for an automatic rerun, and marking an image for deletion, each happen under a short lease of their own in the bucket, `leases/disks/<repository ID>`, apart from the pass's, valid for a minute and held only for that step, which waits for it and finishes within 30 seconds, so no image is chosen as it's being marked, nor marked once chosen. A choice, each reading of it, and a claim also rewrite the image's record, and marking writes the record only at the generation it was read at when the decision to delete it was made, before the choices and claims were read, so a mark can't succeed past a choice or a use even if the lease were lost. A run's choices are dropped only once GitHub, read under the lease, still shows the run finished. A deletion that fails is asked for again under a new request ID. An image whose making was abandoned, an hour after a pass first found its machine gone, goes too. Which version of a series, or which disk of a main family, is newest is read only from the images Compute Engine has ready, never from a record of one that has gone. A repository transferred out of the organization gets no work disk from a retried request, saves nothing and gets no resume image. An image is made only once Compute Engine shows it ready: one still being made is waited for, and one that failed is deleted and made again, while its machine waits. An image is deleted only after it's marked, and an image marked for deletion is never chosen; one of the service's names with no record is recorded as marked, under the lease, unless a choice or claim names it, before it's deleted. A recorded choice whose image is gone, which only happens if someone else deleted it, is picked again. Labels on images and records hold hashes of families and job names wherever a value could be longer or freer than a Compute Engine label allows; the bucket holds the values themselves, in `images/<repository ID>/<image>.json`, written before the image is made.

A job asks to save its work disk, through the `save-disk` action, which asks the service, `POST /v1/disks/save` (specs/0005-interface.md). When the job has finished, the service saves it only if:

- the job succeeded, by GitHub's conclusion for it;
- the run's scope saves: main's for a push to the default branch, a long-lived branch's for a push to it, a pull request's for that pull request's runs, never `read`;
- the job has a work disk, which its `disk` action asked for, of a family.

It makes an image of the stopped machine's work disk, `lsr-<repository ID>-<series>-<save time>-<machine>`: the series is the first 20 hex digits of the SHA-256 of the scope, the architecture, the family and the key, joined by NUL characters, so that each architecture's family is a series of its own; the save time is in Unix seconds; and the machine is the random part of the machine's name, since two jobs can save the same series in one second. It's labelled `lsr-kind` `saved`, with the repository ID, the architecture, and hashes of the scope, family and key, since Compute Engine labels are short and allow few characters, and with `lsr-saved` and `lsr-last-used` dates. Saving again for the same scope, architecture, family and key makes a new version, which later restore choices pick; what a new version replaces goes as Expiry says. Only the work disk is saved, as the job left it. The runner's directory, with its checkouts and any credentials tools left beside them, is on the boot disk, which is never saved.

**Resume images** are the same kind of image, made from the work disk of a preempted Spot machine, or of a machine stopped at its age limit with its job unfinished, `lsr-<repository ID>-resume-<instance ID>`, labelled `lsr-kind` `resume` with the run and hashes of the family and the job's name, the full values being in the bucket's record of the preemption, and used only to resume that one job (specs/0002-machines.md, Preemption). They're never a scope's saved disk, so a disk left mid-write by a preemption or a stop at the age limit is never what a later run starts from.

## Keys

A family's **key** says what its disk's contents depend on, so that a run whose dependencies moved saves beside the disk it restored rather than over it. The service makes it, for each run and family, from the run's commit (specs/0002-machines.md, Binding a run), never from anything a job says. The consumer declares each family its jobs' `disk` actions name in `.github/runners.json` at that commit, under `"disks"`, with `"from"`, the files its contents depend on, such as a list of dependency versions and a toolchain file:

```json
{"disks": {"build": {"from": ["deps/versions.json", "rust-toolchain.toml"]}}}
```

The key is the first 20 hex digits of the SHA-256 of these parts, in this order: the family, then each listed path and its contents, in the order listed. Each part is written as its length in bytes, an unsigned 64-bit big-endian number, followed by its bytes: the family and paths in UTF-8, and contents exactly as the file's bytes at that commit. For example, family `build`, `deps/versions.json` holding `café 1.0` and a newline, and an empty `rust-toolchain.toml`, give the key `be05417a720fa890bf52`. So the key changes when a listed file's contents do, and also when the family, the paths or their order do. A listed path is relative to the repository's root, with no leading or trailing slash, no `.`, `..` or empty segment and no backslash, and is listed once. A family declared without `"from"`, as `{}`, has one key, `00000000000000000000`: a save makes a newer version of that disk, and later runs restore the newest, which is enough for a job that redoes only what's out of date. The service reads the file and the listed files with the App, at the run's commit, once per run, and records the keys it made with the run's choices. For a family the file doesn't declare, a listed file that doesn't exist, or a file that isn't valid, the service refuses the `disk` action's request, saying why, and the action's step fails with that reason (specs/0002-machines.md, The work disk).

## What reads what

Main's disks are read by main's pushes, by every pull request of the consumer into any branch but a listed long-lived one, approved contributions included, and by its `read` runs. A long-lived branch's are read by its pushes and the pull requests into it. A pull request's disks are read only by that pull request's later runs. A contributor's code can therefore change what its own pull request's later runs start from, and nothing else. A pull request's disk that main's code would want, such as a dependency it built for a new pin, is built again by main after the merge: that costs a second build, and in return main never starts from anything a pull request wrote.

## Expiry

Saved disks have no size limits. Instead, each goes as early as nothing needs it, by the rules below. Every rule still keeps an image version that an unfinished run's recorded restore choice names, or that a run still due an automatic rerun needs, and lets it go the moment that stops being true. Each goes by marking, under the disks' lease, then deletion (Saved disks, above).

- **Superseded versions.** Once a new version of a scope, architecture, family and key is ready, the older ones go.
- **A pull request keeps one disk of each family and architecture.** When it saves a family, its earlier disks of that family go, whatever their key. The restore order is unchanged. A family is one lineage: jobs that need several keys alive at once use separate families, or each replaces the others.
- **A closed pull request's scope goes at once,** merged or not. The service acts on GitHub's `pull_request` delivery with action `closed`, and each pass reads the pull request of every scope it holds disks of, or a most recent choice for, in case a delivery was lost. Its most recent choices go with it. The service records each pull request it sees closed, in `closures/<repository ID>/<scope>.json`, with the last time it saw it closed: from the `closed` delivery, recorded before it's acknowledged, as the second after GitHub's `closed_at`, and from every pass that still finds it closed. A disk saved by a run bound up to then is never chosen again, even once the pull request is reopened, replaces none of the pull request's other disks, and goes as soon as no unfinished run's choice names it. So a reopened pull request starts again from its base scope, even one reopened before any pass ran. A saved disk's record holds when its run was bound, for this. Every closure is written under the disks' lease, and only ever moves forward; whether a disk that replaces another is retired is read again under the lease before the other is marked, by a save or a pass, since a closing may be recorded meanwhile. A closure goes once its scope holds no disks and no most recent choices, and 35 days, GitHub's longest run, have passed. An open pull request's disks go 14 days after their last use, for one abandoned and never closed.
- **Main keeps the two newest keys of each family and architecture,** the newest and the one before it, by when their newest versions were saved, and any older key that an open pull request's most recent choice names. That's checked again in every pass, so whenever main saves, a pull request chooses or one closes. The previous key is kept for a pull request branched before main's dependencies moved that hasn't run since, and so has no choice recorded yet, and for main reverting a move: either would otherwise rebuild from nothing. A family of main's that nobody has used for 90 days goes, newest included: it's been retired. Its last use is recorded apart from its versions, in `families/<repository ID>/<hash>.json`, written under the lease before the version used is touched, so that deleting a version never makes the family look unused for longer than it has been, and read again under the lease before any of the family is marked, so that a use of one of its keys during a pass keeps all of them.
- **A long-lived branch's scope** keeps what main's does, for its own pushes and the pull requests into it, and goes at once when its branch is no longer listed in the default branch's `.github/runners.json`, or no longer exists.
- **Resume images** go once the job they resume has started from one, its work disk made, or has finished, or once their run has finished with no rerun left (specs/0002-machines.md, Preemption).

Starting a machine from a saved disk marks it used, at most once a day, in its record, which expiry reads, in the same write under the lease that the choice's use makes, and then in its `lsr-last-used` label. A new version counts as used when it's saved. A run's restore choices are dropped once it has finished and has no automatic rerun left; a later rerun of it, by a maintainer, picks again, as a new run would, even if its choices haven't been dropped yet: a choice records the attempt it was picked in, and holds only for the attempts after it that the service's own reruns started, by GitHub's record of who triggered each. A run with a machine whose job was admitted and that hasn't reported, such as a stopped Spot machine, or one stopped at its age limit, that a pass hasn't yet recorded, counts as unfinished: it may be due a rerun that needs its choices.
