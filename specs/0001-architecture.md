# Architecture

Lanescape Runners is a GitHub Actions runner service for the repositories of the `lanescape` GitHub organization, and for no one else, on Google Cloud. A job asks for a machine by label, as it would ask GitHub or any other runner provider, naming only its shape: `runs-on: lanescape-80vcpu-linux-amd64`. The service creates a Compute Engine machine for that job, booted from the service's own base image, registers a one-job runner on it, and deletes it afterwards. Machines are general: a job can run in a container of an image the consumer defines in its own repository, which the service builds and stores (specs/0006-images.md), and can ask in a step for a work disk, which can be saved when it finishes, so that later jobs start from it (specs/0003-disks.md). Nothing runs before a workflow's jobs to set this up: the service binds each run's scope at its first job's check, from what GitHub told the job's runner, confirmed against GitHub's own records. Nothing runs while no job is queued, apart from storage. Repositories that use it are **consumers**: any repository of the organization.

The service provides compute, consumers' images and saved disks. It never decides what a job may do in a consumer's own cloud resources, and a job's machine has no identity that can reach them: its account has no role anywhere (specs/0002-machines.md). A job that needs a consumer's resources signs in with GitHub's OIDC token through that consumer's own workload identity federation.

## Only the `lanescape` organization

The code is public under the MIT License, so anyone may read or copy it. Only the `lanescape` organization may use the service, and it's built so that no one else can:

1. **The GitHub App is private to the organization.** It's set to install only on its owner's account, so no other organization or person can install it, and the service registers runners nowhere else.
2. **Every check is by ID.** The organization's ID is in the service's configuration; a repository is a consumer if its owner ID is that, whatever its name. Every endpoint checks the owner ID GitHub reports, so a renamed or look-alike organization never matches.
3. **Runners register only in the organization's runner groups,** one per repository, made by the service (below).
4. **Machines, saved disks and images are private to the project.** Compute Engine images are visible only within their project unless shared, and the service never shares one. Consumers' images are in an Artifact Registry repository that only the service's own accounts may read: no one outside the project, and inside it only jobs on the service's machines, through the short-lived pull tokens the service gives them (specs/0006-images.md, Pulling). The service's bucket enforces public access prevention. Nothing the service stores can be read from outside the organization, so no one else's reads cost it anything.
5. **Forks get nothing of the service's** (below), and the actions in `lanescape/actions` do nothing of the service's outside the organization. Anyone can reference a public action; outside the organization it does nothing of the service's, and the service refuses it anyway.

A consumer's own buckets and identities are the consumer's to keep private: public access prevention on, no sign-in for a fork's job, and for a `pull_request_target` run's job only what the consumer means a contribution to have (Forks and contributions, below).

## Components

All of it runs in project `lanescape-dev`, region `northamerica-northeast1`, and is defined in this repository's Terraform (specs/0004-deployment.md).

- **The service,** one Go program on Cloud Run, with GitHub's webhook, the reconcile endpoint, the image, disk, save and pull-token requests, the job-started check, the job-finished report and the builders' requests.
- **A GitHub App,** "Lanescape Runners", installed on the organization. It creates and manages a runner group per consumer, registers just-in-time runners in them, lists jobs and reruns runs, reads runs, pull requests and environments' approvals, and reads consumers' files: `.github/runners.json` from the default branch, and from a run's commit, the files its disks and images depend on, with the permissions specs/0004-deployment.md lists. Its webhook delivers `workflow_job`, `workflow_run` and `pull_request` events; of a pull request's, only its closing starts a pass.
- **Pub/Sub.** The webhook endpoint checks the delivery's signature and publishes its body to a topic, with the delivery's event as the message's attribute `event`, and a push subscription delivers it to the reconcile endpoint, which records a pull request's closing, by GitHub's `closed_at`, before acknowledging it, since GitHub no longer shows it once the pull request is reopened (specs/0003-disks.md, Expiry). A log sink publishes Compute Engine's preemption and guest-shutdown events for the service's machines to another topic, pushed to the same endpoint, which records each preemption in the bucket before acknowledging it.
- **Cloud Scheduler** calls the reconcile endpoint every 5 minutes. Events can be lost, delayed or duplicated, so a pass works from what GitHub and Compute Engine report when it runs, never from the event that started it, and the sweep catches anything an event missed.
- **A bucket,** `lanescape-runners`, for the service's state: the lease, runs' bindings, records of preemptions, saves, resumes, builds and images, boot logs and builds' logs.
- **An Artifact Registry repository for consumers' images,** `lanescape-runners-images`, beside the service's own, `lanescape-runners`. The service's account manages it; two accounts with no other role exist only for the short-lived tokens the service mints of them: `lanescape-runners-puller`, which reads it, for jobs' pulls, and `lanescape-runners-pusher`, which can upload to it but not delete or tag, for builders' pushes (specs/0006-images.md).
- **Secret Manager** holds the App's private key and webhook secret. Their values are added by hand, once.

What machines, disks and images exist, and what they're for, is in their names and labels; what jobs want is in GitHub; what can't be read back from either is in the bucket.

## Runner groups

GitHub gives a job any runner, in a group its repository may use, whose labels include all of the job's. A group per repository keeps one repository's job off a machine made for another's, which its check would refuse. The first time a consumer queues a job, the service creates its group, `lanescape-runners-<repository ID>`, limited to that repository, and registers that consumer's runners there and nowhere else. Every machine boots the same base image, with the service's own runner and hook, and holds nothing of any run's until its job is admitted, so no machine needs a group of a scope's own: whichever of the repository's jobs takes it, the job-started check decides (specs/0002-machines.md). A job that asks for the group by name, `runs-on: {group: ...}`, with no selector, may be given one of its runners, and its check refuses it, since its labels aren't a selector.

## Endpoints

The service is reachable from the internet, so every endpoint authenticates its caller itself:

- **The webhook** checks GitHub's HMAC signature over the body before reading it as JSON, with a size limit on the body, and ignores deliveries for any other organization.
- **The reconcile endpoint** accepts only Google-signed OIDC tokens whose audience is the service, and whose account is the scheduler's or the push subscriptions', verified as such.
- **The image, disk, save and pull-token requests, the job-started check, the job-finished report and the builders' requests, for their build's files, their log, their push token and their result,** accept only a machine's Compute Engine identity token in the full format, whose audience is the service and whose project, zone and instance ID are a machine the service made (specs/0002-machines.md, specs/0006-images.md). An image, disk, save or pull-token request is answered only for the job the service admitted on that machine, while it runs, and its run; a builder's, only for its own build, and its push token only once, after its build steps have ended. A job-started check binds its job's run only from that machine's first check, and only as GitHub's records confirm (specs/0002-machines.md, Binding a run). No endpoint accepts a GitHub token.

Neither the service nor any program of its own on a machine ever logs a credential: no token it mints or is given, no JIT runner configuration, identity token, upload session's URI or signed URL; nor does the service write one to its bucket.

The endpoints are versioned, `/v1/...`. Machines and their programs come from the service's own base images, so they speak the version of the service that made them; a change that breaks `/v1/` comes as `/v2/` beside it, and `/v1/` goes once no machine or action uses it.

## Passes

One pass runs at a time, under a lease in the bucket: an object taken with a generation precondition, valid for 10 minutes, renewed every minute during the pass with the same precondition, and released at its end. A pass has an absolute deadline of 7 minutes from its start. Every call it makes to GitHub or Google is capped by the time left, and reading the queue has a shorter deadline of its own, so a slow GitHub can't starve cleanup. A pass whose renewal fails stops changing anything at once. Cloud Run's request timeout, the scheduler's attempt deadline and the push subscriptions' acknowledgement deadlines are all 10 minutes, above the pass's deadline. A push that finds the lease held is answered with a retryable error, and Pub/Sub delivers it again with backoff; an event is acknowledged only once a pass has run after it arrived.

A pass:

1. Lists the queued jobs of every consumer's runs, the service's machines, disks and images, and its records.
2. Fails builds past their deadlines, and answers the requests of runs whose machines can't wait for theirs, before any capacity is given out (specs/0006-images.md).
3. Gives queued jobs machines, and requested image builds their builders, in one order, oldest first, from one pool for every consumer (specs/0002-machines.md, One pool), and records the output of builds that succeeded and pushes the indexes of images whose every architecture is built, checking each build's deadlines again just before it starts a builder or calls an image ready (specs/0006-images.md).
4. Saves the work disks of jobs that asked, and makes resume images for preempted Spot jobs (specs/0003-disks.md).
5. Reruns runs that lost a Spot job to preemption, once they've finished.
6. Deletes what's finished, too old, expired or orphaned, and removes offline runner registrations named after its machines.

A failure on one machine, job or disk doesn't stop the rest of a pass. If the service itself fails, Compute Engine still stops every machine at its maximum run duration, leaving only its disks to pay for.

## Forks and contributions

A job from a pull request whose head is in another repository is never given one of the service's machines, except for an approved contribution, below. The service makes no machine for any other such job, and if one takes a machine made for another job, the job-started check refuses it before its first step, and before its containers start (specs/0002-machines.md). In a fork, no runner carries the service's selectors, so a consumer's workflow skips the jobs that name them there, or picks another label for them. It tells both cases apart by expressions: in a fork's own runs, `github.repository_owner_id` isn't the organization's; in a fork's `pull_request` run into the consumer, which runs in the consumer's repository, the event's head repository's ID isn't `github.repository_id`; an approved contribution's `pull_request_target` run has a fork's head too, and does use the service's machines. The service makes no machine for a fork's `pull_request` job that names a selector, and cancels its run, so it doesn't wait for a machine that never comes. A fork's pull request runs, at GitHub's expense, whatever needs nothing of ours.

**Approved contributions.** A consumer may also run a contributor's pull request on the service's machines, through a `pull_request_target` workflow with a contribution job: one that names the environment `contribution`, runs only the default branch's code, and that every other job of the run on the service's machines needs. The environment's required reviewers are the consumer's maintainers, and each push to the pull request makes a new run that waits for approval again. The contribution job's check binds the run to the event's pull request, and only if GitHub records an approval of the `contribution` environment for that run (specs/0002-machines.md, Binding a run). Every other check still applies. Until it's bound, the run's jobs are admitted only on the smallest shape, standard, with no work disk, no image and no pull token, which is all a `pull_request_target` workflow that runs only the default branch's code needs.

A `pull_request_target` run runs the default branch's workflow file with the base repository's privileges, so its jobs' tokens name default-branch code even when a job runs the contributor's. So:

- a job that runs the contributor's code checks out exactly `github.event.pull_request.head.sha`, the commit the approved run was made for, never the branch, without credentials, so the head repository must be readable without them: contributions come from public forks of public repositories;
- it has no secrets, and `permissions: {}`, except that a job that must sign in to the consumer's own cloud resources, through the consumer's own identity provider, may have `id-token: write`, and nothing else. That lets the contributor's code mint tokens of the base repository, for any audience, while its job runs;
- it never names the `contribution` environment, which only the contribution job does, so one approval admits the run, and the contribution job, which runs no contributor code, is what every other job waits for;
- it saves work disks, and builds and uses images, only in that pull request's own scope (specs/0003-disks.md, specs/0006-images.md): an image the contribution defines is built from its own head commit, by its own run's request, on a builder whose steps reach no credential, and serves only its own pull request's runs. A job of the run that runs only the default branch's code, such as a trusted final job, never runs in the contribution's image, which is the contributor's code;
- nothing that trusts a token's `job_workflow_ref` or `ref` may trust them for a `pull_request_target` run, whose tokens name the default branch's workflow and ref even in a job that runs the contributor's code. Every party that trusts the consumer's tokens, the consumer's own identity provider included, tells those tokens apart by `event_name`, and gives one only what the consumer means a contribution to have, never what it gives the default branch's runs; a party that can't refuses them. The service takes no GitHub token at all: it binds a run from what GitHub's runner was told, on a fresh machine before any step, and confirms it against GitHub's records, so a contributor's token can bind nothing, and a `pull_request_target` run binds only its event's pull request, once a maintainer has approved the run (specs/0002-machines.md, Binding a run);
- a workflow on the default branch never restores from GitHub's Actions cache, which a `pull_request_target` job's runtime token can write to as if it were the default branch.

Whether a contribution's results count as the pull request's required checks is the consumer's to arrange; a trusted final job can post each result as a commit status on the pull request's head commit.
