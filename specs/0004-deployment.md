# Code, tests and deployment

## Code

Go, at the latest stable release, pinned by `go.mod`'s `toolchain` line, using Google's and GitHub's own Go SDKs for their APIs. One module:

- `cmd/runners/`: the service.
- `internal/`: the reconciler, and the clients for GitHub, Compute Engine, Cloud Storage and Pub/Sub, behind interfaces the emulators also serve.
- `emulators/`: the emulators (below), and `emulators/service`, the emulator of the interface for actions that consumers test against (specs/0005-interface.md).
- `conformance/`: the interface's test suite, which holds the emulator and the service to the same answers.
- `config/`: the organization's ID, shapes, the runner version, and the base images' Debian images, Go checksums and builders (`base.yaml`).
- `machine/`: the supervisor, the job-started hook and the work disk's mount program, with the units and rule that start them, and the builder's script, `build-base.sh`, embedded into the service's binary and baked into the base images by the service's own builders (specs/0003-disks.md, Making a base image), so that what a machine does before its job starts is the service's alone, and what it does after, the service checks against GitHub's records (specs/0002-machines.md, A machine's life): every machine boots a base image, and no consumer can change one (specs/0003-disks.md).
- `cd/`: CD's preview and apply of `infra/`, which `cd.yml` runs, and its test against stand-ins for gcloud and curl.
- `infra/`: the Terraform for everything the service runs on.
- `bootstrap/`: the Terraform that lets `infra/` be applied at all (below).

Never log credentials, JIT runner configurations, OIDC tokens, identity tokens, the App's installation tokens, upload session URIs or signed URLs.

## Tests

Tests run against emulators this repository builds and maintains itself, in Go, in `emulators/`. No test depends on an emulator, container or fake from anyone else. Each emulator serves the real API over HTTP, as the SDKs call it, so the service's real clients run against it unchanged, and each keeps state and fails as the real service does:

- **GitHub:** the REST endpoints the service and the actions use, signed webhook deliveries, pull requests that close, merge and reopen, runner groups and just-in-time registration, environments and their approvals, and an OIDC issuer with its own signing keys and published key set, so tests can mint tokens with each claim wrong in turn. A runner stand-in registers, takes jobs as GitHub would hand them out, including to a machine made for another job, and calls the job-started hook as the real runner does, before a job's first step, with a job's environment able to set what a real job can; after a hook that fails, it still runs the steps whose condition is `always()` or `failure()`, as the real runner does.
- **Compute Engine:** instances, disks, images and zone operations; disks attached to running instances; serial console output, and Cloud Logging's copy of it, which outlives its instance; Spot preemption mid-job; stockouts, quota errors and responses lost after the work was done; `requestId` deduplication; guest attributes; and identity tokens in the full format, signed by the emulator's own keys.
- **Cloud Storage:** objects with generation preconditions, for the lease and the records.
- **Pub/Sub and the scheduler:** publishing, signed pushes, redelivery and duplicates.

Every behaviour in these specs has a test. End-to-end tests run the real service against the emulators, with a client that speaks the interface for actions (specs/0005-interface.md) as the actions do: a pull request's run bound from GitHub's records and through to its work disk and its saves, a job failed with its reason, a job taking a machine made for another run's, a Spot machine preempted mid-job and its run resumed, a job stopped at the age limit and its run resumed, a fork's job refused, and an approved contribution bound by its contribution job. Those interface tests are the service's promise to the actions: a change that breaks one breaks `/v1/`. The conformance suite in `conformance/` runs the same cases against the real service, wired to the emulators, and against `emulators/service`, with its own model of GitHub and on a GitHub emulator, and each must pass every one (specs/0005-interface.md, Testing against the emulator). The actions themselves are tested in `lanescape/actions`, against `emulators/service` at the version of this module they pin, never the real service; conformance is this repository's promise that what passes there passes here. `terraform validate` and `terraform fmt -check` run on every change to `infra/` and `bootstrap/`.

## CI and CD

Workflows here run on Blacksmith, never on this service's own machines, so a broken deploy can always be fixed by the next one. A pull request from a fork runs on GitHub's runners instead; it needs no credentials, since nothing in CI does.

- **`ci.yml`, on pull requests:** `go vet`, `gofmt`, the tests, and the Terraform checks. `cd.yml` calls it too, as a reusable workflow, so the two never check different things.
- **`cd.yml`, on pushes to main:** the same checks, then a deploy that needs them. It builds the service's image with `ko`, for `linux/amd64`, on the base image `.ko.yaml` names by digest, so that building the same commit again gives the same image, and pushes it to Artifact Registry, tagged with the commit and the run's attempt, since the repository's tags are immutable; what it deploys is the image by its digest alone, `<repository>/runners@sha256:<digest>`, as `infra/` requires. Then it asks Infrastructure Manager for a preview, and an apply, of `infra/` from this repository's git source at that commit, never an upload, which would need project-wide Cloud Storage access, with the image's digest as an input, and the run's ID and attempt as another, which `infra/` puts on the Cloud Run service's template, so that every apply makes a new revision, even of the same image: rerunning a deploy whose revision couldn't start, such as the first, before the App's secrets had values, starts one afresh. The artifacts bucket `lanescape-runners-infra-manager` holds their artifacts and logs. One apply changes the infrastructure and deploys the service together. A deploy that changes the base images' key leads the service to make new ones (specs/0003-disks.md). The service's images are pushed to `lanescape-runners`. The job prints the preview's and the apply's logs, which the deployer may read from the artifacts bucket, and fails if anything does. CD's runs go one at a time, each in its turn, in the order they began to wait, and none is cancelled, waiting or running (GitHub's `concurrency` with `queue: max`), up to GitHub's 100 waiting, past which it cancels the newest; then the maintainer reruns main's head's run once the queue has room. A deploy goes ahead only if its commit is still main's head when its turn comes, and otherwise is skipped, with a notice, since main's head has a run of its own, waiting behind it: so an older commit, a maintainer's rerun of one included, never deploys over a newer one, and main's head is always deployed once its run's checks pass.

**What CD is given.** CD takes what it needs to sign in and deploy from the repository's Actions variables, which the maintainer sets once `bootstrap/` is applied (bootstrap/README.md, After the first apply): `RUNNERS_WORKLOAD_IDENTITY_PROVIDER` and `RUNNERS_DEPLOYER`, to sign in; `RUNNERS_IMAGE_REPOSITORY`, where `ko` pushes; `RUNNERS_INFRA_MANAGER_BUCKET`; and `RUNNERS_GITHUB_APP_ID`, the App's ID, which the apply passes to `infra/`. None of them is a secret. Until all of them are set, and in any repository but this one, the deploy is skipped, with a notice on the run that says which are missing, and the checks still run: so merging `cd.yml`, or any change before the maintainer has set them, deploys nothing. Setting them is what lets the next push to main deploy, or a rerun of the latest one's workflow.

`infra/` gives the service its settings in its environment: `RUNNERS_AUDIENCE`, its own Cloud Run address, which must be `endpoints.Service` (specs/0005-interface.md) or it refuses to start; `RUNNERS_PROJECT`, the project its machines are in; `RUNNERS_BUCKET`; `RUNNERS_WEBHOOK_TOPIC`, the full name of the topic the webhook publishes to, which `bootstrap/` makes; `RUNNERS_GITHUB_APP_ID`; the files of the App's key and webhook secret, mounted from Secret Manager; and `RUNNERS_RECONCILE_ACCOUNTS`, the scheduler's and the push subscriptions' accounts. Its Cloud Run service keeps CPU allocated outside requests, since a supervisor's report starts a pass after its response has been sent.

CD signs in with GitHub's token through the workload identity pool `lanescape-runners-github`, whose provider accepts only a push to main from `cd.yml` in this repository. That identity, `lanescape-runners-deployer`, can push to the service's Artifact Registry repository, start previews and applies of the `lanescape-runners` Infrastructure Manager deployment, read its Terraform state and take its lock, which a preview of a deployment that exists needs, and read and release the lock, as a precaution. It uses nothing else, but IAM can't limit Infrastructure Manager by name, so its grants reach every deployment in the project, other teams' state included (bootstrap/README.md, What IAM can't limit). The apply runs inside Google Cloud as `lanescape-runners-infra`.

That doesn't make CD less powerful than the infra identity: whoever controls the Terraform that CD applies, which is whoever can merge to main, can make the infra identity do anything it may do, provisioners included. So the infra identity's authority is CD's, and it's kept to what `infra/` manages:

- the service's own resources, by their names: its Cloud Run service, which it deploys but can't make or delete, its bucket, and secrets' metadata, and the access to each of those, set on the resource itself. That access can still let a merged change give someone more of those resources, such as reading the bucket; beyond them, it reaches only what bootstrap/README.md lists under What IAM can't limit;
- no project-level IAM administration, no service account creation or key management, no role definitions, and no log sinks. The service's accounts, its custom roles, every project-level grant, and the log sink with its fixed filter for the service's own machines are in `bootstrap/`, which only a maintainer applies, so a merged change can't widen what the service's accounts hold in the project, nor send the project's other logs to the service;
- nothing else IAM can't limit by name, beyond what bootstrap/README.md lists under What IAM can't limit: Infrastructure Manager's deployments, their state and their locks, making buckets and secrets, and some lists and reads. The network and its subnetwork, the Pub/Sub topics and push subscriptions, the scheduler job, and the Cloud Run service's first, empty version are in `bootstrap/` too, since an identity that could make or change them could change every other team's networks, topics, subscriptions, jobs and services in the project. The Cloud Run service's first version is an unreachable shell, which `infra/` adopts and deploys.

Infrastructure Manager's Terraform runs no provisioners or external programs here: `ci.yml` refuses `provisioner`, `local-exec` and `external` data sources in `infra/`. That keeps a careless change from running code as the infra identity; a deliberate one would be a merged pull request, which its author answers for.

Whoever merges to main deploys. No agent reviews, approves or merges a pull request without the explicit instruction of the person it works for, for that pull request.

## Bootstrap

`bootstrap/` makes what `infra/` can't make for itself, or mustn't be able to change: the APIs, the Terraform state bucket, Infrastructure Manager's artifacts bucket, `lanescape-runners-infra-manager`, the service's Artifact Registry repository, `lanescape-runners`; every service account (the service's, the machines', the scheduler's, the push subscriptions', `lanescape-runners-push`, the deployer's and the infra identity), the service's right to act as the machines' account, to make machines with it, and to mint tokens of no account, the service's custom roles and every project-level grant, the network with its subnetwork and no firewall rules, the Pub/Sub topics and push subscriptions, the scheduler job, the Cloud Run service's first, empty version, the log sink for Compute Engine's events about the service's machines, and, for their boot logs (specs/0002-machines.md), a log bucket of the service's own, `lanescape-runners-serial`, a sink with a fixed filter that routes there only the serial console entries of the service's machines, by their `lsr-` names in its zones, and a view of that bucket that the service's account alone may read, since a view of the project's default log bucket can't be limited by instance name; and the CD pool. A maintainer applies it by hand, with their own credentials, and again whenever it changes. Its own state is kept in the same state bucket.

## The GitHub App

The maintainer makes and configures the "Lanescape Runners" App by hand, private to the organization (specs/0001-architecture.md). Besides what it needs for runner groups, runners, jobs, runs and environments' approvals, its permissions include **Contents: read**, to read `.github/runners.json` and the files that disks' keys depend on at a run's commit, a contributor's pull request's head commit included, and `.github/runners.json` at the heads of the default branch and each listed long-lived branch, whose declarations keep their scopes' saved disks; **Pull requests: read**, to read a pull request's state, base and head, and it subscribes to the **Pull request** event, whose closing deletes the pull request's scope at once (specs/0003-disks.md), as well as **Workflow job** and **Workflow run**. The webhook ignores every other event, and every other action of a pull request's.
