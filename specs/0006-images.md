# Consumer images

A consumer can define images of its own, so that its jobs start with the system packages and tools they need instead of installing them on every machine. An image is the service's base image for an architecture (specs/0003-disks.md) with the consumer's own script run on it, as root. The consumer defines and versions it in its own repository; the service builds it, and a job boots it by naming it in its selector, `-image-<name>` (specs/0002-machines.md).

An image holds what the machine needs, and changes when its definition does. What a commit pins, such as a source tree, a toolchain named in a file or a private SDK, belongs on a work disk (specs/0003-disks.md), fetched by the job under the consumer's own identity.

## Defining an image

The consumer declares each image in `.github/runners.json` at the run's commit, under `"images"`, from its name to the directory that defines it, relative to the repository's root:

```json
{"images": {"build": ".github/images/build"}}
```

The directory holds:

- **`image.json`:** `"architectures"`, a non-empty list of `amd64` and `arm64`, each at most once; optionally `"disk_gb"`, the boot disk's size, from 100, the base image's, to 1000, and 100 if left out; and optionally `"timeout_minutes"`, how long a build may take once its builder is made, from 1 to 60, and 30 if left out. Any other field fails the build.
- **`init.sh`:** run by `bash` as root, in a copy of the directory, on the base image for the architecture.
- **`check.sh`,** optionally: run the same way after `init.sh`, to show the image does what its jobs need; if it fails, so does the build.
- Any other files the scripts read.

The directory holds only regular files and directories: no links and no submodules, at most 1,000 files and 10 MiB in all.

**Built only from public sources.** A builder (below) has nothing of the consumer's but the directory, and its machine's account has no role anywhere, so a script can fetch only what anyone could. Nothing private belongs in an image: what's private, or pinned by a commit, goes on a work disk.

## Versions

An image's **version** for an architecture is the first 20 hex digits of the SHA-256 of these parts, in this order: the image's name, the architecture, the key of the service's base image for that architecture, then each file of the directory, by its path relative to the directory and its contents, in the bytewise order of the paths. Each part is written as a disk key's are (specs/0003-disks.md, Keys): its length in bytes, an unsigned 64-bit big-endian number, followed by its bytes. For example, image `build`, `amd64`, the base image key `0123456789abcdef0123`, and a directory of `image.json` holding `{"architectures": ["amd64"]}` and a newline and `init.sh` holding `apt-get install -y gcc` and a newline give the version `167e954508294da56a5c`. So any change to the directory, or a new base image, makes a new version.

**A run uses the version its own commit defines,** never another. Images belong to scopes as saved disks do (specs/0002-machines.md, Scope). A run's job boots its own scope's image of that name, architecture and version, or else its base's of the same version, along its restore chain: never a different version, and never one of another pull request's. Main's images are built only by main's runs, a long-lived branch's only by its own, and a pull request's serve only that pull request's runs: after a pull request that changes an image merges, main builds its own, even of the same version, so nothing a pull request built ever reaches main. A `read` run, which saves nothing, uses main's version if there is one, and otherwise one built for that run alone, which goes when the run finishes.

A run's versions are fixed the first time it asks for the image (Building, below): the service records, for each architecture, the base image's key it used and the version it made, and every later request, build and machine of the run, in every attempt, automatic or a maintainer's, uses that record. So a new base image partway through a run never changes what it boots, and a rerun of only the jobs that failed finds the image its earlier image job made. If a later attempt's job needs an image that the record names and that has gone since, such as a `read` run's, which goes when the run finishes, or one past its expiry, the service builds it again for the run's scope from the run's commit, on the base image the record names, or on the current one if that has gone too, and records what it made; the job's machine is made once it's ready, and a job whose rebuild fails is stopped, saying why (specs/0002-machines.md, Failing a job). The service picks the image itself once per run and selector, the first time it makes a machine for it, and records the image it chose with the run's choices for that selector (specs/0003-disks.md), so every job of the run with that selector boots the same one.

## Building

A run builds the images it uses in a job of its own, which the jobs that boot them need, on one of the service's machines. Its `image` action (lanescape/actions) asks the service, by `POST /v1/images` signed with its machine's identity token (specs/0005-interface.md), for an image of the run's commit by name. For each of the image's architectures, the service answers with the version's image if the run's restore chain has it, and otherwise joins the build of that scope, name, architecture and version already under way, or starts one. The action waits, printing each build's log, and fails if any build fails. So the jobs that boot the image are queued only once it's ready; if its build fails, GitHub skips them, and rerunning the failed job asks for a new build. A failed build never falls back to another version.

At most one build of a scope's image, name, architecture and version runs at a time, and the first that succeeds is that version's image, so a later build never replaces it. Every run that starts or joins a build is recorded with it, and the machines of those runs alone may follow it; a `read` run's builds are its own, keyed by its run, and no other run joins them.

**Capacity and deadlines.** A builder comes from the same pool and quota as jobs' machines, ordered among queued jobs by when its build was requested, oldest first (specs/0002-machines.md, One pool), so builds and jobs take turns by age and neither starves the other. A builder can still wait for capacity that running machines hold, including those of jobs waiting on builds, so a build that hasn't got its builder within 20 minutes of its request fails, saying so, and the jobs waiting on it fail and free their machines. A build has an absolute deadline of 80 minutes from its request, for everything until its image is ready, Compute Engine's making of the image included, and fails at it. Each run that asks for or joins a build is answered by its own machine's deadline too: if the image can't be ready before that machine is 85 minutes old, the service answers that run's requests `failed`, saying so, while the build goes on for any other run following it, so a job always hears the outcome before its machine's age limit.

**The builder** is a standard machine, `lsr-<repository ID>-build-<random>`, labelled `lsr-kind` `builder`, booted from the base image of the build's architecture, on a boot disk of `image.json`'s size, in the service's network, with the machine account that has no role anywhere, no work disk, and no runner: no job ever runs on it. Its supervisor, the service's own program, runs as a builder:

1. It asks the service for the build's directory, signed with its machine's identity token; the service answers only a builder it made, with that build's files, read with the App at the run's commit.
2. It writes them to a new directory owned by root, and runs `init.sh`, then `check.sh` if there is one, as root, with `bash`, in that directory, with a fresh environment and no terminal. It sends their output, and how each ended, to the service as the build's log, in order, signed the same way, every few seconds and once more before it reports, and the service appends each part to `builds/<repository ID>/<build>.log` in its bucket, by its offset, so that nothing is lost or written twice, and serves it to the action. A log is kept to its first 10 MiB, with a line saying what was dropped.
3. If both succeed, it removes what makes the machine itself: SSH host keys, the machine ID, cloud-init's and the guest environment's state for the instance, the build's directory, `/tmp` and the system's logs. Then it reports whether the build succeeded, signed the same way, and powers the machine off.

The service then makes an image of the stopped builder's boot disk, and waits until Compute Engine shows it ready; an image that fails to be made fails the build. The image is `lsr-<repository ID>-img-<series>-<build time>`, where the series is the first 20 hex digits of the SHA-256 of the scope, the name, the architecture and the version, joined by NUL characters. It's labelled `lsr-kind` `image` with the repository ID, the architecture and hashes of the scope, name and version, and recorded in the bucket as `images/<repository ID>/<image>.json` before it's made, as saved disks are. Then the service deletes the builder. A build fails, with the reason in its log, if either script fails, if the builder reports failure or doesn't report before `image.json`'s time limit from the builder's creation, if the builder stops without reporting, if it got no builder in time, or if it isn't ready by its deadline (Capacity and deadlines, above). A builder past its time limit is deleted without an image; Compute Engine itself stops it 30 minutes after it. A build's record and log are kept for 14 days after it ends.

**What an image may change.** `init.sh` runs as root, so an image can change anything on the machines that boot it: the supervisor, the job-started hook, even the GitHub runner. That's what any job can already do on its own machine, with passwordless sudo (specs/0002-machines.md), and it reaches no further, because nothing that keeps scopes apart depends on the machine:

- **Disks and saves are the service's.** A work disk is made and attached only when the service admits a job, from GitHub's record of which job the runner took, and a disk is saved only for an admitted job, on GitHub's conclusion for it, in its run's scope. A machine whose hook never asks gets no work disk, and nothing on it is ever saved.
- **Runners are kept to their run by labels, and a pull request's images to its own runner group.** GitHub gives a runner only jobs that name its selector exactly, and the selector names its run, so the jobs a machine of an image normally gets are those of the run whose commit defined the image, which could already run that commit's code. A machine booted from a pull request's image, or a `read` run's own, registers in a runner group of that scope's own, chosen by the scope that owns the image (specs/0001-architecture.md, Runner groups), so a job that asks for the repository's group by name, rather than a selector, never reaches it.
- **A forged selector reaches only what's public.** A selector's run ID can be copied: another run's job that names it may be handed that machine before the service cancels its run. On a base image the job-started check refuses it before its first step. On an image whose hook was changed, it may run, but what it finds there is the image, built only from public sources, and the machine's account, which has no role anywhere: no work disk, no saved state, and no credential of the run the machine was made for, whose jobs never ran there. So the boundaries that matter, scopes' disks and images and runs' credentials, hold; what the copy costs is the machine, which the service replaces for the job still queued.

The service decides nothing from what a machine booted from an image says: such a machine's checks never bind a run (specs/0002-machines.md, Binding a run). The jobs of a contribution's run that run only the default branch's code, such as a trusted final job, never name the contribution's image, so they never run on its machines. A script runs nowhere but on its builder, which no job ever uses, and which has no identity that can reach anything.

## Expiry

Images go as saved disks do, by marking under the disks' lease, then deletion (specs/0003-disks.md), and every rule still keeps an image that an unfinished run's choice names, or that a machine is booting:

- **A pull request keeps one version of each image and architecture,** its newest; all of its images go at once when it closes, merged or not, and 14 days after their last use if it stays open.
- **Main keeps the two newest versions of each image and architecture,** and any older version that an open pull request's run used last, so that a pull request branched before the image changed still finds main's. A long-lived branch's are kept the same way, and go with its scope.
- **A `read` run's images** go once it has finished.
- **A run's images are pinned while it's unfinished.** When the service answers a run's request `ready`, it records, under the disks' lease, the exact image it means, and that image is kept until the run has finished with no automatic rerun left, as a recorded restore choice keeps a saved disk, so a newer version can't make a waiting run's image go before its jobs boot it.
- **An image nobody has used for 90 days** goes, newest included.
