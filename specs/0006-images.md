# Consumer images

A consumer can define images of its own, so that its jobs start with the system packages and tools they need instead of installing them on every machine. An image is an OCI image: a public base image with the consumer's own script run on it, as root. The consumer defines and versions it in its own repository; the service builds it and stores it in its own registry; a job runs in a container of it, as GitHub's `container:` runs any image. Machines themselves are general: every machine boots the service's own base image, whatever its job runs in (specs/0002-machines.md, specs/0003-disks.md), so nothing a consumer defines ever changes a machine's host, its supervisor, its runner or its job-started check.

An image holds what a job's container needs, and changes when its definition does. What a commit pins, such as a source tree, a toolchain named in a file or a private SDK, belongs on a work disk (specs/0003-disks.md), fetched by the job under the consumer's own identity.

## Defining an image

The consumer declares each image in `.github/runners.json` at the run's commit, under `"images"`, from its name to the directory that defines it, relative to the repository's root:

```json
{"images": {"build": ".github/images/build"}}
```

The directory holds:

- **`image.json`:** `"base"`, the public image it starts from, named by its registry, repository and digest, with an optional tag: `"docker.io/library/ubuntu:26.04@sha256:<64 hex>"`; `"architectures"`, a non-empty list of `amd64` and `arm64`, each at most once, which the base must offer; and optionally `"timeout_minutes"`, how long a build may take once its builder is made, from 1 to 60, and 30 if left out. Any other field, or a base without a digest, fails the build.
- **`init.sh`:** run by `bash` as root, on the base, in a copy of the directory, to make the image.
- **`check.sh`,** optionally: run the same way in a container of the image `init.sh` made, to show the image does what its jobs need; if it fails, so does the build. What it changes is thrown away.
- Any other files the scripts read.

The directory holds only regular files and directories: no links and no submodules, at most 1,000 files and 10 MiB in all. It's mounted for the scripts and isn't part of the image; only what `init.sh` leaves on the base is.

**The base is pinned by its digest,** so that the directory alone decides what a build starts from: a base named by a tag that moves would make the same version build something else next time. It's pulled without credentials, so it must be public, and an image of the service's own registry can't be a base.

**Built only from public sources.** A builder (below) has nothing of the consumer's but the directory, its build steps can't reach any credential, and its machine's account has no role anywhere, so a script can fetch only what anyone could. Nothing private belongs in an image, nor in its directory: every job on the service's machines can pull every consumer's images (Pulling, below). What's private, or pinned by a commit, goes on a work disk.

## Versions

An image's **version** is the first 20 hex digits of the SHA-256 of these parts, in this order: the image's name, then each file of the directory, by its path relative to the directory and its contents, in the bytewise order of the paths. Each part is written as a disk key's are (specs/0003-disks.md, Keys): its length in bytes, an unsigned 64-bit big-endian number, followed by its bytes. For example, image `build`, with a directory of `image.json` holding `{"base": "docker.io/library/ubuntu:26.04@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef", "architectures": ["amd64"]}` and a newline, and `init.sh` holding `apt-get install -y gcc` and a newline, gives the version `540ea620f942bc111a64`. So any change to the directory, its base and architectures included, makes a new version, and nothing else does: a new base image of the service's, or a new version of the service, changes no consumer's image.

**A run uses the version its own commit defines,** never another. Images belong to scopes as saved disks do (specs/0002-machines.md, Scope). A run gets its own scope's image of that name and version, or else its base's of the same version, along its restore chain: never a different version, and never one of another pull request's. Main's images are built only by main's runs, a long-lived branch's only by its own, and a pull request's serve only that pull request's runs: after a pull request that changes an image merges, main builds its own, even of the same version, so nothing a pull request built ever reaches main. A `read` run, which saves nothing, uses main's version if there is one, and otherwise one built for that run alone, which goes when the run finishes. An approved contribution's run builds and uses images in its pull request's scope like any pull request's, from its own head commit.

A run's image is fixed the first time the service answers it `ready` for a name: the service records the image it gave, and every later request of the run for that name, in any attempt, automatic or a maintainer's, gets the same one while it exists, so a newer image of the same version, made after another was deleted, never changes what a run's jobs use partway through.

## The image's reference

An image is stored in the service's Artifact Registry repository for consumers' images, `lanescape-runners-images`, made by `bootstrap/` (specs/0004-deployment.md), under a path of its consumer and scope:

```
northamerica-northeast1-docker.pkg.dev/lanescape-dev/lanescape-runners-images/<repository ID>/<scope>/<name>@sha256:<digest>
```

The scope is `main`, `branch-<name>` or `pr<number>`, and a `read` run's own build's is `run<run ID>`. Each architecture's image is pushed by its digest, never by a tag, and once every architecture of a version is built, the service pushes an OCI image index naming them, in the order of `image.json`'s list; the index's digest is the image's. Its **reference** is always that path with that digest, so what a job runs is exactly what its build made, whatever else the path ever holds. Each scope's images are a package of their own, so deleting one scope's image never touches another's, even of the same content.

## Building

A run asks for the images it uses in a job of its own, which the jobs that run in them need, on one of the service's machines, normally of the smallest shape. Its `image` action (lanescape/actions) asks the service, by `POST /v1/images` signed with its machine's identity token (specs/0005-interface.md), for an image of the run's commit by name. The service answers with the image's reference if the run's restore chain has the version, and otherwise joins the build of each architecture of that scope, name and version already under way, or starts one. The action waits, printing each build's log, and fails, with the service's reason, if any build fails, or if the request is refused, such as for an image the run's commit doesn't declare or a definition that isn't valid. Otherwise it outputs the reference, and later jobs name it in `container:`. So the jobs that run in the image are queued only once it's ready, the wait is a job of its own in the run's graph, and if its build fails, GitHub skips them, and rerunning the failed job asks for a new build. A failed build never falls back to another version, nor to another image.

At most one build of a scope's image, name, version and architecture runs at a time, and the first that succeeds is that architecture's image for the version, so a later build never replaces it; once every architecture has one, the service makes the image's index. Every run that starts or joins a build is recorded with it, and the machines of those runs alone may follow it; a `read` run's builds are its own, in its run's scope, and no other run joins them. A build that failed is never joined, and stays the answer to every job that started or joined it: a repeated request from the same job, such as a retry after a lost answer, gets `failed` with its reason, never a new build. A request from another job of the run, such as its image job's in a rerun, starts a new one.

**Capacity and deadlines.** A builder comes from the same pool and quota as jobs' machines, ordered among queued jobs by when its build was requested, oldest first (specs/0002-machines.md, One pool), so builds and jobs take turns by age and neither starves the other. A builder can still wait for capacity that running machines hold, including those of image jobs waiting on builds, so a build that hasn't got its builder within 20 minutes of its request fails, saying so, and the image jobs waiting on it fail and free their machines. A build has an absolute deadline of 80 minutes from its request, for everything until its image is pushed and recorded, and fails at it. Each run that asks for or joins a build is answered by its own machine's deadline too: if the image can't be ready before that machine is 85 minutes old, the service answers that run's requests `failed`, saying so, while the build goes on for any other run following it, so a job always hears the outcome before its machine's age limit.

**The builder** is a standard machine of the smallest shape of the build's architecture, `lsr-<repository ID>-build-<random>`, labelled `lsr-kind` `builder`, booted from the service's base image of that architecture, which has Docker Engine (specs/0003-disks.md), on a boot disk of every machine's size, `boot_disk_gb` in `config/shapes.yaml`, so an image that builds also fits on the machines that pull it. It's in the service's network, with the machine account that has no role anywhere, no work disk, and no runner: no job ever runs on it. Its supervisor, the service's own program, runs as a builder:

1. It asks the service for the build's directory, signed with its machine's identity token; the service answers only a builder it made, with that build's files, read with the App at the run's commit.
2. Before any step of the build, it shuts the build off from the metadata server: build steps run in containers on a network of their own, from which the builder drops every packet to `169.254.169.254`, the metadata server's address, which `metadata.google.internal` also names; builders have no IPv6 address. A build step can't mint the machine's identity token, read its account's token or read its metadata, so it can't speak to the service as the builder. If the supervisor can't put that in place, the build fails before any step runs.
3. It pulls the base, without credentials, and builds the image with Docker's BuildKit, from a definition that is the service's own, never the consumer's: from the base, run `init.sh` as root with `bash`, in a writable copy of the directory mounted for that step alone, with no terminal; then run `check.sh`, if there is one, as root, in a container of the result, with the directory mounted the same way, and throw that container away. The image keeps the base's configuration, its user and entrypoint included. No step is privileged, has the host's network or a secret, or has anything of the host's mounted but the directory; no step can reach the builder's Docker. It sends the steps' output, and how each ended, to the service as the build's log, in order, signed with its identity token, every few seconds and once more before it reports, and the service appends each part to `builds/<repository ID>/<build>.log` in its bucket, by its offset, so that nothing is lost or written twice, and serves it to the action. A log is kept to its first 10 MiB, with a line saying what was dropped.
4. Once both scripts have succeeded and every container of the build has exited, it asks the service for a **push token**, signed the same way. The service answers it once per build, and only to a builder of its own whose build is in that state: a short-lived token, for 30 minutes, of the account `lanescape-runners-pusher`, whose only role is on `lanescape-runners-images`, and lets it upload and read, but not delete. Artifact Registry gives tagging with uploading, so the token could also tag; the builder never does. The builder pushes the image, by its digest alone, to the build's path, then forgets the token and reports the build's result, with the digest it pushed, and powers the machine off.

The service then checks that the build's path holds a manifest of that digest, of one image for the build's architecture, and records it as the build's output, `images/<repository ID>/<image>.json`, before anything uses it. When every architecture of the version has its output, it pushes the image's index, with its own account, and the image is ready. Then it deletes the builder. A build fails, with the reason in its log, if either script fails, if the base can't be pulled, if the builder reports failure or doesn't report before `image.json`'s time limit from the builder's creation, if the builder stops without reporting, if the build's path holds no manifest of the reported digest for its architecture, if it got no builder in time, or if it isn't ready by its deadline (Capacity and deadlines, above). A builder past its time limit is deleted; Compute Engine itself stops it 30 minutes after it. A build's record and log are kept for 14 days after it ends.

**What's stored for a version is exactly its build's output.** A build's own code can reach no credential: not the push token, which exists only after every build step has exited, nor the identity token that asks for it, which no build step can mint. The push token can't delete anything, and though it could add or move a tag, nothing the service records, answers or deletes by is a tag: what a job runs is named by a digest the service recorded from a build of the job's own scope, never by a tag or a path alone. So even a push token taken from a builder could only add content, or tags, that nothing names: it couldn't change what any recorded reference means, nor keep an image from expiring, since the repository's tags are mutable and the service deletes them (Expiry, below). The isolation that rests on Docker's containers on a builder is the only thing between a build step and its builder; a script that escaped its container would still reach only its own build's output and a token that can't change any other.

## Pulling

A job that names an image in `container:` has its machine's Docker pull it before the job's first step, as GitHub's runner does for any job container. The service's base image configures Docker's credential helper for the registry, for the runner's user and for root: a program of the service's own that, whenever Docker pulls from `northamerica-northeast1-docker.pkg.dev`, asks the service for a **pull token** (specs/0002-machines.md, Pulling images), signed with the machine's identity token, and hands it to Docker. A pull token is a token of the account `lanescape-runners-puller`, whose only role is to read `lanescape-runners-images`; it lives for 30 minutes, and the helper asks for a fresh one at each pull, so nothing long-lived is ever on the machine, and nothing writes it to a file or a log. The service gives one only to a machine of its own whose job it admitted, while that job runs, for a run that's bound. A job's `container:` names no `credentials` for the registry.

**What a job may pull.** A pull token reads the whole repository: Artifact Registry's access is per repository, so a job can pull any consumer's image of any scope. That's not what keeps scopes apart. Images are built only from public sources and their directories hold nothing private, so reading one is no breach; what matters is that a run uses its own commit's image and nothing a pull request built reaches main. The first holds because the `image` action outputs the reference the service recorded for the run, by digest, and the second because nothing but a scope's own builds can put an image in a scope's record, and a reference is a digest: a job that names another run's image in its own workflow only runs what that workflow chose, and changes nothing anyone else runs.

**What a pull costs.** Docker pulls the whole image before a job's first step, unlike a disk image, which Compute Engine reads as it's used. For now every machine pulls its job's image straight from the registry, in the same region. Possible later work, not built: keeping Docker's store, with an image's version pulled into it, as a Compute Engine disk image per version, and attaching it to a machine at its job-started check, which would need the check to know which image the job's container names.

## Expiry

Images go as saved disks do, by marking under the disks' lease, then deletion of the image's index and manifests from its scope's package, with any tag that names them (specs/0003-disks.md), and every rule still keeps an image that an unfinished run was answered with:

- **A pull request keeps one version of each image,** its newest; all of its images go at once when it closes, merged or not, and 14 days after their last use if it stays open.
- **Main keeps the two newest versions of each image,** and any older version that an open pull request's run used last, so that a pull request branched before the image changed still finds main's. A long-lived branch's are kept the same way, and go with its scope.
- **A `read` run's own images** go once it has finished.
- **A run's images are pinned while it's unfinished.** When the service answers a run's request `ready`, it records, under the disks' lease, the exact image it gave, and that image is kept until the run has finished with no automatic rerun left, as a recorded restore choice keeps a saved disk, so a newer version can't make a waiting run's image go before its jobs pull it. A maintainer's rerun of only a finished run's failed jobs uses the reference its earlier image job output; if that image has gone since, the jobs' pulls fail, and rerunning the whole run asks for the image again.
- **An image nobody has used for 90 days** goes, newest included. An image is used when a run's request is answered with it, recorded at most once a day.
- **What no record names** goes: every tag in the repository, which no build makes, and every version that no image's record or build under way names, once a day after it was pushed, so content a push token added outside its build costs nothing for long.
