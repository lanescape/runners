# The interface for actions

Consumers' workflows use the service through its selectors, their own `.github/runners.json`, and the actions in this repository's `actions/` (specs/0007-actions.md), which call this service the way many actions call an API maintained elsewhere: through this interface alone, though they live beside it. This spec is everything those workflows and actions may rely on. It's versioned as `/v1/`, and stays compatible: a change that would break an action comes as `/v2/`, beside `/v1/`, which goes only once no action uses it (specs/0001-architecture.md). That promise starts with the service's first release. Until then nothing uses `/v1/`, and it may still change, as it has: runs are no longer bound by `POST /v1/bind`, selectors no longer carry a scope, a run, an image or a disk, a job asks for its work disk in its steps, and for its size and performance, which shapes no longer give, there are no consumer images, so no `/v1/images` or `/v1/pull-token`, and caches replace saved disks, so no `/v1/disks/save` and no family on a work disk.

## Where the service is

The service's address is a constant of this module's package `github.com/lanescape/runners/endpoints`, `endpoints.Service`, beside the organization's immutable ID, `endpoints.Organization`, which is what an action compares `github.repository_owner_id` with, never the organization's name. The address is also the audience of every token sent to it. Every request to the service carries its token as `Authorization: Bearer <token>`.

A token is a credential: the caller never logs one, nor puts one in an output or a file other jobs can read.

**On the service's machines,** Compute Engine's metadata server, `http://metadata.google.internal`, answers `computeMetadata/v1/instance/attributes/lsr-service` with the service's address. An action tells it's on one of the service's machines by that answer; anywhere else the name doesn't resolve, or the attribute is absent. An action asks the metadata server for the machine's identity token anyway (Requests from a job, below), so the same server is the simplest place to learn where it is.

## Selectors

A job names its machine with one selector (specs/0002-machines.md, Selectors), written in the workflow:

```
lanescape-<vCPUs>vcpu-linux-<amd64|arm64>[-spot]
```

```yaml
runs-on: lanescape-80vcpu-linux-amd64-spot
```

A selector is in lowercase. The shapes the service offers are in `config/shapes.yaml`; the smallest is `lanescape-2vcpu-linux-amd64`. Nothing runs to make selectors, and nothing of the run is in them: the service binds every run itself, at its first job's check, from what GitHub told that job's runner, confirmed against GitHub's records (specs/0002-machines.md, Binding a run). A `pull_request_target` run is bound only once a maintainer has approved its `contribution` environment, so a consumer that runs approved contributions gives such a run one contribution job: the only job that names that environment, which every other job of the run on the service's machines needs, and which runs only the default branch's code, on the smallest shape, standard, with no work disk. It needs no step of ours. The service takes no GitHub token, so a contributor's code can't bind anything with one; **every party that does trust the consumer's OIDC tokens must tell one whose `event_name` is `pull_request_target` apart, and give it only what the consumer means a contribution to have, or refuse it** (specs/0001-architecture.md, Forks and contributions).

A job's `runs-on` is exactly its selector, and nothing else: GitHub gives a job only a runner that has every label it names, and the service's runners have their selector alone. Outside the organization no runner has these labels, so a job that names one waits for a runner until GitHub gives up. A workflow that also runs in forks skips such jobs there, or chooses another label, by expressions on `github.repository_owner_id`, for a fork's own runs, and on `github.event.pull_request.head.repo.id` against `github.repository_id`, for a fork's `pull_request` run into the consumer, which runs in the consumer's repository and gets none of the service's machines. An approved contribution's `pull_request_target` run has a fork's head too, but does run on the service's machines, so the workflow tests `github.event_name` as well.

## A consumer's files

**`.github/runners.json`** is an object with either or both of two fields:

- **`"branches"`:** an object from each long-lived branch's name to the name of its scope, 1 to 16 lowercase letters and digits, starting with a letter: `{"support/v1": "v1"}` gives pushes to `support/v1` the scope `branch-v1` (specs/0002-machines.md, Scope). The service reads it only from the default branch, never a run's own copy.
- **`"caches"`:** an object from each cache a job restores or saves to its declaration, `{"from": [<path>, ...]}` or `{}`, from which the service makes the cache's key (specs/0003-disks.md, Keys). A declaration also keeps the cache's versions: the default branch's keeps main's, and a long-lived branch's own keeps that branch's. Removing a cache's declaration from the default branch deletes every version of the cache in main's scope, of every key and both architectures, at the service's next pass, and the same for a long-lived branch's file and its scope; a file that isn't valid deletes nothing (specs/0003-disks.md, Deletion).

A cache's name is 1 to 32 lowercase letters, digits and hyphens, starting with a letter and not ending with a hyphen. The service reads `"caches"`, and the files it names, from the run's commit (specs/0002-machines.md, Binding a run), so a pull request that adds a cache or changes its files uses them in its own runs; and it reads `"caches"` at the heads of the default branch and each listed long-lived branch to decide which of their versions to keep. Any other field, `"disks"` and `"images"` included, or a field named in another case, makes the file invalid, and a request that relies on it is refused, saying why.

A consumer's setup scripts, which its jobs run in their own steps (specs/0002-machines.md, Setting up a machine), are its own to name and keep: the service never reads them.

## Requests from a job

From a job on one of the service's machines, signed with the machine's identity token: a Compute Engine identity token in the full format, audience `endpoints.Service`, from the machine's metadata server, got afresh for each request. The service answers only a machine it made whose job it admitted, while that job runs, by GitHub's record of the job as well as the machine's own state, only for that job and its run, and only once the run is bound: an unbound `pull_request_target` run's job gets `403`. Every request below answers `403` with `{"reason": "<why>"}` for a request the service refuses, and `503` with `{"retryable": true}` and a `Retry-After` when GitHub couldn't confirm an answer, which the caller retries; every request is safe to repeat.

## Work disks

**`POST /v1/disks`** asks for the job's work disk, with a body such as `{"size_gb": 500, "iops": 10000, "throughput_mibps": 2400}`: its size and provisioned performance, each a positive whole number, any of which it may leave out for the service's default: 50 GB, 3,000 IOPS and 400 MiB/s; `{}` takes them all. The answer is `200` with `{"state": "making" | "ready", "restored": "none" | "resume"}`: `making` while the service makes and attaches it, which the caller asks again for, every 5 seconds, until `ready`, once Compute Engine shows it attached to the machine; `restored` says where it came from: `none` for an empty disk, or `resume` for the rerun of a job lost to a preemption or the age limit, made from its resume image (specs/0003-disks.md, Resume images). A job has one work disk: a later request is answered about the same disk, and one that names a setting other than the first request's is refused. A request is refused, `403` with the reason, for a setting that isn't a positive whole number, for a size outside what Compute Engine reports the disk's type, `hyperdisk-balanced`, may be or that, with the boot disk, the job's machine type may hold, and, with Compute Engine's own message, for a disk Compute Engine refuses to make, such as with more IOPS than its size allows; once Compute Engine has refused, every later request is refused the same (specs/0002-machines.md, The work disk).

Once the answer is `ready`, the machine mounts the disk at `/work`, on the host, outside the job (specs/0002-machines.md, The work disk). A caller waits until `/work`, as its own process sees it, is that mounted disk. Before that, `/work` is an empty directory owned by root, which the runner's user can't write.

## Caches

A job keeps what's slow to make again as caches (specs/0003-disks.md, Caches). Each request's body is `{"cache": "<name>"}`, naming a cache `.github/runners.json` declares at the run's commit; the scope, the key and the version are the service's to decide. A request is refused for a cache the file doesn't declare, a file it lists that doesn't exist, or a file that isn't valid. A token in an answer is a credential, as the job's own tokens are: the caller never logs it, prints it, or puts it in an output or a file other jobs can read, and uses it only for the objects the answer names.

**`POST /v1/caches/restore`** asks for the run's version of the cache to restore. The answer is `200` with `{"restored": "none"}` when there's none, or `{"restored": "<step>", "bucket": "<bucket>", "objects": [{"name": "<object>", "size": <bytes>, "crc32c": "<CRC32C>", "generation": <generation>}, ...], "token": "<token>", "expires": "<time>"}`: the step of the restore order it came from, `pull_request_exact`, `pull_request_newest`, `main_exact`, `main_newest`, `branch_exact` or `branch_newest`; the version's objects in the bucket, as Cloud Storage held them when it was committed, each with its CRC32C base64-encoded as Cloud Storage gives it; and an OAuth access token that may read those objects alone, until `expires`, an RFC 3339 time. The caller checks every object, its size, CRC32C and generation, before it extracts anything, and fails without extracting anything if one is gone or differs; it then reads each at its generation, through Cloud Storage's JSON API, checking its CRC32C as it reads. An object that changes between the check and the read, which the service never does to a version a run has chosen, fails the restore partway. Every job of the run that restores the cache on the same architecture gets the same version.

**`POST /v1/caches/check`** asks where a restore of the cache would come from now, without restoring it. The answer is `200` with `{"found": "<step>"}`: the run's choice for the cache on the job's architecture, if one of its jobs has restored it and the choice still stands, whatever it chose, `none` included, or else the step of the restore order a restore would pick now, or `none`. The service records no choice, rewrites no version's record, as a restore's reading of a choice does, keeps no version for it, and gives no token, so the run's first restore still chooses, and may find a version that became ready since. An `_exact` answer says a version for the run's key is there; any other says only that the first in the order isn't one, as a scope's own newest comes before its base's version for the key. It's refused as a restore is.

**`POST /v1/caches/save`** asks to save the cache. The answer is `200` with `{"saves": true, "bucket": "<bucket>", "prefix": "<prefix>", "token": "<token>", "expires": "<time>"}` in a scope that saves: the caller uploads the version's objects to the bucket, each named with the prefix, with the token, which may only create objects there, until it expires; then it commits. A repeat before the commit names the same prefix, with a fresh token. In a scope that saves nothing, such as `read`, the answer is `{"saves": false, "reason": "<why>"}`. A job saves a cache once: a request after the commit is refused.

**`POST /v1/caches/commit`** says the cache's version is uploaded. The answer is `200` with `{"objects": <count>, "bytes": <total>}`, what the service recorded under the prefix; a repeat answers the same. A commit with nothing uploaded, with more than 1,000 objects, or with names too long to record, 512 KiB in all, or of a cache the job hasn't asked to save, is refused. The version is restorable once the job has finished and GitHub's conclusion for it is success, from the service's next pass (specs/0003-disks.md, Saving); a version of a job that fails, or that never commits it, goes.

## The machines

Jobs on the service's machines run directly on the machine, booted from the service's Debian 13 base image, on amd64 or arm64, as the runner's user, UID 1001, with passwordless sudo, as on GitHub's runners, and find their work disk at `/work` once their `disk` step has asked for it (specs/0002-machines.md). The base image has Git, Go at the version of this module's `go.mod`, and the other tools specs/0003-disks.md (Base images) lists, with unprivileged user namespaces enabled, and no Docker. After a deploy that changes what an image holds, machines boot the previous image until the new one is ready (specs/0003-disks.md, Which image machines boot), so for a while a job may find the tools of the previous image's build; a job that needs a tool an image has only just gained checks for it, or installs it. A job sets the machine up in its own steps, from its own commit, such as with `run: sudo ./ci/init.sh` after checking out; it names no `container:` or `services:`, which GitHub's runner would need Docker to start before the first step (specs/0002-machines.md, Setting up a machine). A job the service can't serve is stopped before its first step, with the reason in its log, and its run is cancelled; none of its steps run, whatever their conditions (specs/0002-machines.md, Failing a job). Some of what this relies on is to be confirmed on real GitHub at the first deploy (specs/0002-machines.md, To confirm on real GitHub).

## Testing against the emulator

Consumers test their actions against an emulator of this interface rather than the service: the package `github.com/lanescape/runners/emulators/service`, at the version of this module their `go.mod` pins. It implements the requests this spec describes, `/v1/disks` and `/v1/caches/restore`, `/v1/caches/check`, `/v1/caches/save` and `/v1/caches/commit`, and nothing else, and binds runs as the service does. Its caches' bucket, `service.CachesBucket`, is in a Cloud Storage emulator, this module's `emulators/storage`, that the test hands it with `service.WithStorage`, or that it starts itself; `CacheStorage` gives it, so a caller uploads and reads there as it would in Cloud Storage, with the emulator's token, `service.Token`, which the storage emulator doesn't check. It runs in-process as an `httptest` server and verifies machine identity tokens against its own issuer, as the service verifies Compute Engine's. A test drives it through its `World`: it declares a repository, its files at each commit, its branches, pull requests, from the repository or a fork, and pushes to them, and runs and jobs as GitHub would show them, with their environments and approvals; it starts a job as if on one of the service's machines, which binds the job's run by the rules of specs/0002-machines.md from what GitHub shows of the job, as the service's check does, and mints that machine's identity token; and the emulator chooses caches by specs/0003-disks.md, making a committed version ready once its job finishes with success. A test decides how each work disk goes, holding it at `making` or making it `ready`, and reads what was bound, attached and saved: `WorkDisk`, `WorkDiskSettings` and `Caches`. It refuses a work disk as the service does, by the limits this module's Compute Engine emulator gives `hyperdisk-balanced` and every machine type, as Google documents them. It finishes jobs, or completes one in GitHub alone, as if its machine's supervisor never reported, reruns runs as a maintainer, makes GitHub unavailable or adds any other failure through `emulators/fault`, with `Refuse` and `Unavailable` answering 403 with a reason and 503 with a `Retry-After` as the service does. It doesn't mount anything: what a caller sees at `/work` is the test's to arrange.

**One GitHub for both.** A consumer's test that also runs this module's GitHub emulator, `emulators/github`, to give its jobs the API, event and tokens they see, hands that emulator to the service emulator, `service.New(service.WithGitHub(gh))`, and the service emulator takes its view of GitHub from it, in-process, in place of a model of its own: the repositories of the organization the test makes there, their branches, commits and files, their pull requests and each one's commits, runs and jobs, environments and approvals, as they are when each request arrives; so a job started there is bound from the refs, commits, events and approvals GitHub's emulator gave, as the service's check would bind it, and nothing is translated between two GitHubs. The test may change anything in `gh` directly, such as pushing to a pull request's head branch and syncing it, approving a run, finishing a job or closing a pull request; the emulator sees it at its next request or `Binding`. `World`'s methods act on `gh` too; `RepositoryOf`, `PullRequestOf`, `RunOf` and `JobOf` give the handles of what the test made in `gh` itself, and `GitHubRepo`, `GitHubPull`, `GitHubRun` and `GitHubJob` the objects behind a handle. Faults added to `gh`'s API don't reach the emulator, which doesn't call it; `Unavailable` makes GitHub unavailable to it.

The conformance suite, the public package `github.com/lanescape/runners/conformance`, is this repository's promise that the emulator is the service as far as this interface goes. Its cases run in this repository's CI against the emulator, with a model of GitHub of its own and on a GitHub emulator, and against the real service wired to this repository's emulators of GitHub, Compute Engine, Google's issuers, Pub/Sub and Cloud Storage, and each must pass every one: the scopes runs bind, a binding made once and kept by a maintainer's rerun, a tag named like a branch, forks, approved contributions and their contribution job, one pushed to after its approval, a contribution bound to its own pull request only, a run not approved left unbound and refused disks and caches, a job on a machine made for another run's job, disk and cache requests from a run's own machine and refused from any other, and from a job GitHub shows completed, before its machine reports, caches kept to their repository, a cache restored in the run's own scope from each step of the restore order, a new key's save replacing the old key's version once no unfinished run chose it, one work disk per job and one save of each cache, a work disk of the size and performance its job asks for and refused as the service refuses it, a commit with nothing uploaded refused, a failed or uncommitted job's version not restored, a save in a scope that saves nothing, and the shapes of every refusal and retry. A deliberate divergence of either side's answers fails it, which the suite's own tests check. A change to the service that fails a case breaks `/v1/`, and a change to the emulator that fails one breaks consumers' tests.
