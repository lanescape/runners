# The interface for actions

Consumers' workflows use the service through actions maintained in their own repository, `lanescape/actions`, which call this service the way many actions call an API maintained elsewhere. This spec is everything those actions may rely on. It's versioned as `/v1/`, and stays compatible: a change that would break an action comes as `/v2/`, beside `/v1/`, which goes only once no action uses it (specs/0001-architecture.md).

## Where the service is

The service's address is a constant of this module's package `github.com/lanescape/runners/endpoints`, `endpoints.Service`, at the version an action's `go.mod` names, beside the organization's immutable ID, `endpoints.Organization`, which is what an action compares `github.repository_owner_id` with, never the organization's name. The address is also the audience of every token sent to it. Every request to the service carries its token as `Authorization: Bearer <token>`.

## Binding a run

`POST /v1/bind` at `endpoints.Service`, with the job's GitHub OIDC token, audience `endpoints.Service`, binds the run's scope (specs/0002-machines.md), or returns the binding the run already has. A run's first job calls it.

- **The body** is empty, except from a consumer's bootstrap workflow in a `pull_request_target` run, where it's what the job's own event says: `{"pull_request": <number>, "head_repository_id": <id>, "head_sha": "<commit>"}`.
- **The answer** is `200` with `{"scope": "main" | "branch-<name>" | "pr<number>" | "read"}`; `403` with `{"reason": "<why>"}` when the token or its run isn't one the service binds, or the body isn't a binding request; or `503` with `{"retryable": true}` and a `Retry-After`, when GitHub couldn't confirm an answer, or its signing keys couldn't be read, which the caller retries with backoff. Answers may carry other fields, which callers ignore; nothing else is answered.

A token is a credential: the caller never logs one, nor puts one in an output or a file other jobs can read.

**Contributions.** An approved contribution's job that must sign in to the consumer's own cloud resources has `id-token: write`, so the contributor's code can mint the consumer's tokens while it runs (specs/0001-architecture.md, Forks and contributions). With the service, such a token gets only its own run's scope, as `/v1/bind` answers it: the binding the run's bootstrap made, before any job that runs the contributor's code could start, never another, whatever the body says; or, if it calls before the bootstrap, `read`, for good. Its `ref`, the default branch's, binds nothing of main's, since only a push does. `/v1/bind` is the only request of the service's that takes a GitHub token. **Every other party that trusts the consumer's OIDC tokens must tell one whose `event_name` is `pull_request_target` apart, and give it only what the consumer means a contribution to have, or refuse it.**

## Selectors

A job's selector is `lanescape-<vCPUs>vcpu-linux-<amd64|arm64>[-spot][-disk-<family>-<key>]-<scope>`, in lowercase, with the scope the binding returned (specs/0002-machines.md). `<family>` is 1 to 32 lowercase letters, digits and hyphens, starting with a letter; `<key>` is exactly 20 lowercase hex digits, such as the first 20 of a SHA-256. The shapes the service offers are in `config/shapes.yaml`.

## A consumer's files

- **`.github/runners.json`:** an object from each runner name the consumer uses, a shape such as `lanescape-80vcpu-linux-amd64`, to its fallback outside the organization, a label or a list of labels; if the consumer runs approved contributions, `"bootstrap"`, the `job_workflow_ref` of its bootstrap workflow, `<owner>/<repo>/.github/workflows/<file>@refs/heads/<default branch>`; and if it has long-lived branches, such as release branches, `"branches"`, an object from each branch's name to the name of its scope, 1 to 16 lowercase letters and digits, starting with a letter: `{"support/v1": "v1"}` gives pushes to `support/v1` the scope `branch-v1` (specs/0002-machines.md, Scope). Two readers read the file from different commits, for different things. The `runners` action reads the names and fallbacks from the run's own commit, so a pull request that adds a runner can use it; the service decides nothing from those, since it checks every selector itself. The service reads only `"bootstrap"` and `"branches"`, and only from the default branch, never a caller's copy.

## Asking to save a work disk

On the service's machines, a job asks to save its work disk, as the `save-disk` action does, by writing `{"save": true}` to `/var/lib/lanescape-runners/save`, in a directory the runner's user may write, which the supervisor reads once the runner has exited (specs/0002-machines.md). The file is absent on other runners. Anything else in it, a link in its place, or no file at all, asks for no save. Whether the disk is saved is still the service's to decide, from GitHub's conclusion for the job and its run's scope (specs/0003-disks.md); the job learns nothing of it, since it has ended.

## The machines

Jobs on the service's machines run as the runner's user, with passwordless sudo, as on GitHub's runners, and find their work disk at `/work` (specs/0002-machines.md).

## Testing against the emulator

Consumers test their actions against an emulator of this interface rather than the service: the package `github.com/lanescape/runners/emulators/service`, at the version of this module their `go.mod` pins. It implements the one request this spec describes, `/v1/bind`, and nothing else. It runs in-process as an `httptest` server and verifies tokens against this module's OIDC issuer emulator, `emulators/oidc`, as the service verifies GitHub's. A test drives it through its `World`: it declares a repository, its default branch's `.github/runners.json` and its branches, pull requests, from the repository or a fork, and pushes to them, and runs and jobs as GitHub would show them, and mints each job's token; the emulator binds runs by the rules of specs/0002-machines.md; the test finishes jobs, reruns runs as a maintainer, makes GitHub unavailable or adds any other failure through `emulators/fault`, with `Refuse` and `Unavailable` answering 403 with a reason and 503 with a `Retry-After` as the service does, and reads what was bound.

**One GitHub for both.** A consumer's test that also runs this module's GitHub emulator, `emulators/github`, to give its jobs the API, event and tokens they see, hands that emulator to the service emulator, `service.New(service.WithGitHub(gh))`, and the service emulator takes its view of GitHub from it, in-process, in place of a model of its own: the repositories of the organization the test makes there, their branches, commits and default branch's `.github/runners.json`, their pull requests and each one's commits, runs and jobs, as they are when each request arrives; and it verifies tokens against `gh`'s Actions issuer. So a bootstrap's binding request names the commits, IDs and numbers GitHub's emulator gave, as the service's would, and nothing is translated between two GitHubs. The test may change anything in `gh` directly, such as pushing to a pull request's head branch and syncing it, finishing a job or closing a pull request; the emulator sees it at its next request or `Binding`. `World`'s methods act on `gh` too; `RepositoryOf`, `PullRequestOf`, `RunOf` and `JobOf` give the handles of what the test made in `gh` itself, and `GitHubRepo`, `GitHubPull`, `GitHubRun` and `GitHubJob` the objects behind a handle. Faults added to `gh`'s API don't reach the emulator, which doesn't call it; `Unavailable` makes GitHub unavailable to it.

The conformance suite, the public package `github.com/lanescape/runners/conformance`, is this repository's promise that the emulator is the service as far as this interface goes. Its cases run in this repository's CI against the emulator, with a model of GitHub of its own and on a GitHub emulator, and against the real service wired to this repository's emulators of GitHub, Google's issuers, Pub/Sub and Cloud Storage, and each must pass every one: the scopes runs bind, a binding made once and kept by a maintainer's rerun, forks and approved contributions, one pushed to after its approval, a pull request's binding held to its commits, a contribution's token unable to widen its scope, before its bootstrap or after, and the shapes of every refusal and retry. A deliberate divergence of either side's answers fails it, which the suite's own tests check. A change to the service that fails a case breaks `/v1/`, and a change to the emulator that fails one breaks consumers' tests.
